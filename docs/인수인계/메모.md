## 시스템 파이프라인
모션 게이트
-> (배경 변화가 감지되면) Person/Object Detector
-> (사람이 감지되면) Tracker
-> (Detector 바운딩 박스 크기에 따라) Pose Landmarker + 행동 분석 / 연령대·성별 추정

### 모션 게이트
- 대부분의 시간이 매장이 유휴 상태라고 언급
- 카메라가 고정되어 있음
- 프로세스 리소스 관리가 매우 중요함(유휴 상태일 때는 큐에 걸린 분석 수행)
-> 모션 게이트로 Detector 호출도 절약하는 것이 유리할 것이라 판단

### Object Detection 모델로 테스트 해본 것들
테스트 시엔 동일한 양자화 포맷(INT 8)과 추론 백엔드(GGUF 파일)을 사용함

- YOLO11n
- PP-PicoDet-S/XS: 초경량, CPU 최적화됨
- MobileNetV2-SSDLite: 약간 구형이지만 검증됨
- NanoDet-Plus-m-320
- NanoDet-Plus-m-416
- NanoDet-Plus-m-1.5x-320

(Intel) OpenVINO쪽 사전학습 모델도 있는 것 같은데, 아키텍처 호환성 등을 사유로 테스트를 진행하지 못함

YOLO11n이 가장 정확하지만 리소스 사용량도 제일 많고, PP-PicoDet-S가 어느 정도 정확도를 보여줌과 동시에 리소스 사용량도 YOLO보다 낮아서 후보로 나쁘지 않겠다고 판단함.

#### Runtime
PyTorch 등을 그대로 돌리는 것보다 경량 추론 런타임을 사용하여 최적화

- **OpenVINO**: Intel에서 만든 추론 최적화 도구, Intel 하드웨어 특화되어 있음. 그러나 프로세서(4200U)의 공식 지원 대상이 아니라서 강점이 유의미할지는 미지수
- **ONNX Runtime**: ONNX(오닉스) 파일을 실행하는 추론 엔진. 구형 x86 CPU에도 최적화되어 있음
-> ONNX Runtime을 기본으로 사용하고, OpenVINO는 벤치마크로 후보로 두는 것이 (일단은) 적절할 것으로 생각됨

### Pose 추정 모델로 테스트 해본 것들
- **MediaPipe Pose Landmarkerk Lite**: 경량 모델인데 포즈 추정이 상당히 안정적이나 동시에 최대 1명만 추적할 수 있음
- **Lightweight OpenPose (OpenVINO human-pose-estimation-0001)**: 바텀업 방식이라 사람 수가 늘어도 연산량이 거의 일정하며, 원 논문 자체가 CPU 실시간을 목표로 개발됨. 이 CPU에서 1순위 후보.
- **MoveNet MultiPose Lightning (TFLite)**: 한 번의 추론으로 최대 6명의 바운딩 박스+17개 키포인트를 출력. TFLite XNNPACK으로 CPU에서 가볍게 동작.
- **RTMPose-t/s (+ RTMDet-nano 또는 위 탐지기 조합)**: 탑다운 방식 중 CPU 효율이 가장 좋은 축. 다만 사람 수에 비례해 추론 횟수가 늘어나므로 2~3명 수준일 때 적합.
- **PoseNet (MultiPose, MobileNet 백본)**: 구형이지만 매우 가볍고 다중 인원 지원.

### OD + Pose 모델로 알아본 것들
이 모델의 경우 하나의 모델에서 감지와 추정을 동시에 할 수 있다는 장점이 있음.

다만 포즈 추정이 ‘항상’ 필요한가에 대해서는 고민을 해보고 있어서 무조건 OD + Pose를 선택하는 게 좋을지는 의문. -> 예를 들어, 방문객이 몇 시간 동안 체류 하고 있는 지를 알기 위해 포즈를 추정할 필요는 없음. 그냥 감지와 트래커만 잘 붙이면 됨. 이 경우 포즈 추정을 하면 불필요한 리소스를 사용하게 됨.

- **YOLO11n-pose**: 한 모델로 다중 인원의 박스와 키포인트를 동시에 출력. OpenVINO INT8 양자화 시 이 CPU에서도 시도해볼 만한 가장 간편한 통합 솔루션.
- **MoveNet MultiPose**: 위와 마찬가지로 박스+키포인트 동시 출력이므로 통합 후보로도 분류 가능.
- **RTMO-s**: 원스테이지 다중 인원 포즈 모델이지만 nano급 YOLO-pose보다 무거워, 이 CPU에서는 해상도를 크게 낮춰야 함(후순위).

### Tracker
감지와 별개로 트래커를 붙여서 감지한 대상을 계속 연결시키는 게 중요하고, 아래와 같은 후보를 탐색해봄.

- **ByteTrack**: 테스트 결과 성능이 꽤 별로지만, 튜닝을 해서 쓸만하게 만들 수 있을 수도 있음
- **OC-SORT(occlusion 복구에 강점) + ReID**: ByteTrack 보다는 쓸만하지만 여전히 아쉬움. 추가 튜닝을 해야 할 것 같음.

### C로 작성된 프로그램의 파이프라인
```
카메라/파일 입력
    ↓
FFmpeg가 한 프레임 디코딩
    ↓
RGB24 형식으로 변환
    ↓
416×416 비율 유지 리사이즈 및 여백 추가
    ↓
YOLO11n ONNX 추론
    ↓
사람 클래스만 선별하고 NMS 수행
    ↓
원본 프레임에 박스와 신뢰도 표시
    ↓
화면에 실시간 표시 또는 파일로 저장
```

### 프로그램에 적용된 리소스 절감 솔루션들
- ONNX Runtime을 순차 실행하고 기본 스레드를 1개로 제한
- 작업이 없을 때 추론 스레드가 계속 CPU를 점유하지 않도록 busy-wait 종료
- 전처리 결과, 입력·출력 텐서와 영상 버퍼를 매번 생성하지 않고 재사용 함
- 중간 영상 버퍼를 여러 개 만들지 않고 RGB 프레임에 박스를 직접 그림
- 화면 표시만 할 때는 영상 인코딩과 파일 저장을 완전히 생략
- 윈도우에서는 YOLO 추론을 Intel HD 4400으로 넘길 수 있도록 DirectML을 지원하는 코드를 추가함

또한 프로그램 실행 시 `--detect-every 3 --track`를 추가하여 프레임 스킵을 구현할 수 있음. 이 경우 YOLO는 기본적으로 3프레임마다 실행됨.
(결론적으로 프로세스 사용률을 줄이기 위해선 모델 추론 횟수 자체를 줄이는 게 가장 효과적이라는 결론에 도달하여 이에 집중한 정책)

추론되지 않은 프레임의 경우 초기엔 마지막 추론된 결과를 그대로 그렸지만, 정확도를 향상 시키기 위해 중간 프레임은 다음과 같은 방식으로 박스를 그리도록 구현함:
1. 영상을 가로·세로 1/4 크기의 흑백 영상으로 줄이고
2. 사람 박스 안에서 특징이 있는 작은 지점을 찾는다.
3. 다음 프레임에서 가장 비슷한 위치를 탐색한다.
4. 여러 특징점의 이동량 중앙값만큼 박스를 이동한다.
5. 추적 신뢰도가 낮거나 새로운 움직임이 발견되면 3프레임을 기다리지 않고 YOLO를 즉시 다시 실행한다.

또 모델에 입력하는 이미지 크기를 줄일 경우 성능 향상이 눈에 띄게 증가하는 것을 확인하였음. 예를 들어, 640x640에서 416x416으로 줄일 경우 연산량이 50% 가까이 들어들며 1.5-2배 정도의 성능 향상이 확인됨. 다만, 이미지 크기가 줄어들 수록 작은 객체의 추적 정확도가 떨어져서 이는 실제로 테스트를 진행하며 적당한 트레이드 오프가 필요할 것으로 생각됨.

### 라이브러리 관련 내용들
초반 미팅에서 자주 언급된 내용처럼, 라이브러리를 최대한 적게 사용하는 방향에 집중하여 크게 ONNX Runtime, FFmpeg만 사용하고 있음. OpenCV나 별도의 그래픽 라이브러리는 사용하지 않았으며, 네모 박스와 글자는 프로그램이 직접 RGB 프레임에 그리는 방법을 사용 중.
