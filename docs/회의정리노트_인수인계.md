### ① 기술 구조 (어떻게 만들지)

**인식 방식**

- 얼굴 + 몸 스켈레톤 + 안면인식 + 형태 디텍팅을 결합
- 지금은 대부분 안면인식 위주 (키오스크는 입장할 때부터 인식) → 근데 이 방식은 **포즈 인식이 안 됨**
- 그래서 안면인식 + 포즈를 결합, 라벨은 **큐(queue)로 저장**해서 행동패턴 분석

**언어 / 리소스 관리 (핵심 이슈)**

- 계속 검사해야 해서 리소스 관리가 관건 → CPU 최적화를 위해 **C로 분리**
- C = 코어 하나당 제어 가능, 우선순위 뒤로 밀 수 있음
- Rust = C 라이브러리 가져다 쓰기 편하고 병렬처리에 유리
- 솔루션은 보통 1~2코어만 씀. 같이 돌리면 전 코어가 꽉 참 → 조절 필요
- 프레임 처리: 예전엔 프레임 단위로 다 끊었는데, 지금은 **5프레임씩 건너뛰며** 디텍팅

**데이터 처리 / 추상화**

- 스켈레톤 뽑고 → 얼굴로 추상화하는 흐름
- 이미지 들어올 때 CPU 피크 치는 걸 최대한 줄여야 함 (윈도우에서 자주 발생)

- 하드웨어: **4020U 모바일 CPU → 발열 해결이 중요**
- 메모리: 읽어서 들고 교체하는 방식이라 메모리 소모 큼, 대역폭도 메모리(3200/5600)에 좌우됨

**통신**

- REST API를 많이 쓰지만 이 케이스엔 **웹소켓이 유리**할 듯 (인터페이스 만들어서 전송)

- 참고: Node.js 메모리 과다 → Apache에서 Nginx로 넘어간 이유 (Apache는 설정값 많아 무거움)

### ① C++ 객체지향 & 포인터

**함수 포인터 (핵심 개념)**

- 함수를 전달하기 위해 사용 — 이쪽에서 저쪽 함수를 열어주려면 함수 포인터로 다른 곳에서 그 함수를 제어
- 변수 확인엔 메모리 접근이 필요한데, 함수 포인터를 넣으면 그 함수만 가리키니까 **변수 제어가 용이**
- **이중 함수 포인터**(포인터의 포인터): 라이브러리가 프로그램에 쌓여 있어서 **라이브러리를 라이브러리로 감싼 경우**가 많음 → DLL 라이브러리에 쌓임

**클래스 vs 오브젝트**

- 클래스 = 정의 / 오브젝트 = 생성된 객체
- 클래스 파일을 읽어서 오브젝트를 불러오는 것 → **메모리가 가장 중요**
- 프레임 단위로 준비해도 가용범위가 적어 **저전력 모드**가 되면 프레임이 더 쪼개져 끊기는 것처럼 보임 → 저전력 모드 하려면 **C를 알아야 함**

### ② 캡슐화 & 보안 (컴파일 언어의 장점)

**DLL 모듈 & 인터페이스**

- DLL로 모듈을 만들면 외부에서 쓰려면 인터페이스를 열어야 함
- 예: “1번 사람이 들어왔어 → 지금 어떤 상태인지 리턴” 식으로 설계 = **캡슐화**
- 내부 행동은 캡슐 안에 있어 밖에서 알 수 없음 → **보안에도 좋음**

**컴파일 vs 스크립트 언어**

- 스크립트 언어(자바 등)는 밖에서 내부 동작을 알 수 있음 (디컴파일 가능하지만 정확하진 않음)
- 컴파일러는 **번역이 아니라 재조립** → 디컴파일해도 똑같이 안 나옴 = **보안 우수**
- 펌웨어 디컴파일은 어느 정도 가능하나, 캡슐화된 윈도우 프로그램은 불가능
- 라이브러리 배포 주의: 깔려 있다고 가정하고 쓰면 **.NET 버전에 따라 달라짐**

### ③ 왜 C인가 (언어 선택 이유)

- **파이썬 지양 이유**: 인터프리터라 리소스를 너무 많이 잡아먹음
- **자바 지양 이유**: 메모리 접근 불가, JVM이 자바 해석 후 다시 C로 처리하는 구조
- 그래서 **애플리케이션도 C로 제작**
- **로봇 쪽은 전부 C** (연구소에서만 파이썬). 펌웨어는 자바도 C 기반 컴파일러라 결국 다 C
- OpenCV도 실행하려면 **OpenGL을 깔아야 함** → 2D/3D 그래픽 엔진 (유니티·언리얼 이전엔 게임도 이걸로 제작)
- OpenCV 용도: 이미지 충돌 / 거리 측정 / 접근 탐지 등
- **원칙**: 리소스 줄이고 최대한 정밀하게 → 뭘 써도 상관없지만 이 기준이 우선

### ④ 멀티스레드 & 메시지 큐 (동시성 제어)

**스레드 동기화**

- 스레드·세마포어·이벤트 = 여러 스레드 띄워놓고 **동시성 제어**
- 멀티스레드는 *개념* → 개념 이해 + 제어 이해가 핵심
- “빈 곳(로직 구멍)을 찾았을 때 전체 로직이 흔들리지 않게만 하면 됨”

**메시지 큐 (RabbitMQ / Kafka)**

- 메시지를 큐 방식으로 쌓음 (예: 티켓 예매 — 큐 길이를 리턴해서 대기순서 부여)
- 단일 큐에서 뽑으면 행(hang)이 걸림 → **멀티 큐**
- **Kafka**는 대용량 시스템에서만 (초당 1만 건 이상, 예: 인터파크 예매). 큐 번호가 바뀌며 꺼냄
- **게임에서 가장 많이 씀** (실시간성 보장)
    - 예: 보스에 1만 명 몰림 → **IOCP** 개념. 동작별로 스레드를 여러 개 (친구요청 스레드, 보상 스레드…), 각자 스레드만 사용, 패킷 받는 애는 쪼개기만, 느리면 스레드 늘리기
- 요즘은 그냥 **서버를 늘림**. TCP로 하면 보장되지만 개발자가 없어서 안 됨
- 참고: NC가 C 개발자 많아 유명했으나 리소스 문제로 (지하가 전부 서버실, ’22~’23년경)

- 이미지 프로세싱 라이브러리는 80년대부터 쌓인 게 많음 → 용량 큰지 작은지, 압축방식 유무 등을 **리소스 모니터 띄워놓고 직접 확인**

**핵심 통찰: 디텍팅을 잘해야 리소스 관리가 잘됨**

- 디텍팅 성능에 따라 리소스 소모가 갈림
- 카메라 달았을 때 **문에 들어온 사람부터 어디까지 추적할 것인가?**가 관건
- 무인카페는 크지 않음 → **7~10평, 10m 안쪽**. 이 공간을 어떻게 디텍팅할지

**하드웨어 미정 이슈 (팀장님께 보고할 자료)**

- 지금 필요한 건 **“몇 미터까지 되더라” 하는 자료** → 자료 선택 / 로직 선택 / 이미지 어떻게 썼는지 (포인터 따라가며 파악)

### ② C 언어 계열 정리

- **C** = 기초 언어
- **C++** = C에 라이브러리(자료구조 등) 추가
- **MFC** = 마이크로소프트 함수 (이점: **윈도우 UI를 다 쓸 수 있음** → 그동안 많이 쓴 이유)
- **비주얼 C++** = C++을 비주얼하게 사용
- 정의하는 이유 = 컴파일 후 **아웃풋을 어떻게 낼지**에 대한 것
- 요즘은 **커스텀 UI** 원하면 C#(자바와 비슷) 또는 C++ 컴파일해서 .exe로

### ③ 이미지 스트리밍 처리 (while vs 큐)

**기본: while 문**

- 이미지 들어오면 while 문으로 처리 = **스트리밍의 기본**
- while 문에서 디텍팅 받다가 입력 오면 튕겨나오게 하는 방식 (단, 비주얼로는 못 함)

**큐 방식**

- 큐는 올 때만 처리 = “큐에 데이터 있어? 있네 → 빼와”

**주의: 용량 문제**

- 파일이 너무 크면(예: 10GB) while 문이 행 걸려서 **프로세스 죽고 무한 루프** (저장할 메모리 없음)
- **이미지는 자르면 안 됨**

### ④ 메모리 직접 제어 (C++ 핵심)

- 작업관리자 누르면 바로 메모리 청소됨 (죽이고 살림)
- **memset** = “나 이만큼 쓸 거니까 이 영역은 아무것도 쓰지 마” → 포인터 쓰려면 이렇게 해야 함
- memset 하고 **memory copy** 실행
- **자바와의 차이**: 자바도 스트링 카피 하지만 메모리를 필요로 하지 않고, **값이 같다는 보장을 안 함** (메모리 내부 값이 달라질 수 있음)
    - 메모리엔 들여쓰기 같은 것도 다 들어있는데 자바는 똑같이 안 나옴
    - 자바는 비트 단위로 옮기는 게 아니라 이미지 전체 인덱스를 삭제할 수도 있고, 자동으로 처리하는 것도 있음
- 리틀엔디안/빅엔디안: 요즘은 빅엔디안, 옛날 건 리틀엔디안 (x86)

### ⑤ 영상처리 실전 (다음 주 목표)

**과거 방식 참고**

**지금 해야 할 것 = “네모에 1이라고 적는 것”**

- 위치·도트 세팅 → 가까이 있다가 멀어지면 **크기가 줄어야 함** → **벡터**가 들어감
    - 벡터 이미지는 크기를 내가 정하는 것 (크기 정보가 안 들어있음)
- **윈도우 물리 좌표 ≠ 프로그램 좌표** → (10,10) 찍었을 때 둘을 맞춰주는 소스가 따로 있음

### ⑦ 암호화 & 개인정보 (중요)

- **HSM**(하드웨어 머신): 머신에 암호를 넣음. HMS/KMS는 **오프라인으로만** 접근 가능

**ISMS 인증 (법적 필수)**

**키 관리 방식**

# 8월 7일 (금)

#### ① 자료구조 선택과 메모리 관리 (안정성 vs 효율성)

- **해시맵(HashMap)의 한계:** C 언어 환경에서는 구현과 메모리 제어가 까다로움. 유행하는 기술보다 ’본인이 완벽히 이해하고 제어할 수 있는 자료구조’를 쓰는 것이 최우선.
- **배열 포인터의 위험성:** 배열 포인터로 저장하는 방식도 존재하나, 런타임 시 메모리 누수나 관리 통제가 어려워질 수 있음.
- **이미지 처리 메모리 딜레마:** 이미지를 통째로 맵에 때려 넣고 처리할 것인가? vs 최소한의 영역만 잡고 이미지 포인터만 연결해 생성할 것인가? (메모리를 어떻게 줄일지에 대한 깊은 고민 필요)
- **할당 방식의 트레이드오프:**
    - 정적(Static) 할당 = **안정성**이 뛰어남.
    - 동적(Dynamic) 할당 = **효율성**이 뛰어남.

#### ② 멀티스레드 설계 및 동기화 (실시간성 확보)

- **단일 스레드(원프레스)의 한계:** DB 저장 로직과 읽기 로직을 하나로 돌리면 속도가 크게 저하됨. 실시간성을 맞추기 위해 **멀티스레드 구성은 선택이 아닌 필수**.
- **하드웨어 자원 분산:** 현재 시스템 CPU 점유율 20%는 지나치게 높은 수치. 4코어 8스레드, 최대 8코어 16스레드까지 지원하는 하드웨어의 자원을 적극적으로 분산시켜야 함.
- **동기화(Synchronization) 과제:** 멀티스레드 환경에서 데이터 읽기/쓰기가 꼬이지 않도록 스레드 간 동기화를 어떻게 맞출 것인지 구체적인 설계가 필요함.

#### ③ 극한의 리소스 최적화 전략

# 8월 10일 (월)

#### ① 행동 패턴 필터링 및 시나리오 (Rule-based Filtering)

- **무인 매장 목적에 반하는 행동 감지:** 입장하자마자 키오스크를 거치지 않고 바로 자리에 앉는 행위 등, 구매 목적이 아닌 행동 패턴을 즉각적으로 필터링.
- **체류 시간 초과 감지:** 음료 1잔 구매 후 6시간 이상 장기 체류하는 등의 상황을 판별하여, 추가 주문을 유도할지 퇴장을 안내할지 결정하는 로직 필요.
- **출입 제한 대상 필터링:** 매장 정책에 따라 반려견 동반 여부, 미성년자(청소년) 출입 여부 등을 걸러내는 조건 필터 필수.

#### ② AI 활용 최소화 및 점주 중심의 판단

- **필터(조건문) 우선 처리:** 리소스 소모가 큰 AI로 모든 상황을 판단하려 하지 말고, 1차적으로 룰 기반 필터를 최대한 거쳐 AI 판단을 최소화할 것.
- **예외 상황만 AI 위임:** 고객이 갑자기 드러눕는 등 자체 필터 로직으로 명확한 판단이 서지 않는 예외 상황 파라미터만 제한적으로 AI에게 추론을 맡김.
- **최종 결정권은 점주에게:** 3시간 체류 제한 등 정책적인 부분은 시스템이 강제하기보다, 점주가 알림을 받고 직접 선택할 수 있도록 설계.

#### ③ 사용자 관점 분류 및 관리자 UI 기획

- **니즈(Needs)의 분리:** 기능을 기획할 때 1번: 점주 입장(운영 효율, 수익성)과 2번: 고객 입장(편의성)을 명확히 분류하여 접근할 것.
- **점주 전용 필터 페이지:** 앞서 논의된 행동 패턴 허용/제한, 체류 시간 등을 점주가 직접 조작하고 세팅할 수 있는 ’점주 전용 Filter 페이지’를 별도로 구성할 것.

#### ④ 디버깅 효율화 및 코드 아키텍처 (유지보수)

- **통합 로깅(Logging) 시스템:** 카메라나 네트워크가 끊겼을 때 일일이 스텝(Step) 단위로 코드를 추적(디버깅)하는 것은 비효율적임. 문제 발생 시 한 번에 원인을 추측하고 찾아낼 수 있도록 명확한 로그를 남기도록 설계할 것.
- **코드 모듈화:** 함수 분기(기능별 분리)를 철저히 하고, 각 로직이 어떤 역할을 하는지 주석을 상세히 달아둘 것.

#### ① 결제 내역 연동 및 ‘설명 가능한’ 로깅 (신뢰도 확보)

- **로그 기반의 고객 동선 증명:** “주문 안 하고 앉아있다”는 알림이 떴을 때, 점주가 납득할 수 있는 명확한 로그(증거)를 제공해야 함.
    - *예시:* “14:00 입장 → 14:02 키오스크 앞 대기 → 14:05 주문(결제) 없이 좌석 이동 → 30분째 미결제 체류 중”
- **결제 DB와의 크로스체크:** 비전 AI의 시각 데이터와 실제 포스기(결제기)의 승인 내역을 연동하여 정확한 상태를 판별해야 함.

#### ② 하드웨어 한계 대응 및 엔지니어 역제안

- **백화현상 및 하드웨어 장애 알림:** 렌즈가 뿌옇게 되거나 초점을 잃는 ’백화현상’이 발생하면 AI 디텍팅 자체가 무용지물이 됨. 이때는 로그로 설명할 수 없으므로, **시스템이 하드웨어(카메라) 이상을 스스로 감지하고 점주에게 알람**을 보내야 함.
- **카메라 설치 조건 역제안:** 토스 단말기 등 외부 결제기를 따로 쓰는 경우, 결제 내역 연동이 꼬일 수 있음. 이를 해결하기 위해 하드웨어 엔지니어에게 “카메라 화각 안에 바코드 리더기와 상품을 가져가는 손의 동선이 무조건 보여야 한다”는 필수 조건을 명확히 제시해야 함.

#### ③ 얌체 고객 방지 및 고도화된 행동 패턴 (AI + Rule)

- **일행 판별 및 체류 허용량 계산:**
    - 3명이 들어와서 1잔만 시키는 경우(인원수 vs 잔 수 불일치) 판별 로직 필요.
    - 1인이 2잔을 시켰을 경우의 예외 처리. (기본 룰: 1잔당 1~2시간 체류 허용).
- **비품 도난 및 어뷰징 감지:**
    - 시럽을 10번씩 짜서 물을 타 먹는 행위 감지.
    - 티백, 빨대, 컵홀더 등 비품을 무단으로 훔쳐 가는 행위 알림.
- **매장 환경 및 시설 관리:**
    - 에어컨이 가동 중인데 출입문을 열어두고 가는 행위 감지 및 닫힘 안내.
    - 미결제 상태로 상품 섭취/이탈 시 외부 스피커를 통한 경고 방송 송출.
    - 무인 편의점 확장 고려: 빵 등 바코드 없는 상품의 진열대 증감(+, -) 파악.

#### ④ 특정 출입 제한 필터링 (라이브러리 활용)

- **반려견 감지 고도화:** 단순히 강아지가 들어왔는지뿐만 아니라, 강아지를 ‘사람용 의자에 앉히는’ 행위까지 디텍팅.
- **노키즈존 (얼굴/나이 추정):** 미성년자 및 어린이 출입을 제한하기 위해, 얼굴 기반으로 나이대를 추정하는 가벼운 라이브러리 추가 도입 검토.
- **외부 음식 반입 감지:** 매장 판매 상품이 아닌 외부 음식물을 테이블에 올려두고 먹는지 판별.

#### ⑤ 관리자(점주) 커스텀 UI 기획의 핵심

- **모든 룰은 ’체크박스’로:** 위에서 나열된 수많은 규칙(시럽 어뷰징, 반려견 의자 착석, 노키즈존, 외부 음식 등)을 시스템이 일방적으로 강제해서는 안 됨.
- **점주가 본인 매장 형태와 정책에 맞춰 원하는 기능만 체크박스로 [ON/OFF] 설정할 수 있도록 UI를 구성**하는 것이 이번 기획의 핵심.
