## 작업 목적

Windows 실행 흐름에서 대시보드 설정이 detector에 실제로 반영되도록 연결하고, 문 여닫이 감지의 상태 흔들림·ROI 설정·기준 이미지 갱신 문제를 개선했다.

## 1. 실행 스크립트와 `config.json` 연결

### 문제

detector는 `--config PATH`로 전달된 파일만 읽고 hot-reload한다. 그러나 기본 실행 스크립트가 이 인자를 전달하지 않아, 대시보드가 프로젝트 루트의 `config.json`을 저장해도 실행 중인 detector에는 적용되지 않았다.

### 변경

- `run.bat`
  - detector 실행 인자에 `--config "%ROOT%\config.json"` 추가.
- `run.ps1`
  - `-Config` 인자를 생략하면 프로젝트 루트의 `config.json`을 기본값으로 사용.
  - `-StreamPort`를 명시하지 않으면 `config.json`의 `stream_port`를 사용하도록 변경.
- `src/main.c`
  - 시작 시 `motion_gate`도 config 값으로 초기화하도록 수정. 기존에는 config를 읽은 뒤 CLI 기본값으로 다시 덮어썼다.
  - `--stream-port`를 명시하지 않은 경우에만 config의 `stream_port`를 사용한다. 명령줄 인자가 있으면 명령줄 값이 우선한다.

### 적용 범위

`motion_gate`, 모션 임계값, 체류 시간, 문 감지 설정, 카메라 장애 임계값 등은 저장 후 detector가 최대 2초 내에 다시 읽는다. 이미 열려 있는 MJPEG 서버의 포트는 런타임에 교체할 수 없으므로 `stream_port` 변경은 detector 재시작 후 적용된다.

## 2. 문 감지 상태 안정화

### 기존 문제

문 상태는 현재 프레임과 열림/닫힘 기준 이미지의 거리를 비교한 한 번의 결과로 바로 바뀌었다. 사람 통과, 자동 노출, 일시적인 조명 변화가 발생하면 `open`과 `closed`가 프레임마다 흔들릴 수 있었다.

### 변경

`DoorMonitor`에 아래 상태를 추가했다.

```c
int confirm_frames;   /* 새 상태 확정에 필요한 연속 프레임 수 */
int candidate_state;  /* 확정 대기 중인 상태 */
int candidate_frames; /* 후보 상태 연속 관측 수 */
```

- 첫 상태는 즉시 공개한다.
- 이후 반대 상태가 관측되면 후보 상태로 보관한다.
- 같은 후보가 `door_confirm_frames`만큼 연속 관측된 뒤에만 실제 상태를 전환한다.
- 기본값은 `5`프레임이며, `config.json`과 대시보드에서 조절할 수 있다.

```json
"door_confirm_frames": 5
```

15 FPS 입력에서는 약 0.33초의 상태 전환 지연이다. 오탐이 많으면 값을 높이고, 실제 문 상태 반응이 너무 늦으면 값을 낮춘다.

## 3. 기준 이미지 재적재

### 기존 문제

대시보드의 `닫힘 상태 캡처`/`열림 상태 캡처`는 stream 서버를 통해 raw 기준 이미지를 디스크에 저장했지만, detector는 시작 때 읽은 메모리의 기준 이미지만 계속 사용했다. 따라서 새 캡처는 detector 재시작 전까지 반영되지 않았다.

### 변경

- `src/main.c`가 `door_closed_reference.raw`, `door_open_reference.raw` 각각의 수정 시각을 2초 간격으로 확인한다.
- 한 파일이라도 바뀌면 `door_load()`로 두 기준 이미지를 다시 읽고, 상태 전환 후보/열림 지속 시간도 초기화한다.
- 두 파일의 최신 시각 하나만 비교하지 않고 각 파일의 시각을 분리해 추적한다. 따라서 열림 또는 닫힘 기준 중 한쪽만 다시 캡처해도 놓치지 않는다.

### 기준 이미지 파일 형식

stream 서버가 저장하는 형식은 아래와 같다.

```text
[int32 width][int32 height][width * height * 3 bytes RGB]
```

JPEG가 아니라 원본 RGB를 저장하므로 재압축 오차 없이 픽셀 비교를 한다.

## 4. ROI 설정·적용 흐름

### 실제 동작

ROI는 기준 이미지를 잘라 저장하는 기능이 아니다. 기준 이미지와 현재 카메라 프레임은 전체 크기로 보관하고, 상태 판정 때 동일 좌표의 ROI 부분만 비교한다.

```text
대시보드: 현재 화면 스냅샷 수신
  → 문짝/문틀 영역 드래그
  → door_roi_x/y/w/h를 config.json에 저장
  → detector가 config 파일 변경을 감지 (최대 2초)
  → 이후 프레임에서 해당 좌표 영역만 열림/닫힘 기준 이미지와 비교
```

현재 저장된 ROI는 다음과 같다.

```json
"door_roi_x": 589,
"door_roi_y": 203,
"door_roi_w": 555,
"door_roi_h": 517
```

### 대시보드 UX 변경

- 버튼 표기를 `1. 현재 화면 불러오기`, `3. ROI 저장 및 적용`으로 변경.
- ROI 미설정(`0,0,0,0`)이면 전체 화면 비교 상태 및 오탐 가능성을 경고.
- 선택된 ROI의 좌표·크기와 “이 영역만 문 상태 판단에 사용” 문구 표시.
- 문짝·문틀만 넣고 사람, 통로, 창문을 제외하도록 안내.
- 기존 `mouseup`만 사용하던 드래그 처리를 Pointer Events + pointer capture로 교체. 마우스가 캔버스 밖으로 나가도 좌표가 취소되지 않고, 터치 입력도 지원.
- ROI 저장 요청에 진행 상태와 5초 제한을 추가. 대시보드 서버가 응답하지 않을 때 무한 대기 대신 오류를 보여 준다.

### 운영 절차

1. `run-all.bat`으로 detector와 dashboard를 함께 실행한다.
2. 대시보드에서 스트림이 보이는지 확인한다.
3. ROI를 문짝과 문틀의 변화 부분으로 좁게 지정하고 저장한다.
4. 사람이 없는 닫힘 상태에서 닫힘 기준 이미지를 캡처한다.
5. 사람이 없는 열림 상태에서 열림 기준 이미지를 캡처한다.
6. 카메라 해상도·화각을 바꾸지 않은 상태로 문을 여러 번 열고 닫아 안정성을 확인한다.

기준 이미지 캡처 해상도와 현재 프레임 해상도가 다르면 문 상태 판정은 중단된다. ROI 좌표도 프레임 좌표이므로 카메라 해상도 변경 후에는 ROI와 두 기준 이미지를 다시 설정해야 한다.

## 5. 대시보드 설정 저장 API 수정

### 증상

`ROI 저장 및 적용`을 눌러도 반응이 없거나 `config.json`에 ROI가 저장되지 않는 문제가 있었다.

### 원인

`dashboard/server.c`는 TCP `recv()` 한 번으로 HTTP POST 헤더와 본문 전체를 받는다고 가정했다. TCP는 메시지 경계를 보장하지 않으므로, 본문이 다음 수신으로 나뉘면 body가 비어 있는 것으로 처리해 `{"ok":false}`를 반환할 수 있다.

### 변경

- `Content-Length`를 읽고, 그 길이만큼 POST 본문을 받을 때까지 `recv()`를 반복한다.
- config 저장 본문 최대 길이를 7,000 bytes로 제한한다.
- 대시보드 서버를 재빌드·재시작한 뒤 `POST /api/config` 저장 성공과 `config.json` 갱신을 확인했다.

## 6. `camera_blackout`과 문 상태의 구분

`camera_blackout`은 문 감지 결과가 아니라 화면 전체 평균 밝기가 매우 낮다는 카메라 헬스 이벤트다.

- `CAM_BLACKOUT`: 다운샘플된 전체 프레임 평균 luma가 `luma_black_threshold` 미만인 상태가 5프레임 이상 지속.
- 문 감지 ROI는 이 카메라 헬스 판정에 사용되지 않는다.
- 문을 열었을 때 어두운 출입구가 화면 대부분을 차지하면 `blackout`, 문을 닫아 밝기가 돌아오면 `ok`가 될 수 있다.

현장 상황에서 정상적인 문 개방을 blackout으로 오인하면 `luma_black_threshold`를 낮춘다. 현재 값은 `40`이며, 어두운 출입구가 일반적인 환경에서는 `5~10`부터 조정해 볼 수 있다. `0`이면 blackout 검출은 사실상 비활성화된다.

## 7. `unordered_seated`의 실제 기준과 한계

로그 예시:

```text
unordered_seated track=1 dwell=301s grace=300s
```

현재 이 이벤트는 실제 착석 여부나 실제 주문 여부를 판별하지 않는다. 다음 조건만 만족하면 발생한다.

```text
동일 track ID가 active 상태
AND order == TRACK_UNORDERED
AND dwell_seconds > unordered_grace_seconds
```

- 새 person track은 항상 `TRACK_UNORDERED`로 시작한다.
- IoU 기반 트래커가 같은 사람으로 유지한 시간만 `dwell_seconds`에 누적한다.
- `unordered_grace_seconds` 기본값은 300초이므로, 301초에 최초 발화한다.
- 트랙당 한 번만 로그를 남기며, 트랙이 비활성화되거나 주문 상태가 되면 latch가 해제된다.

`ORDERED` 전환 지점은 키오스크 ROI 또는 향후 POS 연동이다. 하지만 현재 실행 설정에는 키오스크 ROI/POS 이벤트 연결이 없으므로, 장기 체류자를 미주문으로 추정하는 수준이며 오탐 가능성이 높다.

### 향후 POS 연동 방향

```text
카메라 track 생성
  → 키오스크 ROI 진입/체류 확인
  → POS 또는 키오스크 결제 완료 이벤트 수신
  → 결제 시각 전후의 키오스크 주변 track을 매칭
  → 해당 track을 TRACK_ORDERED로 전환
```

1인 키오스크에서는 결제 시각과 위치를 결합하면 실용적이다. 여러 사람이 동시에 키오스크 앞에 서는 환경에서는 주문번호, 회원 QR, 좌석 번호 같은 추가 식별 정보가 필요하다.

## 9. 계획 문서 작성

### 9.1 `docs/improvement-plan.md`

문서가 "완료"라고 적은 것과 코드가 실제로 하는 일을 파일·라인 단위로 대조했다. 가장 중요한 발견:

**`unordered_seated`는 사실상 동작하지 않는다.**

```
rules.c:159  키오스크 ROI 검사는 roi_kiosk_set 이 참일 때만 실행
             ↓
include/rules.h:18  roi_kiosk_set 에 1을 대입하는 코드가 프로젝트에 없음
             ↓
src/config.c        "x,y,w,h" 형태를 파싱하는 함수 자체가 없음
```

`TRACK_ORDERED` 전환 경로가 죽어 있으므로 이 이벤트는 **"유예 시간 이상 머문 모든 사람"** 을 뜻한다. `checklist.md`에는 완료(`[x]`)로 표시되어 있다. 7절에서 이미 "오탐 가능성이 높다"고 적었지만, 실제로는 오탐 가능성이 아니라 **판정 근거가 아예 없는 상태**다.

그 외 P0~P3로 분류한 항목은 문서 본문 참조.

### 9.2 `docs/i5-4200u-optimization.md`

리소스 목표(현재의 1/4)를 FLOPS가 아니라 **L3 3MB / 15W TDP** 제약에서 출발해 다시 계산했다.

```
1280 × 720 × 3 = 2.76 MB   (프레임 하나)
L3                = 3 MB
```

전체 프레임을 훑는 연산 하나가 L3의 88%를 비운다. 현재 파이프라인은 프레임당 그 순회를 9번 한다. **추론이 매번 캐시가 비워진 상태에서 시작한다.**

문서 구성은 "룰 우선, AI 최소" 방침을 최적화의 1순위 축으로 삼았다.

```
YOLO11n 416×416 추론 1회   ≈ 60~120 ms
8배 다운샘플 Y 평면 차분    ≈ 0.01 ms      → 약 6,000~12,000배
```

추론 1회를 아끼는 것이 픽셀 최적화 수천 번보다 크므로, Part A(추론 회피)를 Part B(연산 최적화)보다 앞에 두었다.

주요 결론:

| 항목 | 내용 |
|---|---|
| 720p 캡처 | 검출에 기여 없음. 1280×720과 640×360 모두 모델이 보는 영역은 416×234로 동일 |
| 그레이스케일 | 같은 프레임에서 3번 계산(`gray.c`, `tracker.c`, `camera_health` 사본). 원본 YUV의 Y 평면이 이미 luma |
| 모델 입력 | 정사각형 416×416에 16:9를 넣으면 43%가 회색 패딩. 종횡비별 모델 세트로 해결 |
| 모델 세트 비용 | **재학습 불필요** — 가중치 하나에서 `imgsz`만 바꿔 export만 반복. anchor-free라 앵커 재계산도 없음 |
| J1900 | `/arch:AVX2` 전역 적용은 최적화가 아니라 크래시 버그 |

## 10. 최적화 1차 구현

문서의 "1차 — 설정과 빌드만" 항목을 구현했다. 측정 가능성 확보를 함께 넣었다.

### 10.1 J1900 크래시 수정 (버그)

`CMakeLists.txt`가 `/arch:AVX2`를 전역으로 걸고 있었다. 이 옵션은 컴파일러가 **모든 부동소수 코드에 VEX 인코딩 AVX 명령**을 쓰게 한다. Celeron J1900(Bay Trail)은 SSE4.2까지만 지원하므로, CLAUDE.md가 차순위 배포 대상으로 명시한 기기에서 **이 바이너리는 시작 즉시 `EXCEPTION_ILLEGAL_INSTRUCTION`으로 종료된다.**

```cmake
set(TARGET_ISA "baseline" CACHE STRING "baseline (SSE2, J1900 호환) | avx2 (Haswell 전용)")
```

기본값을 baseline으로 두고, AVX2가 필요한 핫스팟은 나중에 별도 번역 단위로 분리해 런타임 디스패치할 계획이다(문서 B-5).

### 10.2 Makefile 복구

`SOURCES`가 `tracker.c` 이후 추가된 모듈을 하나도 포함하지 않아 **macOS/Linux 빌드가 이미 깨져 있었다.** `gray.c`, `log.c`, `config.c`, `camera_health.c`, `tracks.c`, `rules.c`, `door.c`를 추가했다.

`stream.c`는 WinSocket2 전용이라 제외하고, `stream.h`에 비Windows용 no-op 인라인 정의를 두어 `main.c`가 플랫폼 분기 없이 컴파일되게 했다.

### 10.3 헤드리스 실행 허용

```c
/* 이전 */
if (!args->model || (!args->output && !(args->camera && args->preview)) || ...)
```

`--output`이 없으면 "카메라 + 미리보기" 조합만 허용했다. 그런데 **실제 배포 형태는 화면도 파일도 없는 헤드리스 상시 감시**이고, 결과는 이벤트 로그·CSV·대시보드 스트림으로 나간다. 미리보기(ffplay)는 배포 기기에서 오히려 꺼야 하는 기능인데 그것이 실행 조건이었다.

출력 필수 조건을 제거하고, `run.bat`/`run.ps1`의 미리보기 기본값을 껐다.

> ffplay는 별도 프로세스로 코어 하나를 차지하고 프레임마다 raw RGB를 파이프로 보낸다(720p 15fps 기준 41MB/s).

### 10.4 관찰자가 없으면 그리지 않는다

`draw_detections()` + `draw_hud()`가 무조건 실행되고 있었다. 출력 파일도, 미리보기도, 스트림 클라이언트도 없는 배포 상태에서는 **아무도 보지 않는 픽셀을 칠하는 것**이다.

```c
int has_observer = app->preview || app->has_output ||
                   (app->stream_port > 0 && stream_client_count() > 0);
```

`stream.c`에 `InterlockedIncrement`/`Decrement` 기반 연결 수 카운터를 추가했다.

### 10.5 스트림 낭비 제거

세 가지를 고쳤다.

| 문제 | 조치 |
|---|---|
| 매 프레임 2.76MB 복사 (`stream.c:409`) | `STREAM_FPS`(10) 시간 게이트. 클라이언트 0명이면 1 FPS |
| 클라이언트마다 같은 프레임 개별 인코딩 (`stream.c:307`) | 프레임 일련번호 기준 JPEG 캐시 → 먼저 도착한 스레드의 결과를 공유 |
| 프레임마다 스크래치·결과 버퍼 malloc/free | 전역 스크래치 + 클라이언트별 재사용 버퍼 |

클라이언트가 0명이어도 1 FPS는 유지한다. **완전히 멈추면 `/snapshot`과 `/door/save`가 실패해 문 기준 이미지를 캡처할 수 없다.**

JPEG 캐시는 `g_lock`과 별도 락을 쓴다. 인코딩은 수 ms가 걸리는데 그동안 `g_lock`을 쥐면 파이프라인의 `stream_push`가 통째로 막힌다. 결과는 호출자 버퍼로 복사한 뒤 락을 놓고 전송한다 — 복사 대상이 프레임 전체(2.76MB)가 아니라 JPEG(수십 KB)이라 비용이 작다.

### 10.6 문 감지 순서 수정 (정확도 버그)

`door_check()`가 **그리기 이후에** 실행되고 있었다.

```
기존: draw_detections → draw_hud → stream_push → door_check
```

`door_check()`는 프레임 픽셀을 기준 이미지와 직접 비교한다. 박스와 HUD를 먼저 그리면 **그 픽셀이 그대로 비교 대상에 섞인다.** 사람이 문 근처에 서면 그 사람의 박스 선이 ROI 안에 그려져 없던 변화를 만들어 낸다.

```
변경: door_check → draw(관찰자 있을 때만) → stream_push
```

### 10.7 모션 게이트 조기 종료

57,600 픽셀을 **항상 끝까지** 순회한 뒤 비율을 계산했다. 임계값 0.004는 230픽셀인데, 사람이 움직이는 흔한 경우는 첫 몇 줄에서 이미 넘어선다.

비율 대신 절대 개수와 비교하고 도달 즉시 중단하도록 바꿨다. **판정 결과는 완전히 동일하다.**

### 10.8 추론마다 돌던 정렬 제거

`detector_ort.c`가 **추론 1회마다 256개 double을 복사하고 삽입 정렬**했다(평균 약 16,000회 비교). 그 결과인 p50/p95는 metrics 출력과 스로틀링 감시에만 쓰인다.

기록은 매번 O(1), 백분위 재계산은 5초 주기로 바꿨다. 2KB 스택 배열도 구조체 멤버로 옮겼다(i5-4200U의 L1d는 코어당 32KB뿐이다).

다만 첫 구현에서 짧은 실행의 p50/p95/max가 표본 1개로 고정되는 문제가 나와, `latency_count < 32`인 동안은 매번 재계산하도록 보정했다.

### 10.9 `max_candidates` 1024 → 128

```
1024 × 224 B = 229 KB   ← L2 256KB를 혼자 차지
 128 × 224 B =  29 KB
```

7~10평 매장에서 confidence를 넘는 후보가 1024개일 일이 없다. 상한에 걸려도 `append_candidate()`가 점수 낮은 후보부터 밀어내므로 상위 128개는 보존된다.

### 10.10 계측 추가

최적화 대상 구간이 정작 측정되지 않고 있었다. metrics JSON에 추가:

```json
"gray_seconds":   0.040261,
"door_seconds":   0.000013,
"stream_seconds": 0.002898,
"drawn_frames":   0
```

## 14. A-1 — 그레이스케일 3중 계산 제거

### 문제

같은 프레임의 그레이스케일을 **세 번** 만들고 있었다. 그리고 그 원본이 애초에 그레이스케일이었다.

```
디코더(YUV420P)  →  sws_scale  →  RGB24  →  77R+150G+29B>>8  →  gray
   Y 평면 = luma                              ↑ 이 계산을 3곳에서 반복
                                              gray.c / tracker.c / camera_health
```

`gray.c`의 주석이 이미 *"tracker.c의 make_gray()와 동일한 공식"* 이라고 적고 있었다. 두 함수는 downsample도 4로 같았다. 여기에 `camera_health`가 그 결과의 사본을 또 하나 들고 있어 이전 프레임 버퍼가 두 벌이었다.

### 변경

| 대상 | 조치 |
|---|---|
| `media.h` / `media_ffmpeg.c` | `RgbFrame`에 디코더 Y 평면을 차용 포인터로 노출 |
| `gray.c` | `gray_buf_update_luma()` — 산술 없이 바이트만 이동 |
| `gray.c` | `gray_analyze()` — luma 합·변화 픽셀 2종을 단일 순회로 계산 |
| `camera_health` | 픽셀 순회와 `prev_gray` 소유를 모두 제거, `GrayStats`만 받음 |
| `tracker.c` | `tracker_set_luma()` — 기존 호출부·테스트는 그대로 |
| 공통 | downsample 4 → 8 |

Y 평면 판별은 `av_pix_fmt_desc_get()`에 맡겼다. YUV420P/NV12/YUV422P 등 변형이 많고 그중 "첫 평면이 8비트 luma"인 경우만 안전하게 골라야 하기 때문이다. packed 포맷(YUYV422, BGR24)은 여기서 걸러져 RGB 폴백으로 간다.

downsample을 8로 올린 이유는 캐시다. 720p 기준 160×90 = 14KB로 i5-4200U의 L1d(코어당 32KB)에 통째로 들어간다. 4일 때는 57KB로 L1을 넘쳤다.

### 검증

동일 내용을 planar(yuv420p)와 packed(bgr24)로 각각 인코딩해 A/B 했다.

```
_ab_planar.mp4   source=luma_plane    gray 0.0456 ms/frame
_ab_packed.avi   source=rgb_fallback  gray 0.0670 ms/frame
```

어느 경로를 탔는지는 기동 시 한 번 로그로 남긴다. 현장에서 "왜 이 기기만 느리지"를 로그로 구분하기 위해서다.

```
gray  source=luma_plane 그레이스케일 RGB 재계산 생략
gray  source=rgb_fallback 입력에 luma 평면 없음
```

## 15. A-2 / A-3 — 변화의 "양"이 아니라 "위치"로 게이팅

### 문제

기존 모션 게이트는 화면 전체 변화율 하나만 봤다. 이 값으로는 두 가지를 구분할 수 없다.

- 창밖에서 흔들리는 나뭇가지 vs 좌석의 손님
- 이미 추적 중인 사람이 제자리에서 움직임 vs 새 사람이 들어옴

두 번째가 특히 비싸다. **앉아 있는 손님 한 명 때문에 추론이 주기마다 계속 돈다.**

### 변경

`gray_analyze()`가 같은 순회에서 블록 지도까지 채운다. 다운샘플 프레임을 8×8 블록으로 나누고 블록당 1비트를 남긴다.

```
720p → 다운샘플 8 → 160×90 → 8×8 블록 → 20×12 = 240 블록 = 30바이트
```

240비트면 캐시 한 줄이라, 이후 판정이 비트 연산 몇 번으로 끝난다.

```
L1  변화 블록 0개                  → 추론 생략 (idle_refresh_seconds 까지)
L3  변화가 전부 기존 트랙 박스 안  → 추적기만 (track_refresh_seconds 까지)
```

두 상한은 안전 밸브다. 추적기 드리프트가 무한히 누적되어 영영 갱신되지 않는 상태를 막는다.

### 구현 중 고친 설계 오류

처음에는 블록 게이트를 비율 게이트 **위에** 얹었다. 그 결과 정적 영상에서 `gated=23, L1=0`이 나왔다. 비율 게이트가 먼저 걸려 `run_detector`를 0으로 만들면 블록 게이트의 조건문 자체가 실행되지 않기 때문이다.

**게이트를 겹쳐 걸면 먼저 걸린 쪽이 뒤쪽을 가려 계측이 무의미해진다.** 블록 지도가 있으면 비율 게이트를 대체하도록 바꿨다.

```
                 frames  inference  gated  L1
겹쳐 걸었을 때      90        1       23    0    ← L1 이 무슨 일을 했는지 알 수 없음
대체하도록 수정     90        1       22   22
```

### 설정

```json
"block_gate": 1,
"block_min_changed": 2,
"block_margin": 1,
"track_refresh_seconds": 5.0
```

`block_min_changed`를 1로 두면 센서 노이즈 한 점에도 블록이 켜지므로 기본값은 2다.

### 한계

**L3는 end-to-end로 검증하지 못했다.** 사람이 나오는 실제 영상이 필요한데 이 PC에는 없다. `gray_blocks_outside()` 수준의 단위 테스트(`test_motion_map_locates_change`)로 블록 위치 판정과 박스 포함 여부는 확인했다. 파일럿 영상이 확보되면 `gate_l3_hits` 카운터로 실효를 측정해야 한다.

## 16. 대시보드 설정 저장이 키를 지우던 문제

### 증상

`block_gate` 같은 새 설정을 `config.json`에 넣어도, 점주가 대시보드에서 "저장"을 누르면 사라진다.

### 원인

`serve_config_post()`가 받은 본문으로 파일을 **통째로 덮어썼다**. 본문은 브라우저가 `index.html`의 입력 필드로 만든다. 따라서 **대시보드 UI가 모르는 키는 저장 한 번에 전부 삭제**되고 detector는 조용히 기본값으로 되돌아간다.

기능이 꺼졌다는 사실이 아무 데도 남지 않는 종류의 사고다. 9.1의 `roi_kiosk`와 같은 계열이다.

### 변경

기존 파일을 읽어 본문에 없는 키만 살려서 병합한다. `src/config.c`의 flat JSON 파서를 대시보드 타겟에도 링크했다.

### 검증

키 3개만 POST하고 나머지가 남는지 확인했다.

```
POST  {"stream_port":8081,"motion_gate":1,"door_enabled":1}
결과  18개 키 전부 보존 (door_roi_x/y/w/h, 각종 임계값 포함)
```

## 18. 구현 중 걸린 도구 문제

`bash` heredoc이 백슬래시를 한 단계 먹어 C 문자 상수 `'
'`, `''`, `'	'`, `' '`가 실제 제어 문자로 파일에 들어갔다. `server.c`에 NUL 바이트가 섞여 `grep`이 바이너리 파일로 인식했다.

해당 구간은 이스케이프가 필요 없는 `isspace()`로 바꿔 해결했다. 코드도 더 짧아졌다. 앞으로 C 문자 이스케이프가 들어가는 편집은 heredoc 대신 파일 기반으로 처리해야 한다.
