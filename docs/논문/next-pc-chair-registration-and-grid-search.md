## 3. 경로 및 실행 환경 주의

기존 프로젝트 경로는 `D:\DMU\Contest\hunik\object-detector`다. manifest와 baseline의 영상·모델 경로에 이 절대 경로가 들어 있다.

### 같은 Windows 경로를 재현할 수 있는 경우

- 프로젝트와 FFmpeg를 기존 경로에 복사하면 경로 변경을 최소화할 수 있다.
- 이 PC에서 사용한 Node.js는 v24.16.0이며 `C:\Program Files\nodejs\node.exe`로 실행했다. 새 PC에서 `node --version` 및 명령 접근 여부를 확인한다.
- 기준 평가에는 초기 보존 폴더의 EXE와 **같은 폴더에 있는 ONNX Runtime DLL**을 함께 사용한다. 기록된 기준 런타임은 1.26.0이다. 임의의 DLL로 교체하지 않는다.
- EXE는 Windows용이므로 다른 OS/아키텍처에서는 그대로 실행할 수 있다고 가정하지 않는다. 소스 재빌드 시 별도 아티팩트 버전으로 기록하고 초기 결과 재현부터 확인한다.
- 카메라 없이 저장 영상으로 평가 가능하다. 운영 감지기를 실행할 필요가 없다.

### 프로젝트/FFmpeg 경로가 다른 경우

**완료된 원본 manifest·baseline.json을 일괄 문자열 치환하지 않는다.** 해시·탐색 서명 및 과거 재현 근거가 깨질 수 있다.

1. 원본 메타데이터를 보존한다.
2. 새 도구에 `project_root`, `records_root`, `baseline_root`, `ffmpeg_path`를 받는 경로 해결 계층을 추가한다. 이는 **추가 구현할 요구사항**이며 현재 모든 CLI가 지원하는 옵션이 아니다.
3. 원래 경로와 새 경로의 대응을 별도 migration manifest에 기록한다. 영상 및 모델의 SHA-256이 동일한지 확인한다.
4. 경로를 바꾼 새 실행은 새 출력 폴더/manifest를 사용한다. 과거 완료 실행의 resume 검증을 우회하지 않는다.
5. `evaluate_all50_initial.js`의 기존 `--run`은 저장된 절대 경로를 사용하므로, 경로 해결 기능을 구현하기 전에는 다른 경로의 manifest를 그대로 실행하지 않는다.

기존 도구에는 FFmpeg 경로 하드코딩도 있다. Node PATH만 설정한다고 해결되는 것이 아니다.

## 5. 의자 등록이 필요한 이유와 설계 방향

S36 컵 등록 후에도 남은 알림 위치는 `[0.2278, 0.6055, 0.2428, 0.6512]`다. 원본 화면에서 테이블 왼쪽/의자 경계 부근이며, 컵 등록 영역과 다르다. 컵 등록 전후 모두 체크포인트 FP였다. S02·S04·S07 등도 경계 후보를 먼저 확인할 필요가 있다.

### 기존 fixtures에 의자 전체를 넣으면 안 되는 이유

- `src/surface_config.c`는 fixture polygon의 모든 꼭짓점이 표면 ROI 안에 있어야 한다고 검사한다. 대부분이 테이블 밖인 의자 전체는 이 계약에 맞지 않는다.
- 현재 `src/surface_monitor.c`의 fixture 비교는 기준 외형과 제한된 평행 이동을 비교한다. 의자의 회전, 사람 착석에 의한 외형 변화, 가림을 일반적으로 추적하는 기능이 아니다.
- 의자 영역을 큰 상시 제외 영역으로 만들면 의자 근처에 남긴 실제 컵·종이도 놓칠 수 있다. 정상 비치물 등록과 무조건 무시 마스크는 구분해야 한다.

### 권장: 테이블 비치물과 외부 가림 물체를 분리

아래는 **설계 제안**이며 현재 파서에서 바로 읽을 수 있는 새 필드가 아니다.

| 구성 | 역할 |
|---|---|
| 기존 `fixtures` | 테이블 위 컵 등 정상 비치물. 기존 계약 유지 |
| 새 외부 가림 물체 설정(예: `occluders`) | 테이블 밖에도 있는 의자 원래 영역, 제한된 이동 범위, 관련 surface ID 저장 |
| 프레임별 현재 가림 마스크 | 실제 의자/사람으로 가려진 부분과 표면 ROI의 교집합만 처리 |
| 가시성·재확인 상태 | 매칭 실패/가림 중에는 불확실 상태. 깨끗함으로 확정하거나 정상 기준을 갱신하지 않음 |

처리 원칙:

1. 사람이 없는 초기 프레임에서 의자 영역과 허용 이동 범위를 지정한다. 알림 박스 자체를 의자 전체 정답으로 쓰지 않는다.
2. 경량 후보로는 제한된 탐색 범위의 기준 패치·에지 비교부터 검토한다. 의자 회전/가림에서 신뢰가 떨어지면 임의 위치를 확정하지 않는다.
3. 상시 제외 대신 **현재 확인된 가림과 표면 ROI의 교집합**만 변화 검사에서 보류한다. 테이블의 나머지 영역은 계속 감시한다.
4. 사람과 의자를 혼동하거나 매칭에 실패한 영역은 `unknown`으로 유지한다. 이 상태를 TN/청결 성공으로 간주하지 않는다.
5. 의자가 이동하여 표면이 다시 보이면 일정 수의 가림 없는 관측 후 기존 정상 기준과 비교한다. 이동 직후의 물체를 새 정상 기준에 흡수하지 않는다.
6. 의자 등록을 이유로 전체 테이블의 동물·위험 오염 알림을 일괄 억제하지 않는다. 가려진 영역은 관측 불가로 분리한다.
7. 등록/이동 범위 변경 시 기준 호환성 키와 geometry revision에 반영하고 필요 시 재수집한다.
8. 의자 처리 ON/OFF, 매칭 신뢰도, 가림 면적, 불확실 지속 시간, 추가 처리 시간을 로그에 남긴다.

가림 인식 개선과 사람 이용 구역 수정은 서로 다른 변경이다. S39 사용 중 오탐도 있으므로 둘을 한꺼번에 바꾸지 말고 각각 비교한다. 특히 움직일 수 있다는 이유만으로 기존 fixture의 `movable=true`를 켜는 것을 의자 추적 구현으로 간주하지 않는다.

### 수정 위치 및 필요한 테스트

- `include/surface_monitor.h`: 실제 구조체/상수 위치 확인 후 외부 가림 물체와 상태 정의 검토.
- `src/surface_config.c`: 새 스키마 검증, ROI 밖 등록 허용 범위, 이동 범위/면적 제한. 기존 fixtures의 계약을 조용히 완화하지 않기.
- `src/surface_monitor.c`: 가림 마스크 결합, 불확실 상태, 기준 보호, 재관측, 로그.
- `tests/evaluate_surface_video.c`: 새 상태·설정을 평가에서 재현할 수 있는지 확인.
- UI는 로직 검증 후 구현. 기존 ROI 그리기 방식은 유지하고 “의자 등록”을 별도 동작으로 제공.

필수 회귀 조건: 빈 테이블/의자 이동, 사람이 앉았다 떠남, 의자 회전, 의자 옆 컵·작은 종이 잔류, 가림 동안 물체 배치/제거, 매칭 실패, 해상도/카메라 이동, 등록 해제. 오탐 감소와 함께 재현율·가시성 손실도 확인한다.

## 6. 비교 실험 순서

| 단계 | 설정 | 목적 |
|---|---|---|
| A | 보존 초기 코드·모델·파라미터 | 완료된 50개 결과 재현. 변경하지 않음 |
| B | 의자 처리만 추가, 임계값은 초기값 | 의자 기능의 효과 분리 |
| C | B를 고정한 후 파라미터 탐색 | 의자 기능 위에서의 튜닝 효과 |

B/C에서도 S36 컵 등록 적용 여부를 먼저 고정한다. A는 미등록 기본 50개이고 별도 등록 비교가 있으므로, B에 컵 등록까지 새로 넣었다면 의자 효과만의 비교라고 주장하지 않는다. 동일 조건 대조군을 추가하거나 변경 항목을 명시한다.

ROI·모델·의자 영역·정답까지 동시에 최적화하지 않는다. 의자 영역은 별도 초기/설정용 프레임에서 정하고, 테스트 결과를 본 뒤 계속 마스크를 넓혀 오탐을 지우는 방식은 피한다.

## 7. 50개용 Grid Search: 추가 구현이 필요함

**현재 `run-surface-grid-search.bat`와 `scripts/surface_grid_search.js`는 과거 21개 기준용이다. 그대로 실행해도 이번 50개를 탐색하지 않는다.**

현재 구현의 차이:

| 항목 | 기존 21개 도구 | 이번 50개 평가 |
|---|---|---|
| 입력 목록 | baseline.json의 cohort, init은 21개 고정 검사 | all50 manifest.json의 cases |
| 정답 | expected_residue | labels.json의 expected_alert |
| 예측 | predicted_alert | alert |
| 품질 | valid_at_reference | valid |
| 초기 결과 재사용 | candidate-00에 기존 21개 결과 재사용 | **해당 코드/설정/라벨/영상이 모두 동일한 50개 기준 결과만** 재사용 가능 |
| 추천 제약 | FP ≤ 2, 품질 ≥ 95% | 새 비교 목적에 맞춰 사전에 정해야 함 |

S39처럼 물체는 있어도 사용 중이므로 기대 알림이 없는 사례가 있다. `expected_alert`를 물체 존재 라벨로 바꾸거나 S36 컵을 새 쓰레기 양성으로 자동 변환하지 않는다.

### 구현 요구사항

1. 검토 완료된 50개 manifest·labels를 입력으로 받아 새 기준 스냅샷을 생성한다. 영상·정답·ROI·비치물/의자 설정·모델·EXE·DLL·FFmpeg·코드 해시를 포함한다.
2. 새 의자 코드 B의 기본 파라미터 결과 50개를 먼저 생성한다. **A의 기존 결과를 B의 candidate-00으로 재사용하면 안 된다.**
3. 경로 이동을 고려한 상대 경로/명시적 root 옵션, 경로 매핑 기록, 파일 해시 검증을 구현한다.
4. 후보마다 전체 50개를 동일 체크포인트로 실행하고 미완료/실패 영상을 분모에서 빼서 순위를 만들지 않는다.
5. 영상별 새 기준 상태, 타임아웃, 오류 로그, 중복 실행 잠금, 중단 후 검증된 결과만 재사용하는 resume를 유지한다.
6. 코드/정답/의자 영역/모델/평가 정의가 바뀌면 새 탐색 서명과 폴더를 생성한다. 검증을 끄고 예전 캐시를 쓰지 않는다.
7. `progress.json`, 전체 후보 표, 추천값, 완료 표시, 후보별 프레임 로그, CSV/Markdown 보고서를 저장한다. 운영 설정 자동 적용은 하지 않는다.
8. 일부 ID 재현용 smoke 기능 및 불확실 정답 거부·결과 누락·해시 불일치·품질 제약·resume 테스트를 추가한다.

### 최초 탐색 범위 제안

의자 설계와 등록 영역을 먼저 고정한 뒤, 과거와 같은 작은 탐색으로 시작한다.

| 파라미터 | 후보 |
|---|---|
| threshold | 16, 24, 32 |
| min_area | 0.001, 0.003 |
| confirm_seconds | 5, 10, 15 |

18개 × 50개 = **900개 후보-영상 평가**다. 완전히 동일한 초기 조합 50개가 이미 보존되어 검증된 경우 신규 실행은 850개다. 이는 900개의 독립 원본 영상을 뜻하지 않는다.

순차 실행, 영상 사이 10초, 실제 조합 사이 60초의 기존 휴식 방식을 기본 후보로 둔다. CPU 사용률 상한 제어는 아니다. 새 PC에서 짧은 실행으로 시간을 추정한 뒤 전체 작업을 시작한다. 이 PC의 50+1개 실행은 휴식/부대 작업 포함 약 25분이었으나 새 PC·새 코드의 소요 시간을 보장하지 않는다.

### 추천값 선정 기준 제안 — 결과를 보기 전에 확정

- 현재 A 기준은 FP 12, 재현율 65.2%, 품질 유효 96%다. 과거 21개용 `FP ≤ 2`를 의미 확인 없이 복사하지 않는다.
- B 위에서 튜닝한다면 B 기본값의 점수를 먼저 고정하고, **FP가 B보다 늘지 않음**, 품질 유효 비율이 B보다 낮아지지 않음, 재현율 저하 허용 여부를 사전에 정한다. B 자체가 A보다 나빠졌다면 의자 기능부터 재검토한다.
- 가림/unknown을 늘려 오탐만 줄이는 것을 성공으로 취급하지 않는다. 품질 유효 비율과 S39 등 보호 사례를 함께 검사한다.
- 조건 통과 후보 중 F1 최대, 동점이면 FP 적은 순 등 결정 규칙을 고정한다. 통과 후보가 없으면 “추천 없음”으로 끝낸다.
- 50개 전체 및 촬영 조건이 다른 S33 제외 49개를 같은 기준으로 병기한다. 결과가 나쁘다는 이유로 추가 제외하지 않는다.
- S39의 75초 사용 중 알림, S15의 후반 알림 등 체크포인트 외 문제도 대표 시간축 검토 항목으로 고정한다. 후반 점수만 좋아졌다고 채택하지 않는다.

18개 후보 중 조건부 최고점이지 전역 최적값이 아니다. 이미 모두 검토한 50개에서 튜닝한 결과는 개발 점수다. 최종 일반화 평가는 코드·설정을 고정한 뒤 새 세션으로 검증해야 한다. 같은 영상의 프레임 무작위 분할은 독립 검증이 아니다.
