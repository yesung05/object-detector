# 필요한 시나리오만 재촬영하기

2026-09-14 추가. 기존 `run-scenario-recorder.bat`로 실행한다. 이미 서버가 실행 중이면 기존 녹화를 끝낸 뒤 서버 창을 닫고 다시 실행하여 새 기능을 불러온다.

## 사용 순서

1. `run-scenario-recorder.bat` 실행 → Chrome/Edge에서 녹화 화면 열기.
2. **필요한 것만 다시 촬영**에서 기본 선택을 확인한다. 현재 records 기준 S06·S17·S32·S36·S38, 총 5개다.
3. 아직 촬영하지 않은 25개도 하려면 **미촬영까지 함께 선택**을 누른다. 선택 목록에서 개별 추가·해제 가능하며 촬영 수가 함께 바뀐다.
4. 카메라 연결 → 저장 폴더로 프로젝트의 `records` 선택 → 촬영 시작. 선택한 항목만 무작위 순서로 녹화한다.
5. 설명이 길면 **설명 건너뛰기 → 타이머 시작**을 누른다. 현재 음성만 중지하고 준비/해당 단계 타이머로 진행한다. 모든 음성을 끄려면 시작 전에 기존 음성 안내 체크를 해제한다.
6. 실제 MediaRecorder 시작 이벤트에서 약 0.25초의 880 Hz 삐 소리가 난다. 처음은 깨끗한 기준 장면을 찍는 단계이므로 삐 소리에 바로 물체를 놓지 않는다. **행동하세요** 단계의 타이머에 맞춰 행동한다.

각 시나리오는 별도의 WebM으로 저장하며 새 session 폴더를 만든다. 원본을 편집·삭제하거나 기존 평가를 덮어쓰지 않는다. 다음에 새 세션을 시작하기 전에 **기록 다시 확인**으로 재집계할 수 있다. 저장 폴더를 records 이외로 선택하면 그 영상은 자동 집계되지 않는다.

## 선별 기준

| 분류 | 기준 |
|---|---|
| 재촬영 | 건너뜀, 부분 녹화, 실패/미완료, 영상 없음/빈 파일, 기록 용량 불일치, 기존 육안 검토에서 문제가 확인된 원본 |
| 미촬영 | 해당 시나리오의 결과 기록 없음 |
| 완료 파일 있음 | 같은 시나리오에 위 문제 없이 완료 저장된 파일이 하나 이상 있음; 행동 정확성 합격이라는 뜻은 아님 |

S17·S38의 육안 검토 사유는 2026-09-11 원본 세션에만 적용한다. 새로 완료 녹화하면 그 원본 문제 때문에 계속 재촬영 대상으로 남지 않는다. S06은 전체 녹화가 부분 종료되어 보충 대상으로 표시하지만 기존 21개 체크포인트 평가에 사용한 판단은 취소하지 않는다. 원하지 않으면 S06 체크만 해제한다.

오탐/미검출인 S08·S12·S44 등은 감지기의 실패일 수 있으며 그 이유만으로 자료를 교체하지 않는다. 결과가 잘 나오는 영상만 남기는 선택 편향을 피한다. 재촬영 자료를 평가에 사용할 때는 기존 개발 자료와 별도 촬영 세션이라는 사실 및 교체 사유를 기록한다. 재촬영했다고 자동으로 독립 테스트가 되는 것은 아니다.

## 한계와 기록

- 서버가 프로젝트 records 바로 아래 세션 폴더의 session.json 및 누락된 WebM sidecar를 읽는다. 영상 내용·디코딩 손상·행동 수행의 정확성은 자동 판별하지 않는다. 읽을 수 없는 메타데이터는 경고하므로 직접 확인해야 한다.
- 안내 건너뛰기 시각은 `prompt_skips`, 시작음 요청 상태는 `start_beep`, 자동 선별 근거는 세션의 `selection_source`에 기록한다. 실제 최종 선택은 `order`가 기준이다. 직접 선택을 바꾸면 자동 선별 근거는 비운다.
- 타이머나 음성 시각은 실제 행동 정답 시각이 아니다. 음성 생략으로 프롬프트 길이가 바뀌므로 기존 영상의 고정 초 위치를 새 영상에 그대로 적용하지 않는다.
- 삐 소리는 스피커 출력 전용이다. 마이크를 녹음하지 않으므로 저장 영상에는 들어가지 않는다. 자동재생 정책·음소거·출력 장치에 따라 들리지 않을 수 있어 화면의 녹화 표시도 확인한다. `scheduled`는 재생 요청 성공이지 사람이 들었다는 증명이 아니다.
- 준비·초기 기준·행동·관찰 시간 자체는 생략하지 않는다. 설명 건너뛰기와 시나리오 전체 건너뛰기는 다른 기능이다.
