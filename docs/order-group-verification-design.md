# 주문·일행 검증 설계

## 1. 목적

키오스크 소프트웨어를 수정하지 않고 별도 실행되는 detector가 다음을 **그룹/테이블 단위**로 판단한다.

- 매장 안에 있는 사람이 몇 명인지
- 결제된 메뉴가 몇 인분인지
- 특정 그룹 또는 테이블에 실제 상품(컵·트레이·포장)이 새로 전달됐는지
- 주문 근거가 부족한 장기 체류 그룹이 있는지

목표는 사람 한 명의 영구 신원을 알아내는 것이 아니다. 사각지대가 있는 매장에서 개인 `track_id`가 끊기는 것을 전제로, 여러 증거를 합쳐 **주문 상태의 신뢰도**를 관리한다.

## 2. 전제와 비목표

### 전제

- 기존 키오스크 SW는 수정하지 않는다.
- detector는 키오스크와 별도 프로세스로 실행한다.
- 주문 완료 정보는 기존 키오스크의 DB, 로그 파일, 영수증 데이터 또는 제공 API에서 읽기 전용으로 얻는다.
- 정책상 기본적으로 메뉴 1개는 1명의 주문 커버(1인 1메뉴)를 뜻한다. 이 정책은 매장별로 켜고 끌 수 있어야 한다.
- 카메라는 매장 전체 동선을 연속적으로 보지 못하며, 사람은 사각지대를 거쳐 다른 구역에 나타날 수 있다.
- 좌석/테이블 구역 또는 사람이 모이는 구역은 ROI로 정의할 수 있다.

### 비목표

- 얼굴 인식, 실명 식별, 고객 개인정보 수집은 하지 않는다.
- `track_id`만으로 사각지대 전후의 동일인을 확정하지 않는다.
- 컵 개수만으로 주문 여부를 확정하지 않는다.
- 자동 판정을 결제 부정행위의 확정 증거로 사용하지 않는다.

## 3. 핵심 원칙

### 3.1 개인이 아니라 그룹에 주문을 배정한다

현재 `track_id`는 화면 안에서 연속적으로 보이는 동안의 임시 ID다. 화면을 오래 벗어나거나 가려지면 종료될 수 있고, 재등장하면 새 ID가 된다. 따라서 주문을 단일 `track_id`에 영구 연결하면 안 된다.

대신 근접·동시 이동·같은 테이블 착석으로 형성된 익명 `group_id`에 주문 수량과 상품 증거를 배정한다.

```text
개별 탐지(track_id) → 테이블/근접 그룹(group_id) → 주문 커버 및 상품 증거
```

### 3.2 수량은 가설이고, 상품은 보강 증거다

`menu_count = 4`는 최대 4명을 커버할 수 있다는 뜻이다. 실제 4명이 상품을 받았다는 사실은 아니다. 주문 이후에 생긴 컵·트레이·포장 객체가 해당 그룹/테이블에서 관찰되면 신뢰도를 높인다.

### 3.3 확정하지 못하면 미확정으로 남긴다

영상 사각지대, 가림, 테이크아웃, 기존 컵 등으로 증거가 모자랄 수 있다. 이 경우 다른 사람에게 주문을 임의 배정하지 않고 `UNVERIFIED`로 남긴다.

## 4. 입력 데이터

### 4.1 주문 데이터 어댑터

키오스크 SW를 바꾸지 않고, detector의 별도 어댑터가 기존 저장소를 읽는다. 우선순위는 다음과 같다.

1. 제공되는 주문/POS API의 읽기 전용 조회
2. 키오스크 로컬 DB의 읽기 전용 조회 또는 변경 감시
3. 주문 완료 로그·영수증 파일의 변경 감시
4. 최후 수단으로 화면의 주문 완료 표시를 OCR로 읽기

어댑터가 detector 내부에 전달할 최소 이벤트는 다음과 같다.

```json
{
  "event_id": "unique-event-id",
  "order_id": "A20260830-1042",
  "kiosk_id": "kiosk-01",
  "status": "paid",
  "paid_at": "2026-08-30T14:32:11+09:00",
  "menu_count": 4,
  "items": [
    {"name": "americano", "quantity": 2},
    {"name": "latte", "quantity": 2}
  ]
}
```

- `event_id`: 중복 수신 방지용. 반드시 안정적으로 제공하거나 생성한다.
- `paid_at`: 카메라 시스템 시간과 동기화되어야 한다.
- `menu_count`: 취소·증정·세트 상품을 반영한 **주문 커버 수량**과 다를 수 있으므로, 장기적으로는 `cover_count` 필드를 별도로 둔다.
- `status`: 결제 완료만 주문 크레딧을 만들며, 취소·환불은 크레딧을 회수한다.

### 4.2 영상 데이터

영상 분석에서 생성하는 입력은 다음과 같다.

```text
PersonObservation : track_id, 시각, 바운딩 박스, 신뢰도, ROI/테이블
GroupObservation  : group_id, 구성 인원 수, 테이블 ID, 관찰 구간
ObjectObservation : object_id, 클래스(cup/tray/bag 등), 시각, 위치, 테이블 ID
```

처음에는 지원 객체를 매장 유형에 맞춰 제한한다.

| 매장 유형 | 우선 검출 객체 |
| --- | --- |
| 음료 매장 | 컵, 트레이 |
| 카페/베이커리 | 컵, 트레이, 포장 봉투 |
| 푸드코트 | 트레이, 식판, 음식 용기 |

COCO의 `cup` 검출만으로 운영하지 않는다. 실제 컵·트레이의 거리, 조명, 가림 환경에서 검출률을 측정한 후 전용 모델/데이터를 추가한다.

## 5. 데이터 모델

### 5.1 그룹

```json
{
  "group_id": "G-20260830-0012",
  "table_id": "T-03",
  "observed_people": 3,
  "first_seen": "2026-08-30T14:30:00+09:00",
  "last_seen": "2026-08-30T14:45:00+09:00",
  "order_credits": 3,
  "new_product_evidence": 3,
  "status": "CONFIRMED_ORDERED",
  "confidence": 0.91
}
```

`group_id`는 개인 식별자가 아니며, 같은 테이블에 일정 시간 함께 관찰된 익명 집합이다. 구성원의 일시 `track_id`가 바뀌어도 테이블 인원 및 객체 증거를 통해 그룹 상태를 유지한다.

### 5.2 주문 크레딧

결제 완료 주문은 `menu_count` 또는 매장 정책의 `cover_count`만큼의 **주문 크레딧**을 만든다.

```text
order_id A1042, cover_count 4
→ 아직 배정되지 않은 주문 크레딧 4개
→ 하나 이상의 그룹에 배정되면 남은 크레딧 감소
```

크레딧은 결제 후 제한 시간(예: 20분) 동안만 배정 후보로 유지한다. 시간 초과 크레딧은 테이크아웃·미관측 주문으로 종료하며, 다른 손님에게 뒤늦게 배정하지 않는다.

## 6. 그룹과 테이블 구성

### 6.1 테이블 ROI가 있는 경우

가장 먼저 구현할 방식이다.

- 테이블마다 폴리곤 ROI 또는 사각 ROI를 설정한다.
- 일정 시간 이상 같은 테이블 ROI에 존재하는 사람 수를 `observed_people`로 계산한다.
- 한 테이블의 사람이 모두 사라진 뒤 유예 시간(예: 60초)이 지나면 해당 그룹을 종료한다.
- 새 사람의 재등장 여부보다 테이블의 점유·비점유 변화에 집중한다.

### 6.2 테이블 ROI가 없는 경우

사람 사이 거리, 이동 방향, 동시 체류 시간을 사용해 근접 그룹을 만든다. 이 방식은 서로 가까이 지나가는 타인도 일행으로 묶을 위험이 있으므로 `LIKELY` 이상을 자동 확정하지 않는다.

### 6.3 사각지대 처리

사각지대 전후 개인 동일성은 확정할 수 없다. 다음 중 하나가 있을 때만 주문과 그룹의 연결 신뢰도를 올린다.

- 결제 시각 직후 동일 테이블에 새 그룹이 형성됨
- 주문 수량과 그룹 인원 수가 일치함
- 해당 테이블에서 주문 이후 새 상품 객체가 증가함
- 다른 경쟁 그룹이 없음

## 7. 상품 증거 판정

### 7.1 단순 객체 수가 아닌 `새로운 등장`을 센다

테이블별로 주문 직전 기준선(baseline)을 저장한다.

```text
14:31:50 T-03: 사람 3명, 컵 0개, 트레이 0개
14:32:11 주문 3개 결제
14:34:00 T-03: 사람 3명, 컵 3개, 트레이 1개
→ 신규 상품 증거: 컵 +3, 트레이 +1
```

기존에 놓인 컵, 쓰레기, 다른 테이블에서 이동한 컵은 신규 증거로 세지 않는다. 객체가 일정 시간(예: 3~5초) 지속해서 검출되고, 테이블 ROI 안에서 정지/배치된 경우에만 카운트한다.

### 7.2 증거 점수 예시

아래 점수는 초기안이며, 실제 영상 데이터로 보정한다.

| 조건 | 점수 |
| --- | ---: |
| 주문 수량과 그룹 인원이 일치 | +0.35 |
| 주문 후 5분 안에 그룹/테이블 형성 | +0.20 |
| 신규 컵 또는 용기 1개당 (최대 인원 수까지) | +0.10 |
| 신규 트레이 1개 | +0.15 |
| 경쟁 그룹 없음 | +0.15 |
| 다른 그룹에도 동등한 후보가 있음 | -0.30 |
| 상품 증거가 전혀 없음 | -0.15 |

점수는 0~1 범위로 정규화한다. 컵 수가 메뉴 수를 초과해도 무한히 점수를 올리지 않으며, 사람 수/주문 커버 수를 상한으로 둔다.

## 8. 주문 배정 알고리즘

### 8.1 후보 생성

결제 이벤트마다 아래 조건을 만족하는 그룹을 후보로 만든다.

- 결제 이후 배정 시간 창(예: 0~10분)에 관찰됨
- 비어 있지 않은 테이블/근접 그룹임
- 아직 주문 커버가 부족함
- 신규 상품 증거 또는 수량 일치 중 하나가 있음

### 8.2 배정

주문 크레딧을 후보 그룹에 배정하되 다음 규칙을 지킨다.

1. 한 그룹에는 관찰 인원 수보다 많은 크레딧을 확정 배정하지 않는다.
2. 수량 일치와 상품 증거가 높은 그룹을 우선한다.
3. 두 그룹의 점수 차가 작으면 어느 쪽에도 자동 확정하지 않는다.
4. 하나의 주문이 여러 테이블에 나뉘는 것은 기본적으로 불허한다. 매장 운영상 흔하면 설정으로 허용한다.
5. 결제 취소/환불 시 아직 사용되지 않은 크레딧부터 회수하고, 이미 확정된 경우 `REVIEW_REQUIRED`로 남긴다.

### 8.3 상태 정의

| 상태 | 의미 | 알림 처리 |
| --- | --- | --- |
| `CONFIRMED_ORDERED` | 주문 수량·인원·상품 증거가 충분히 일치 | 미주문 알림 제외 |
| `LIKELY_ORDERED` | 주문 연결이 그럴듯하나 증거가 부족 | 기본적으로 알림 보류 |
| `UNVERIFIED` | 주문/상품 근거가 부족하거나 경쟁 후보 존재 | 장기 체류 시 점검 후보 |
| `REVIEW_REQUIRED` | 상충하는 주문, 환불, 수량 초과 등 | 대시보드 확인 필요 |

기존의 `unordered_seated`는 `UNVERIFIED` 상태가 설정된 유예 시간 이상 지속된 경우에만 발생시킨다. 이벤트 메시지도 “미주문 확정”이 아니라 “주문 확인 필요”로 표시한다.

## 9. 시나리오

### 시나리오 A: 4명, 메뉴 4개

```text
14:30  T-03에 4명 관찰
14:32  주문 1건, menu_count=4, 결제 완료
14:34  T-03에서 새 컵 4개 또는 트레이/용기 증거 관찰

결과: T-03 = CONFIRMED_ORDERED (커버 4 / 인원 4)
```

### 시나리오 B: 1명 팀 + 3명 팀, 메뉴 3개

```text
14:30  T-01에 1명, T-03에 3명 관찰
14:32  주문 1건, menu_count=3, 결제 완료
14:34  T-03에 새 컵/용기 3개 관찰

결과: T-03 = CONFIRMED_ORDERED (커버 3 / 인원 3)
      T-01 = UNVERIFIED (커버 0 / 인원 1)
```

T-01은 즉시 위반으로 처리하지 않는다. 추가 주문·상품 수령 가능성을 위해 유예 시간을 적용한다.

### 시나리오 C: 근거 부족

```text
14:32  주문 4개 결제
14:34  4명 그룹이 보이지만, 테이블이 가려져 컵/트레이를 볼 수 없음

결과: LIKELY_ORDERED 또는 UNVERIFIED
```

이 경우 시스템은 자동 확정을 피하고 대시보드에 근거 부족 사유를 기록한다.

## 10. 대시보드 요구사항

- 테이블 ROI를 추가·수정·삭제하고, 이름(`T-01`)을 붙일 수 있어야 한다.
- 테이블별 현재 인원, 주문 커버 수, 신규 컵/트레이 수, 상태·신뢰도를 보여야 한다.
- 주문 이벤트 목록: 주문번호, 결제 시각, 메뉴 수량, 남은 크레딧, 배정 그룹을 보여야 한다.
- 자동 배정 후보와 점수 근거를 확인할 수 있어야 한다.
- 점주가 `UNVERIFIED` 그룹에 주문을 수동 배정/해제할 수 있어야 한다.
- 수동 조정과 원래 자동 판정은 감사 로그에 남겨야 한다.

## 11. 구현 단계

### 1단계: 관측과 기록

- 주문 DB/로그 읽기 전용 어댑터
- 중복 없는 주문 이벤트 저장
- 테이블 ROI와 테이블별 인원 카운트
- 컵·트레이 후보 객체의 검출 로그 및 테이블별 기준선

이 단계에서는 자동 미주문 알림을 내지 않고, 영상·주문 데이터가 실제로 맞는지 검증한다.

### 2단계: 보수적 자동 배정

- 결제 후 시간 창, 인원 수, 신규 상품 증거를 이용한 점수 계산
- `LIKELY_ORDERED`와 `UNVERIFIED` 표시
- 경쟁 후보 또는 낮은 점수는 자동 배정하지 않음

### 3단계: 운영 알림

- 높은 신뢰도의 `CONFIRMED_ORDERED`만 주문 완료 처리
- 충분한 유예 시간 뒤에도 `UNVERIFIED`인 그룹만 “주문 확인 필요” 알림
- 점주 수동 보정 결과를 수집해 임계값을 조정

## 12. 검증 지표

- 주문 이벤트 누락률·중복률
- 테이블별 사람 수 오차
- 신규 컵/트레이 검출 정밀도와 재현율
- 자동 배정 정답률
- `UNVERIFIED` 알림의 오탐률
- 수동 보정 비율과 보정 사유

운영 전에는 실제 매장 영상과 주문 로그를 시간 동기화해 재생하면서, 최소 며칠치 표본으로 위 지표를 확인한다.

## 13. 결정이 필요한 항목

- 메뉴 수량을 그대로 `cover_count`로 볼 수 있는 매장 정책인지
- 세트·사이드·무료 증정 메뉴의 인원 환산 규칙
- 테이크아웃 주문을 제외할 수 있는 주문 필드의 유무
- 사용할 주문 데이터 원본(DB, 파일, API)과 접근 권한
- 테이블 ROI를 볼 수 있는 카메라 화각 및 상품 객체의 실제 가시성
- 주문 배정 시간 창, 장기 체류 유예 시간, 수동 검토 담당자

이 항목이 정해지기 전에는 `unordered_seated`를 미주문 확정 용도로 사용하지 않는다.
