# i5-4200U에서 YOLO Pose + Tier2 동시 운용 부하 추정

> 작성일: 2026-09-12
>
> 대상: Intel Core i5-4200U (2코어 4스레드, 15W), Windows, ONNX Runtime CPU EP
>
> 주의: 이 문서는 **4200U 실측값이 아니라 코드 분석 + 현재 개발 PC 벤치마크를 이용한 용량 산정치**다.

> **후속 실험:** U8S8 후보를 실제 생성해 비교한 결과, 빠른 전체 양자화 모델은 confidence가 0으로 깨졌고 정상 출력 모델은 FP32보다 느렸다. 상세 결과는 `docs/haswell-u8s8-quantization-benchmark.md`를 참조한다. 현재 배포 속도 후보는 FP32다.

## 결론

현재 설정으로 두 모델을 운용하는 것은 가능하지만 여유가 크지는 않다.

- 평상시에는 모션 게이트와 트래커가 Pose 호출을 줄이므로 운용 가능성이 높다.
- 움직임이 계속되어 Pose가 최대 주기인 초당 3회 실행되면, 추론만으로 두 물리 코어를 약 **28~43%의 시간** 점유할 것으로 예상한다.
- Windows 작업 관리자 기준 추론 자체의 평균 증가분은 대략 **14~22%p**다. 디코딩·트래킹·스트리밍까지 합치면 보통 **30~55%**, 미리보기까지 켜면 **55~80% 이상**을 예상한다.
- 90번째 프레임에는 Pose와 Tier2가 병렬이 아니라 **직렬로 연속 실행**되어 약 **145~225ms**의 지연이 생길 수 있다. 15fps의 프레임 간격 66.7ms보다 길어 2~3프레임가량 처리가 밀릴 수 있다.
- 사람이 사라진 직후 회전 재검사가 발동하면 Pose를 최대 3회 실행하므로, 드문 최악 프레임은 **325~505ms + 전후처리**까지 늘어날 수 있다.
- 현재 `--threads 3`보다는 **`--threads 2`를 권장**한다. 4200U는 물리 코어가 2개라 세 번째 작업 스레드는 HT 자원과 디코딩/스트리밍 자원을 경쟁한다.

따라서 **미리보기 OFF, ORT 2스레드, 현재의 모션 게이트 유지**가 권장 배포 설정이다. 24시간 운용 전에는 실제 4200U에서 20분 이상 열 포화 상태로 검증해야 한다.

## 계산에 사용한 현재 설정

`run.bat`과 코드 기본값을 기준으로 했다.

| 항목 | 현재 값 | 부하에 미치는 영향 |
|---|---:|---|
| 카메라 | 1280×720, 15fps | 프레임 간격 66.7ms |
| Pose | 416×416 INT8 | `--detect-every 5`, 최대 3회/s |
| Tier2 | 320×320 INT8 | `detect_every_obj=90`, 최대 0.167회/s |
| Provider | CPU | 4200U 내장 GPU로 INT8 ONNX를 실행하지 않음 |
| ORT 스레드 | 현재 3 | 권장 2 |
| 트래킹/모션 게이트 | 사용 | 실제 Pose 호출 수를 크게 줄임 |
| 스트림 서버 | 8081 | 접속 중 JPEG 인코딩 부하 발생 |

중요한 점은 15fps에서 90프레임은 **3초가 아니라 6초**라는 것이다.

또한 일반 Tier2 주기 실행 코드는 Pose가 실제로 실행된 프레임 안에 있다. 따라서 모션 게이트가 해당 프레임의 Pose를 생략하면 Tier2도 생략된다. Surface Monitor를 사용하면 이 주기 실행 대신 요청 기반으로 Tier2가 실행된다.

## 모델 크기와 형식

| 모델 | 입력 | 파일 크기 | 양자화 그래프 |
|---|---:|---:|---|
| YOLO11n Pose INT8 | 416×416 | 3.12MiB | `ConvInteger` 중심 |
| Tier2 YOLO11n INT8 | 320×320 | 2.80MiB | QDQ (`QuantizeLinear/DequantizeLinear`) |
| 합계 | - | **5.92MiB** | 서로 다른 INT8 형식 |

파일 크기는 작지만 실행 메모리는 가중치, 중간 activation, ORT 세션, FFmpeg 버퍼를 포함하므로 더 크다. 두 추론 세션의 추가 메모리는 대략 **80~200MiB**, 전체 프로세스는 브라우저를 제외하고 대략 **250~500MiB** 범위로 잡는 것이 안전하다. 이 메모리 수치는 아직 실측하지 않은 계획값이다.

## 개발 PC 상대 벤치마크

4200U가 아닌 현재 개발 PC의 i7-8700에서 두 모델의 상대 비용과 INT8 실행 특성을 확인했다. 카메라·트래커·그리기·스트리밍을 제외하고 ONNX Runtime CPU EP만 측정했으며, 각 모델 5회 워밍업 후 30회 실행했다.

### INT8 결과

| ORT 스레드 | Pose 평균 | Tier2 평균 | 직렬 합계 평균 | 직렬 합계 p95 |
|---:|---:|---:|---:|---:|
| 1 | 52.3ms | 31.3ms | 83.6ms | 87.5ms |
| 2 | 39.7ms | 24.2ms | 63.9ms | 67.5ms |
| 3 | 37.0ms | 22.5ms | 59.5ms | 61.8ms |

### FP32 비교(2스레드)

| 형식 | Pose 평균 | Tier2 평균 | 직렬 합계 평균 |
|---|---:|---:|---:|
| FP32 | 22.2ms | 12.5ms | 34.8ms |
| INT8 | 39.7ms | 24.2ms | 63.9ms |

이 결과에서는 INT8이 FP32보다 약 1.8배 느렸다. 즉, 파일 크기는 크게 줄었지만 해당 양자화 연산자가 이 CPU에서 빠른 경로를 타지 못했다. 4200U도 AVX2는 지원하지만 VNNI가 없으므로 **INT8은 무조건 빠르다는 가정을 하면 안 된다.** 실제 4200U에서는 FP32와 INT8을 모두 비교해야 한다.

재현 스크립트:

```powershell
.\.venv-train\Scripts\python.exe scripts\benchmark_dual_onnx.py --threads 2 --runs 100
```

## 4200U 추론 시간 환산

i7-8700의 2스레드 결과에 4200U의 낮은 지속 클럭, 세대 차이, 15W 열 제한을 고려한 **2.3~3.5배 계수**를 적용했다. 이는 제품 보증값이 아니라 용량 계획용 범위다.

| 구간 | 4200U 예상 시간 |
|---|---:|
| Pose INT8 1회 | **90~140ms** |
| Tier2 INT8 1회 | **55~85ms** |
| 같은 프레임의 직렬 합계 | **145~225ms** |
| 회전 Pose 2회까지 포함한 드문 최악값 | **325~505ms** |

장시간 열 포화, 낮은 메모리 대역폭, 백그라운드 프로세스가 겹치면 상단 값을 넘을 수 있다.

## 평균 추론 부하 계산

모델 호출이 CPU를 점유하는 시간 비율은 다음처럼 계산했다.

```text
추론 점유율 = Pose 호출률 × Pose 시간 + Tier2 호출률 × Tier2 시간
```

모션 게이트가 전혀 줄여주지 않는 상한은 다음과 같다.

```text
Pose  : 3/s × 90~140ms       = 27.0~42.0%
Tier2 : 1/6s × 55~85ms       =  0.9~ 1.4%
합계                            = 27.9~43.4%
```

이는 두 물리 코어를 사용하는 추론 호출이 존재하는 시간 비율이다. ORT 2스레드가 실행 중 두 논리 프로세서를 채운다고 단순화하면, 4논리 스레드로 정규화하는 Windows 작업 관리자에는 추론만 약 **14~22%p**로 나타난다. 반면 프로그램 내부 CPU 지표는 1코어를 100%로 계산하므로 추론 부분만 대략 **56~87%**로 보일 수 있다.

## 운용 시나리오별 예상

아래의 전체 CPU는 작업 관리자 기준 계획값이다. 디코더 종류, 스트림 접속 여부, 카메라 드라이버에 따라 달라진다.

| 시나리오 | Pose 호출률 가정 | 추론 점유 시간 | 전체 CPU 예상 | 판단 |
|---|---:|---:|---:|---|
| 정적/빈 화면 | 약 0.1/s 이하 | 약 1~3% | **10~25%** | 여유 있음 |
| 일반 운용 | 약 1/s | 약 10~15% | **20~40%** | 운용 가능 |
| 움직임 지속, 게이트 효과 없음 | 3/s | 약 28~43% | **30~55%** | 여유 적음 |
| 위 조건 + 로컬 미리보기 | 3/s | 약 28~43% | **55~80%+** | 비권장 |
| 회전 재검사/스트림/OS 작업 중첩 | 순간 최대 | - | **순간 80~100% 가능** | 프레임 지연 가능 |

Tier2의 평균 기여분은 작다. 실제 문제는 6초마다 생기는 평균 CPU 증가가 아니라, Pose 직후 Tier2가 붙으면서 생기는 **145~225ms 순간 지연**이다.

## 권장 설정

1. `--threads 2`를 사용한다. 3스레드는 i7 벤치에서는 7% 정도 빨랐지만 2코어 4200U에서는 HT 경쟁과 나머지 파이프라인 정체 가능성이 더 크다.
2. 배포 장비에서는 로컬 `--preview`를 끈다. 영상 확인은 필요할 때만 스트림으로 한다.
3. 현재의 `--detect-every 5`, 15fps, 모션 게이트와 트래커를 유지한다.
4. Tier2의 즉시성이 중요하지 않으면 `detect_every_obj`를 120~150으로 늘린다. 평균 절감은 작지만 충돌 빈도는 줄어든다.
5. 실제 4200U에서 INT8과 FP32를 같은 조건으로 비교한다. 현재 개발 PC에서는 FP32가 더 빨랐기 때문에 4200U에서도 역전 가능성이 있다.
6. 정확도에 영향이 없다면 Pose 입력을 416×288 또는 416×224로 낮추는 것이 가장 큰 여유를 만든다.

권장 실행 변경 예시는 다음과 같다.

```text
--provider cpu --threads 2 --camera-fps 15 --detect-every 5
```

## 실제 장비 합격 기준

4200U에서 미리보기 없이 실제 카메라와 스트림을 연결한 뒤 최소 20분 연속 실행한다.

- 평균 전체 CPU: 60% 이하
- 순간 CPU: 90% 이상이 장시간 지속되지 않을 것
- Pose p95: 160ms 이하
- Pose+Tier2 충돌 프레임: 250ms 이하
- 카메라 입력 15fps 유지, 누적 지연이 계속 증가하지 않을 것
- CPU 온도/클럭이 안정된 마지막 10분 결과를 사용할 것

이 기준을 넘으면 순서대로 `threads 2`, 미리보기 OFF, Pose 비율 축소, `detect_every` 증가를 적용한다. Tier2 주기만 늘리는 것은 평균 부하 개선 효과가 1%p 안팎이라 우선순위가 낮다.
