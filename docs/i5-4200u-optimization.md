# i5-4200U 전용 최적화 계획

> 작성일: 2026-08-30
> 대상 하드웨어: Intel Core i5-4200U (Haswell-ULT, 2C/4T, 15W)
> 차순위 대상: Celeron J1900 (Bay Trail, 4C/4T, 10W) — 9절 별도 프로파일
> 기준 실행 설정: `run.bat` — `--camera-size 1280x720 --camera-fps 15 --preview --provider cpu --detect-every 3 --track`
>
> **이 문서의 모든 수치는 코드를 읽어 산출한 추정치다.** 실측이 아니다. 8절의 측정 프로토콜로 검증한 뒤 채택 여부를 정한다.

## 1. 하드웨어 예산 — 무엇이 진짜 병목인가

| 항목 | 값 | 함의 |
|---|---|---|
| 코어 / 스레드 | 2C / 4T | HT 형제는 실행 유닛을 공유. AVX2 GEMM은 FMA 유닛을 포화시키므로 **HT 이득이 거의 없다** |
| 클럭 | 기본 1.6GHz / 터보 2.6GHz | 15W 안에서 **AVX2 지속 부하 시 1.6~1.9GHz로 수렴**. 카탈로그 클럭을 전제로 계산하면 안 된다 |
| L1d / L2 | 32KB/코어 / 256KB/코어 | 다운샘플 그레이(57KB)는 L2에 상주 가능 |
| **L3** | **3MB (2코어 공유)** | **이 문서에서 가장 중요한 숫자** |
| 메모리 | DDR3L-1600 듀얼채널, 실측 대역폭 ~15GB/s | **iGPU와 공유**. DirectML을 쓰면 같은 버스를 두 번 두드린다 |
| TDP | 15W (CPU + iGPU + 언코어 합산) | iGPU를 쓰면 코어가 다운클럭된다. 제로섬이다 |
| ISA | AVX2 + FMA3 | 쓰고 있지 않다 (5절) |

### 핵심 제약: L3 3MB vs 720p RGB 프레임 2.76MB

```
1280 × 720 × 3 bytes = 2,764,800 bytes = 2.64 MB
L3 = 3 MB
```

**전체 프레임을 한 번 훑는 연산 하나가 L3의 88%를 쓸어버린다.** 현재 파이프라인은 프레임당 이런 전체 순회를 **9번** 한다(2절). 그 결과 YOLO 추론이 시작될 때마다 가중치와 활성값이 L3에서 이미 축출된 상태로 시작한다.

Haswell에서 이 기기가 느린 진짜 이유는 FLOPS가 부족해서가 아니라, **캐시가 계속 비워지기 때문**이다. 따라서 최적화의 1차 목표는 연산량 감소가 아니라 **프레임 버퍼를 L3에 들어가는 크기로 줄이고, 전체 순회 횟수를 줄이는 것**이다.

### 여기서 즉시 보이는 세 가지 낭비

**(1) 같은 프레임의 그레이스케일을 3번 만든다.**

`gray.c`의 주석이 스스로 인정하고 있다 — *"tracker.c의 make_gray()와 동일한 공식"*. 두 함수는 downsample도 똑같이 4다(`main.c:995` `{4, 3, 2, 24}`의 첫 필드, `main.c:677`의 인자 4). 여기에 `camera_health`가 그 결과의 사본을 또 하나 들고 있다(`camera_health.c:28`).

**(2) 그 그레이스케일의 원본이 애초에 그레이스케일이었다.**

디코더는 YUV420P를 내놓는다. **Y 평면이 곧 luma다.** 현재 흐름은:

```
YUV420P (Y = luma) ──sws_scale──> RGB24 ──77R+150G+29B>>8──> gray
                     [2.76MB 쓰기]        [× 3회 반복]
```

Y 평면을 그대로 읽으면 이 경로 전체가 사라진다.

**(3) 미리보기가 기본으로 켜져 있다.**

`run.bat:47`에 `--preview`, `run.ps1:21`에 `[switch]$Preview = $true`. 배포 기기에서 ffplay는 **코어 하나를 통째로 먹는 별도 프로세스**이고, 여기에 41MB/s의 파이프 쓰기가 더해진다. 개발 편의 기본값이 배포 설정에 그대로 남아 있다.

## 3. 최우선 원칙 — 가장 싼 추론은 실행하지 않는 추론

CLAUDE.md와 `tiered-inference.md`의 방침대로, **1차 판단은 전부 룰(픽셀 연산 + 조건문)로 하고 YOLO는 룰이 판단을 포기했을 때만 돌린다.**

이 원칙은 단순히 정확도 정책이 아니라 **이 하드웨어에서 가장 효과가 큰 최적화 수단**이다. 근거:

```
YOLO11n 416×416 FP32 1회 추론 (i5-4200U 추정)  ≈ 60 ~ 120 ms
8배 다운샘플 Y 평면 전체 차분 (160×90=14,400 B) ≈ 0.01 ms
                                          ────────────────
                                          약 6,000 ~ 12,000 배
```

**추론 1회를 아끼는 것이 픽셀 연산 수천 번을 아끼는 것보다 압도적으로 크다.** 따라서 아래 Part A(추론 회피)를 Part B(연산 최적화)보다 먼저, 더 공격적으로 적용한다.

무인 카페의 실제 운영 조건이 이 전략을 뒷받침한다. 7~10평 매장은 **영업시간의 상당 부분이 무인·무손님 상태**다. 이 시간의 CPU를 0에 가깝게 만드는 것이 평균 점유율을 낮추는 가장 큰 레버다.

# Part A — 추론을 실행하지 않기 위한 룰 계층

현재 게이트는 "전체 화면 변화율 < 임계값" 이라는 **단일 이진 판정** 하나뿐이다(`main.c:712-726`). 이것을 위치 정보를 가진 다단계 게이트로 바꾼다.

## A-1. Y 평면 직접 사용 — 그레이스케일 3중 계산 제거

**변경**

`RgbFrame`에 디코딩 원본의 luma 평면을 차용 포인터로 실어 콜백까지 전달한다.

```c
/* include/media.h
 *
 * luma: 디코더가 만든 Y 평면을 그대로 가리킵니다. FFmpeg(AVFrame) 소유이며
 *       콜백이 반환하는 순간 무효화됩니다. 호출자는 절대 free하지 않고,
 *       콜백 범위 밖으로 포인터를 보관해서도 안 됩니다.
 *       입력이 RGB 계열이라 Y 평면이 없으면 NULL입니다.
 *
 * Y 평면을 별도로 넘기는 이유: 디코더 출력이 이미 luma를 갖고 있는데
 * RGB로 변환한 뒤 다시 luma를 계산하는 것은 같은 값을 두 번 만드는
 * 일입니다. 모션·카메라헬스·추적기가 모두 luma만 필요로 합니다. */
typedef struct {
    uint8_t *data;          /* RGB24, Pipeline 소유 */
    const uint8_t *luma;    /* 차용 — 위 설명 참조. NULL 가능 */
    int luma_stride;
    int width, height, stride;
    int64_t index;
} RgbFrame;
```

`handle_decoded_frame()`에서 `decoded->format`이 YUV 계열이면 `decoded->data[0]`/`linesize[0]`을 실어 준다.

**효과**

| 제거되는 것 | 근거 |
|---|---|
| `gray_buf_update()`의 RGB→luma 변환 전체 | 곱셈 3회 + 시프트가 픽셀마다 사라짐 |
| `tracker.c: make_gray()` 중복 변환 | `gray.c`와 동일 결과를 재사용 |
| `camera_health`의 별도 prev 버퍼 57KB | `gray_prev` 하나로 통합 |
| 스트라이드 점프 샘플링의 캐시 낭비 | Y 평면은 연속 바이트 — 8배 다운샘플 시 **160×90 = 14,400 B, L1에 통째로 상주** |

다운샘플도 4 → 8로 올린다. 모션 게이트·카메라 헬스·문 감지 트리거 용도에 160×90이면 충분하고, 14KB는 L1(32KB)에 들어가 이후 모든 차분 연산이 캐시 미스 없이 돈다.

**주의**: RGB 입력 파일(JPEG 등)이나 `luma == NULL`인 경우를 위해 기존 RGB→gray 경로를 폴백으로 유지한다. 기동 시 어느 경로인지 로그를 남긴다.

```
gray: luma plane direct (YUV420P) — RGB 변환 생략
gray: RGB fallback — 입력에 luma 평면 없음
```

**공수**: 1일 / **추정 효과**: 항목 2·3·4·5 합산 21 MB/s → 약 2 MB/s

## A-2. 블록 단위 변화 맵 + 조기 종료

**현재 문제**

`main.c:716`은 57,600 픽셀을 **항상 끝까지** 순회한 뒤 비율을 계산한다. 임계값은 0.004 = 230픽셀이다. 사람이 움직이는 흔한 경우는 **첫 몇 줄에서 이미 230을 넘는데도 나머지 57,000 픽셀을 계속 센다.**

그리고 결과가 "변했다/안 변했다" 한 비트뿐이라, **어디가 변했는지**를 모른다. 그래서 문 앞에서 흔들리는 그림자와 좌석의 사람을 구분하지 못한다.

**변경**

8배 다운샘플 Y(160×90)를 **8×8 블록 격자(20×12 = 240 블록)** 로 나눠 블록별 변화량을 낸다.

```c
/* include/motion.h
 *
 * 240개 블록의 변화 여부를 비트맵으로 담습니다. 240비트 = 30바이트로
 * 캐시 한 줄에 들어가므로, 이후 ROI 교차 판정이 사실상 무료입니다.
 *
 * 비율 하나가 아니라 위치를 남기는 이유: "변화가 있다"만으로는 추론
 * 필요 여부를 판단할 수 없습니다. 변화가 이미 추적 중인 박스 안에서만
 * 일어났다면 YOLO 대신 추적기로 충분합니다. */
typedef struct {
    uint32_t bits[8];       /* 240블록 비트맵 */
    uint16_t changed_blocks;
    uint16_t changed_pixels;
} MotionMap;

void motion_analyze(const uint8_t *cur, const uint8_t *prev,
                    int w, int h, int threshold, MotionMap *out);
```

**조기 종료**는 "전체 변화율" 판정에만 쓴다. 블록 맵이 필요한 프레임에서는 전체를 돌되, 대상이 14KB뿐이라 L1 안에서 끝난다.

**공수**: 0.5일

## A-3. 변화 위치 기반 4단계 게이트 (핵심)

`motion_analyze()`의 결과를 써서 **YOLO 실행 여부를 위치로 판단**한다.

```
                    ┌─────────────────────────────┐
                    │ L0  영업시간 밖?            │ → 추론 0, 15초마다 헬스만
                    └──────────┬──────────────────┘
                               ▼
                    ┌─────────────────────────────┐
                    │ L1  변화 블록 == 0?         │ → 종료. 비용 ≈ 0.01ms
                    └──────────┬──────────────────┘   (빈 매장의 정상 상태)
                               ▼
                    ┌─────────────────────────────┐
                    │ L2  변화가 감시 ROI 밖에만? │ → 종료.
                    │     (창밖 나무, 간판 조명)  │   무시 마스크 적용
                    └──────────┬──────────────────┘
                               ▼
                    ┌─────────────────────────────┐
                    │ L3  변화가 기존 트랙 박스   │ → SAD 추적기만 실행.
                    │     안에서만 일어났는가?    │   YOLO 생략
                    └──────────┬──────────────────┘
                               ▼
                    ┌─────────────────────────────┐
                    │ L4  트랙 밖 새 변화         │ → YOLO 실행
                    └─────────────────────────────┘
```

**L2 — 무시 마스크**: 설치 시 점주/설치자가 대시보드에서 "감시하지 않을 영역"(창문, 출입구 밖 도로, 모니터 화면, 흔들리는 현수막)을 칠한다. 240블록 비트맵과 AND 한 번이면 끝난다. 무인 카페에서 창밖 차량·행인으로 인한 불필요한 추론은 실제로 매우 잦다.

**L3 — 트랙 내부 변화**: 이미 추적 중인 사람이 제자리에서 움직이는 것뿐이라면 새 객체가 등장한 게 아니다. 기존 `--track` SAD 추적기로 박스를 보정하는 것으로 충분하다. 현재는 `detect_every` 주기가 오면 무조건 YOLO를 돌리므로, **앉아 있는 손님 한 명 때문에 초당 5회 추론이 계속 돈다.**

다만 트랙 드리프트 누적을 막기 위해 **`track_refresh_seconds`(기본 5초)마다 1회는 강제로 YOLO를 실행**한다. L3에 갇혀 영원히 추론을 건너뛰는 상태를 방지하는 안전 밸브다.

**L0 — 영업시간 게이트**: `config.json`에 `active_hours = "07:00-23:00"`. 영업시간 밖에는 추론을 완전히 끄고 카메라 헬스만 15초 주기로 확인한다. 침입 감지가 필요한 매장은 `after_hours_mode = motion_only`로 L1만 켠다.

**추정 효과 (7~10평 매장 하루 기준)**

| 상황 | 시간 비중(가정) | 현재 추론/초 | 개선 후 |
|---|---:|---:|---:|
| 영업시간 밖 | 33% | 5 | 0 |
| 빈 매장 | 40% | 0 (모션 게이트가 이미 처리) | 0 |
| 손님 정지 착석 | 20% | 5 | 0.2 (5초 갱신) |
| 손님 이동·입퇴장 | 7% | 5 | 5 |

가중 평균 추론 횟수: **5회/초 → 약 0.4회/초 (약 1/12)**

이 표의 시간 비중은 가정이다. 파일럿 매장 로그로 실제 분포를 측정한 뒤 갱신한다. 다만 **어떤 분포를 넣어도 이 게이트가 가장 큰 레버라는 결론은 바뀌지 않는다.**

**공수**: 2일

## A-4. 모션 게이트가 사람을 "빈 매장"으로 오인하지 않게

현재 게이트는 사람이 앉아만 있어도 `idle_refresh_seconds`(10초)까지 추론을 끊는다(`main.c:721-725`). 체류·쓰러짐 판정이 최대 10초 지연된다.

# Part B — 그래도 도는 연산을 싸게 만들기

## B-1. 파이프라인 해상도를 640×360으로 (전체 순회 비용 ÷4)

**핵심 관찰: 720p로 캡처해도 모델이 보는 픽셀 수는 똑같다.**

```
1280×720 → 416×416 letterbox
  scale = min(416/1280, 416/720) = min(0.325, 0.578) = 0.325
  실제 이미지 영역 = 416 × 234

640×360 → 416×416 letterbox
  scale = min(416/640,  416/360) = min(0.650, 1.156) = 0.650
  실제 이미지 영역 = 416 × 234      ← 완전히 동일
```

**720p 캡처는 검출 성능에 아무것도 기여하지 않으면서 모든 전체 프레임 순회를 4배로 만든다.** 10m 거리의 사람이 모델 입력에서 차지하는 픽셀 수는 두 경우가 같다.

**변경 방법**

카메라 모드 협상에 의존하지 않는다(640×360을 지원하지 않는 장치가 흔하다). **이미 돌고 있는 `sws_scale`의 출력 크기만 바꾼다.** 추가 순회가 0이다.

```c
/* media_ffmpeg.c — 색공간 변환과 다운스케일을 한 번에 처리합니다.
 * 별도 스케일 패스를 두지 않는 이유: sws_scale이 어차피 프레임 전체를
 * 훑으므로, 출력 해상도를 낮추는 것은 추가 비용 없이 이득만 얻습니다. */
pipeline->input_sws = sws_getCachedContext(
    pipeline->input_sws,
    decoded->width, decoded->height, (enum AVPixelFormat)decoded->format,
    target_width, target_height, AV_PIX_FMT_RGB24,   /* ← 640×360 */
    SWS_FAST_BILINEAR, NULL, NULL, NULL);
```

동시에 카메라에도 낮은 모드를 요청한다(`--camera-size 640x480`). 장치가 받아주면 USB 대역폭과 MJPEG 디코딩 비용까지 절약된다. 안 받아줘도 sws 단계에서 걸러지므로 손해가 없다.

**효과**

```
RGB 프레임: 2.76 MB → 0.69 MB    ← L3 3MB에 여유 있게 상주
```

항목 1·7·8·9·10이 모두 1/4이 된다. **L3 축출이 사라지는 것이 숫자보다 더 큰 이득이다.**

**주의 — 마이그레이션**: `door_roi_*`와 향후 ROI 좌표가 전부 프레임 좌표다. 해상도를 바꾸면 **ROI와 문 기준 이미지를 재설정해야 한다.** config에 `roi_reference_width/height`를 함께 저장해 두고, 현재 프레임 크기와 다르면 자동 스케일하거나 대시보드에 재설정을 경고한다. 이 처리 없이 해상도만 바꾸면 문 감지가 조용히 망가진다.

**공수**: 0.5일 (+ ROI 마이그레이션 0.5일)

## B-2. 종횡비별 모델 세트 — 패딩 연산 제거

### 문제: 정사각형 모델은 어떤 카메라와도 맞지 않는다

416×416 모델에 16:9 영상을 넣으면 **세로 182줄이 회색 패딩**이다.

```
416×416 중 실제 이미지 = 416×234 (56.25%)
                패딩 = 416×182 (43.75%)   ← 이 영역을 YOLO가 전부 연산한다
```

**YOLO를 회색 여백에 대해 43% 돌리고 있다.** 그리고 이 낭비율은 카메라 종횡비마다 다르다. 4:3 카메라면 25%, 세로 설치라면 다시 43%다.

**매장 종횡비는 확정할 수 없다.** USB 웹캠은 대개 16:9지만 저가 CCTV·산업용 카메라는 4:3이나 5:4가 흔하고, 좁고 긴 매장이나 출입구 전용 카메라는 세로 설치가 합리적이다. 하나의 고정 종횡비를 전제하면 안 된다.

### 해결: 모델을 종횡비별로 미리 export해 두고 실행 시 하나만 로드한다

디스크에 있지만 로드하지 않는 ONNX 파일은 **비용이 정확히 0이다.** 세션을 만들지 않으면 파싱도, 가중치 할당도, 스레드 생성도 없다. 프로세스 메모리에 아무 흔적이 없다.

### 먼저 정정 — 재학습은 필요 없다

여러 모델을 준비한다고 해서 여러 번 학습할 필요가 없다. **학습된 가중치 하나에서 `imgsz`만 바꿔 export만 반복하면 된다.**

| | 필요 여부 | 이유 |
|---|---|---|
| 재학습 | **불필요** | Conv/C2f는 해상도 불변. 같은 가중치가 임의 입력 크기에서 동작한다 |
| 앵커 재계산 | **불필요** | YOLO11은 anchor-free다 |
| export | 필요 | 형상당 수 초 |
| INT8 재양자화 | 필요 | 형상당 수 분 (캘리브레이션 데이터셋 재사용) |

```python
# scripts/export_shapes.py — 가중치는 하나, 형상만 바꿔 반복 export
for (w, h) in SHAPES:
    YOLO("yolo11n.pt").export(format="onnx", imgsz=(h, w), simplify=True)
```

즉 **"모델을 여러 개 학습해야 한다"는 비용은 실제로 발생하지 않는다.** export 스크립트를 한 번 돌리는 것이 전부다.

한 가지 유의점: COCO 사전학습 가중치는 640으로 학습되어 있어 416/320 추론은 이미 스케일 불일치가 있다. **다만 이것은 현재도 동일한 상태**이며, 직사각형으로 바꾼다고 새로 생기는 문제가 아니다. 오히려 패딩이 줄어 입력 분포가 학습 시와 가까워진다. 파일럿에서 검출률이 부족하면 그때 해당 형상으로 fine-tune 하되, 그것은 별개 과제다.

### 형상 결정 규칙

긴 변을 티어로 고정하고, 짧은 변은 종횡비로 계산해 **32의 배수로 올림**한다.

```
short = ceil_to_32(long / aspect)
```

**올림이어야 하는 이유**: 내림하면 letterbox의 `scale = min(MW/W, MH/H)`에서 짧은 변이 병목이 되어 **긴 변의 해상도까지 함께 줄어든다.** 올림하면 긴 변이 병목이 되어 해상도를 전부 살리고 짧은 변에 약간의 패딩만 남는다.

### Tier M — i5-4200U 기본 (긴 변 416)

| 종횡비 | 대표 입력 | 짧은 변 계산 | 모델 형상 | 픽셀 | vs 416² | 패딩 |
|---|---|---:|---|---:|---:|---:|
| 16:9 | 1280×720, 640×360 | 234.0 → 256 | **416×256** | 106,496 | 0.62 | 8.6% |
| 16:10 | 1280×800 | 260.0 → 288 | **416×288** | 119,808 | 0.69 | 9.7% |
| 3:2 | 1080×720 | 277.3 → 288 | **416×288** | 119,808 | 0.69 | 3.7% |
| 4:3 | 640×480, 800×600 | 312.0 → 320 | **416×320** | 133,120 | 0.77 | 2.5% |
| 5:4 | 1280×1024 | 332.8 → 352 | **416×352** | 146,432 | 0.85 | 5.4% |
| 1:1 | 어안 보정 | 416 | 416×416 | 173,056 | 1.00 | 0% |
| 9:16 (세로) | 세로 설치 | — | **256×416** | 106,496 | 0.62 | 8.6% |

**16:10과 3:2가 같은 형상(416×288)으로 수렴한다.** 실제로 준비할 형상은 생각보다 적다.

**현실적 배포 세트: `416×256`, `416×288`, `416×320` 세 개가 카메라 대부분을 덮는다.** 세로 설치를 지원하면 전치 형상 3개를 더한다.

### Tier S — J1900 (긴 변 320)

| 종횡비 | 모델 형상 | 픽셀 | vs 416² |
|---|---|---:|---:|
| 16:9 | 320×192 | 61,440 | 0.36 |
| 16:10 / 3:2 | 320×224 | 71,680 | 0.41 |
| 4:3 | 320×256 | 81,920 | 0.47 |

### Tier L — 여유가 있을 때 (긴 변 512)

512는 특이하게도 **16:9와 4:3 모두 패딩이 정확히 0**이 되는 값이다.

```
512 × 9/16 = 288 = 9×32   ✓ 정확히 맞음
512 × 3/4  = 384 = 12×32  ✓ 정확히 맞음
```

| 종횡비 | 모델 형상 | 픽셀 | vs 416² | 패딩 |
|---|---|---:|---:|---:|
| 16:9 | 512×288 | 147,456 | 0.85 | **0%** |
| 4:3 | 512×384 | 196,608 | 1.14 | **0%** |

Tier L은 절감 티어가 아니라 **품질 티어**다. 416 대비 연산이 늘지만 유효 해상도가 23% 올라간다. Part A의 게이트로 추론 빈도가 충분히 낮아졌다면, 남는 예산을 여기에 재투자해 10m 거리 검출률을 올리는 선택지가 된다.

### C 코드는 거의 손댈 게 없다

이 방식이 싼 결정적 이유다. **엔진은 이미 임의 형상을 지원한다.**

| 확인 지점 | 상태 |
|---|---|
| `detector_ort.c:344-351` | `input_shape[2]`, `[3]`을 각각 읽어 `input_height`/`input_width`로 저장. 정사각형 가정 없음 |
| `postprocess.c:159` | `model_width`, `model_height`를 독립 인자로 받음. letterbox가 이미 비정사각형 처리 |
| `postprocess.c:368-378` | `yolo11_decode()`가 텐서 shape에서 채널/후보 수를 판별. 형상별 후보 수 변화를 자동 흡수 |

검증: 416×416의 후보 수는 52²+26²+13² = 3,549이고, 416×256은 52×32 + 26×16 + 13×8 = 2,184이다. 비율 0.62로 **연산량 감소율과 정확히 일치한다.** 후처리 비용도 같이 줄어든다. `[1,84,2184]`는 `shape[1]=84`(5~512 범위), `shape[2]=2184 > 84`이므로 기존 `channel_first` 판별 경로를 그대로 탄다.

**필요한 코드 변경은 "어느 파일을 로드할지 고르는 것"뿐이다.**

### 모델 선택 방식

기기 종횡비를 알아야 하는데, `detector_create()`는 `media_process()`보다 먼저 호출되어 프레임 크기를 아직 모른다(`main.c:988` vs `main.c:1156`). 세 가지 선택지가 있다.

| 방식 | 장점 | 단점 |
|---|---|---|
| (a) 설치 시 config에 명시 | 구현 비용 0, 시작 실패가 즉시 드러남 | 설치자가 한 줄 적어야 함 |
| (b) 입력을 미리 열어 해상도 probe | 자동 | 카메라를 두 번 여는 것이 dshow에서 불안정할 수 있음 |
| (c) 첫 프레임에서 지연 생성 | 자동, probe 불필요 | 모델 로드 실패가 시작이 아닌 스트리밍 중에 드러남. 첫 프레임 300ms 지연 |

**권장: (a) 기본 + (b) 폴백.**

매장별 설치 작업에는 어차피 ROI 설정과 문 기준 이미지 캡처가 포함된다(`2026-08-30.md` 4절). **카메라 해상도 확인은 그 절차의 자연스러운 일부**이고, 이 프로젝트는 이미 매장별 config 주입을 설계 원칙으로 삼고 있다.

```json
{
  "model": "models/yolo11n-416x256-int8.onnx",
  "model_auto": 1
}
```

`model`이 비어 있고 `model_auto = 1`이면 입력을 한 번 probe해 종횡비에 가장 가까운 형상을 고른다. 정확히 맞는 형상이 없으면 **가장 가까운 것을 고르되 반드시 로그로 알린다.**

```
model: 카메라 1280×720 (16:9) → models/yolo11n-416x256-int8.onnx 선택 (패딩 8.6%)
model: 카메라 1024×768 (4:3) → 정확히 맞는 형상 없음, 416x320 사용 (패딩 2.5%)
model: config의 model 지정이 카메라 종횡비와 불일치 — 패딩 43%, 형상 재검토 권장
```

마지막 줄이 중요하다. 설치자가 잘못된 모델을 지정하면 **조용히 느려지는 대신 로그로 드러나야 한다.** CLAUDE.md의 로깅 요구사항에 해당한다.

### 확장: 종횡비를 맞추는 것보다 좋은 선택 — 검출 영역 크롭

여기까지가 "카메라 종횡비에 모델을 맞춘다"였다. 하지만 더 나은 기준이 있다.

**맞춰야 할 것은 카메라 종횡비가 아니라 "실제로 검출이 필요한 영역"의 종횡비다.**

4:3 카메라에서 위 25%가 천장이고 아래 10%가 테이블 모서리라면, 전체 프레임을 letterbox 하는 것은 천장에 YOLO를 돌리는 것이다. 그 영역을 잘라내면 **연산이 줄면서 동시에 사람이 차지하는 유효 해상도가 올라간다.**

```
config: detect_crop = "0,120,1024,432"   (4:3 프레임에서 중앙 밴드만)
        → 크롭 종횡비 1024:432 = 2.37:1
        → 모델 416×176 선택
        → 연산 0.42×, 사람의 유효 해상도는 오히려 상승
```

**구현 비용이 거의 없다.** `letterbox_to_nchw_fast()`에 크롭된 시작 포인터와 크롭 크기를 넘기면 그만이다.

```c
/* 크롭은 별도 버퍼 복사 없이 시작 포인터 오프셋만으로 처리합니다.
 * stride는 원본 프레임 값을 그대로 유지해야 행 이동이 맞습니다.
 * rgb: Pipeline 소유 프레임 버퍼를 차용만 하며, 이 함수는 보관하지 않습니다. */
const uint8_t *crop_origin = rgb + crop_y * stride + crop_x * 3;
letterbox_to_nchw_fast(crop_origin, crop_w, crop_h, stride, ...);
```

`Letterbox` 구조체에 `offset_x`, `offset_y`를 추가하고 `map_box()`에서 마지막에 더해 주면 좌표가 원본 프레임 기준으로 돌아온다. **이것이 코드 변경의 전부다.**

크롭은 Part A의 무시 마스크(A-3의 L2)와 같은 사상이다 — 볼 필요 없는 곳을 보지 않는다. 다만 A-3은 추론 여부를 결정하고, 크롭은 추론 범위를 줄인다.

**주의**: 크롭 영역 밖은 완전히 감지 불가가 된다. 무시 마스크(변화는 감지하되 추론만 생략)와 달리 되돌릴 수 없으므로, 설치 시 화각 확인이 필수다. 대시보드에서 크롭 경계를 오버레이로 보여 줘야 한다.

### 패키징 비용

ONNX 파일 크기는 가중치가 지배하므로 **형상이 달라도 크기는 거의 같다.**

| 구성 | 개당 | 개수 | 합계 |
|---|---:|---:|---:|
| YOLO11n detection INT8 | ~3.2 MB | 3 | 9.6 MB |
| YOLO11n-pose INT8 | ~3.5 MB | 3 | 10.5 MB |
| | | | **약 20 MB** |

PC 설치본에서 20MB는 무시할 수준이다. 세로 설치·Tier S/L까지 전부 포함해도 60MB를 넘지 않는다. **런타임 비용은 0이므로 넉넉히 담아 두고 매장별로 하나만 고르는 것이 옳다.**

FP32도 함께 담으면 INT8 정확도 문제가 생겼을 때 재배포 없이 config 한 줄로 되돌릴 수 있다. 그 보험 값으로 40MB는 싸다.

**공수**: export 스크립트 0.5일 / 자동 선택 로직 0.5일 / 크롭 지원 0.5일

## B-3. 전처리 재작성 — 패딩 1회 채움 + 좌표 테이블화

`letterbox_to_nchw_fast()`(`postprocess.c:159`)의 문제 세 가지.

**(1) 매 프레임 텐서 전체를 패딩으로 채운다**

```c
for (size_t i = 0; i < total; ++i) tensor[i] = padding;   /* 2.08MB 쓰기 */
```

그런데 입력 해상도와 모델 크기는 **첫 프레임 이후 절대 변하지 않는다**(`media_ffmpeg.c:410`이 중간 해상도 변경을 명시적으로 거부한다). 패딩 영역의 위치와 값이 상수다. **최초 1회만 채우고, 이후 프레임은 이미지 영역만 덮어쓰면 된다.**

640×360 + 416×256 조합이면 패딩은 22줄뿐이라 사실상 0이 된다.

**(2) 열 좌표 계산을 매 행마다 반복한다**

```c
for (int x = 0; x < resized_width; ++x) {
    float sx = ((float)x + 0.5f) / scale - 0.5f;   /* 행마다 동일한 값 */
    int raw_x0 = (int)floorf(sx);                  /* 행마다 동일 */
    float fx = sx - floorf(sx);                    /* 행마다 동일 */
```

`sx`, `x0`, `x1`, `fx`는 **모든 행에서 같고, 모든 프레임에서도 같다.** 416개 열에 대해 234번씩 재계산하고 있다.

```c
/* 열 매핑 테이블 — 기하가 고정이므로 detector_create()에서 1회 계산합니다.
 * Detector 소유이며 detector_destroy()에서 free 합니다.
 * 프레임마다 재계산하지 않는 이유: 입력·모델 해상도가 런타임에
 * 바뀌지 않도록 media_ffmpeg.c가 보장하기 때문입니다. */
typedef struct { int x0, x1; float fx; } AxisMap;
```

`floorf` 호출이 픽셀당 2회 × 3채널에서 0회로 사라진다.

**(3) `/255.0f` 나눗셈**

```c
tensor[...] = (float)value / 255.0f;
```

부동소수 나눗셈은 Haswell에서 지연 10~14사이클, 처리율 1/4~1/8이다. `* (1.0f/255.0f)`로 바꾸면 곱셈 1회(지연 5, 처리율 1/2)가 된다. 컴파일러는 `/fp:fast` 없이는 이 변환을 하지 않는다(반올림이 달라진다).

또한 중간에 `uint8_t`로 캐스팅했다가 다시 float로 돌리는 경로가 있다:

```c
uint8_t value = (uint8_t)(top * (1.0f - fy) + bottom * fy + 0.5f);
tensor[...] = (float)value / 255.0f;
```

float→uint8→float 왕복은 정밀도만 잃고 변환 명령만 추가한다. **float으로 계속 계산해 바로 정규화**한다.

**재작성 후 내부 루프**

```c
/* 테이블 기반 bilinear — 분기·transcendental 없음, 자동 벡터화 가능 */
const float inv255 = 1.0f / 255.0f;
for (int y = 0; y < resized_height; ++y) {
    const uint8_t *r0 = rgb + ymap[y].x0 * stride;
    const uint8_t *r1 = rgb + ymap[y].x1 * stride;
    float fy = ymap[y].fx, ify = 1.0f - fy;
    float *dr = tensor + (y + pad_y) * mw + pad_x;
    float *dg = dr + plane, *db = dg + plane;
    for (int x = 0; x < resized_width; ++x) {
        int a = xmap[x].x0 * 3, b = xmap[x].x1 * 3;
        float fx = xmap[x].fx, ifx = 1.0f - fx;
        dr[x] = ((r0[a+0]*ifx + r0[b+0]*fx)*ify + (r1[a+0]*ifx + r1[b+0]*fx)*fy) * inv255;
        dg[x] = ((r0[a+1]*ifx + r0[b+1]*fx)*ify + (r1[a+1]*ifx + r1[b+1]*fx)*fy) * inv255;
        db[x] = ((r0[a+2]*ifx + r0[b+2]*fx)*ify + (r1[a+2]*ifx + r1[b+2]*fx)*fy) * inv255;
    }
}
```

**검증**: `letterbox_to_nchw()`(reference 경로)를 그대로 남겨 두고, `test_core`에서 두 경로의 출력 차이가 허용 오차 안인지 확인한다. 이 reference 함수가 존재하는 이유가 바로 이것이므로 지우면 안 된다.

**공수**: 1일 / **추정 효과**: 전처리 시간 3~5배 단축

## B-4. AVX2 SIMD 커널 — 실제로 이득이 나는 3곳만

`/arch:AVX2`가 켜져 있지만(`CMakeLists.txt:76`) 손으로 쓴 루프 대부분은 자동 벡터화되지 않는다. 분기와 스트라이드 접근 때문이다. **전부 SIMD화하지 않고, 효과가 확실한 세 곳만** 손으로 짠다.

### (a) `door.c: avg_l1()` — `_mm256_sad_epu8`

현재 555×517 = 287,000 픽셀 × 3채널에 대해 스칼라 절대차 합산(`door.c:90-110`). 이 연산은 x86에 **전용 명령이 있다**.

```c
/* _mm256_sad_epu8: 32바이트의 절대차 합을 1명령으로 계산합니다.
 * 문 상태 판정은 정확히 이 연산이므로, 스칼라 루프를 쓸 이유가 없습니다.
 * 32바이트/명령 → 스칼라 대비 약 10~20배. */
__m256i acc = _mm256_setzero_si256();
for (; i + 32 <= n; i += 32) {
    __m256i a = _mm256_loadu_si256((const __m256i *)(ref + i));
    __m256i b = _mm256_loadu_si256((const __m256i *)(cur + i));
    acc = _mm256_add_epi64(acc, _mm256_sad_epu8(a, b));
}
```

### (b) 모션 블록 차분 (A-2) — `_mm256_subs_epu8` + 비교 + popcnt

임계값 초과 픽셀 수 세기:

```c
/* |a-b| > T 를 부호 없는 포화 뺄셈 두 번으로 구합니다.
 * abs()에 분기가 없어야 벡터화가 유지됩니다. */
__m256i d  = _mm256_or_si256(_mm256_subs_epu8(a, b), _mm256_subs_epu8(b, a));
__m256i gt = _mm256_cmpgt_epi8(_mm256_xor_si256(d, sign), thr_signed);
count += _mm_popcnt_u32((uint32_t)_mm256_movemask_epi8(gt));
```

### (c) `tracker.c` SAD 패치 매칭 — 동일한 `_mm256_sad_epu8`

추적기는 **비추론 프레임마다** 돈다. A-3의 L3 경로가 활성화되면 추적기 호출 빈도가 오히려 **늘어나므로**, 여기가 새로운 핫스팟이 된다. 패치 반경 2(5×5)에 탐색 반경 3(7×7=49 위치)이라 패치당 1,225회 절대차 연산이다.

### 하지 않을 곳

`gray_buf_update()`는 **SIMD화하지 않는다.** A-1에서 함수 자체가 사라지기 때문이다. 스트라이드 gather는 Haswell에서 스칼라보다 느리므로, SIMD로 살리는 것보다 없애는 것이 맞다.

**공수**: 1.5일 (런타임 디스패치 포함, 아래 B-5 참조)

## B-5. 컴파일 플래그 — 그리고 J1900 크래시 문제

### 현재

```cmake
target_compile_options(yolo11-person PRIVATE /O2 /W4 /arch:AVX2 /utf-8)
```

### 문제: 이 바이너리는 J1900에서 즉시 죽는다

`/arch:AVX2`는 컴파일러가 **모든 부동소수 코드에 VEX 인코딩 AVX 명령을 쓰게** 한다. Celeron J1900(Bay Trail)은 **SSE4.2까지만 지원하고 AVX/AVX2가 없다.** CLAUDE.md가 차순위 배포 대상으로 명시한 기기에서 현재 Windows 빌드는 `EXCEPTION_ILLEGAL_INSTRUCTION`으로 시작하자마자 종료된다.

**해결 — 베이스라인 분리 + 런타임 디스패치**

```cmake
# 본체는 SSE2 베이스라인으로 빌드해 J1900에서도 실행됩니다.
# /arch:AVX2를 전역으로 걸면 Bay Trail에서 illegal instruction으로 죽습니다.
target_compile_options(yolo11-person PRIVATE /O2 /W4 /utf-8 /GL /Gw)

# SIMD 커널만 별도 번역 단위로 분리해 AVX2로 컴파일하고,
# __cpuid로 지원 여부를 확인한 뒤에만 호출합니다.
set_source_files_properties(src/simd_avx2.c PROPERTIES COMPILE_OPTIONS "/arch:AVX2")
```

```c
/* src/simd.c — 기동 시 1회 판별하고 함수 포인터를 고정합니다.
 * 프레임마다 cpuid를 부르지 않기 위해 포인터로 분기합니다. */
static uint64_t (*sad_u8)(const uint8_t *, const uint8_t *, size_t);

void simd_init(void) {
    if (cpu_has_avx2()) { sad_u8 = sad_u8_avx2; log("simd: AVX2"); }
    else                { sad_u8 = sad_u8_sse2; log("simd: SSE2 baseline"); }
}
```

### 추가로 켤 플래그

| 플래그 | 효과 | 주의 |
|---|---|---|
| `/GL` + `/LTCG` | 전체 프로그램 최적화. `clampf`·`sample_bilinear` 등이 TU 경계를 넘어 인라인됨 | 빌드 시간 증가 |
| `/Gw` | 미사용 전역 데이터 제거 (draw.c의 글리프 테이블 등) | 없음 |
| `/fp:fast` | 역수 곱셈·FMA 축약 허용. B-3의 `/255.0f`가 곱셈이 됨 | **전역 적용 금지** |

**`/fp:fast` 주의**: 전역으로 켜면 `letterbox_to_nchw()`(reference)와 `letterbox_to_nchw_fast()`의 수치 일치 검증이 깨질 수 있고, NMS의 IoU 비교가 미세하게 달라진다. **`postprocess.c`, `door.c`, SIMD 커널에만 파일 단위로 적용**하고 `test_core`로 허용 오차를 확인한다.

```cmake
set_source_files_properties(src/postprocess.c PROPERTIES COMPILE_OPTIONS "/fp:fast")
```

**공수**: 0.5일 (플래그) + B-4에 포함된 디스패치 1일

## B-6. 추론 엔진 설정 — INT8 / 스레드 수 / DirectML

### INT8 양자화

`scripts/quantize.py`가 이미 있다. Haswell에는 VNNI가 없지만 ONNX Runtime은 AVX2의 `vpmaddubsw`/`vpmaddwd` 경로로 u8s8 GEMM을 돌린다. **기대치 1.5~2배**(`checklist.md` 기재값과 일치).

INT8은 가중치 크기도 1/4로 줄여 **L3 압박을 직접 완화**한다. 1절의 캐시 논의를 고려하면 연산량 감소보다 이쪽 효과가 클 수 있다.

배포 기본값으로 채택하되, 파일럿에서 10m 거리 검출률을 FP32와 비교한 뒤 확정한다.

### intra-op 스레드 수

현재 기본 1(`main.c:260`), 상한 3(`main.c:349`).

2C/4T에서 HT 형제는 FMA 유닛을 공유한다. AVX2 GEMM은 이미 FMA를 포화시키므로 **HT 스레드를 추가해도 이득이 거의 없고 캐시 경합만 는다.**

```
threads = 1 : 물리 코어 1개. 디코딩·스트림과 경합 없음
threads = 2 : 물리 코어 2개.  ← 권장 시작점
threads = 3 : HT 형제 침범. 캐시 경합 + TDP 압박으로 역효과 가능
```

**권장: 2로 기본값 변경.** 단 A-3 게이트 적용 후에는 추론 빈도 자체가 낮아지므로, 1로 두고 지연을 감수하는 편이 발열 면에서 유리할 수 있다. 8절 프로토콜로 두 설정을 모두 측정한다.

`allow_spinning=0`이 이미 기본값인 것은 **이 하드웨어에서 매우 중요하고 올바른 선택**이다(`main.c:264`). 스핀 대기는 15W 예산을 아무 일도 하지 않으면서 태워 클럭을 떨어뜨린다.

### DirectML을 쓸 것인가

Windows 기본값이 DirectML이다(`main.c:266`). 그러나 `run.bat:47`은 `--provider cpu`를 명시하고 있어 **실제 배포 설정과 코드 기본값이 어긋나 있다.**

HD 4400(20 EU) 이론 성능은 CPU AVX2보다 높지만, 이 기기에서는 다음이 상쇄한다.

| 요인 | 영향 |
|---|---|
| 같은 DDR3L 버스 공유 | 1절의 대역폭 병목이 그대로 |
| 같은 15W 패키지 예산 | iGPU가 켜지면 **코어가 다운클럭** |
| 레이어당 디스패치 오버헤드 | YOLO11n처럼 작은 모델에서 비중이 큼 |
| `DisableMemPattern` 강제 | `detector_ort.c:230-235` — 메모리 재사용 최적화가 꺼짐 |
| INT8 미가속 | 코드가 이미 경고 중(`detector_ort.c:483-489`) |

**INT8을 채택하면 DirectML은 선택지에서 빠진다.** FP32로 간다면 `scripts/bench.ps1`로 양쪽을 실측해 결정하되, iGPU를 비워 두는 편이 미리보기·대시보드 렌더링에도 유리하다.

어느 쪽으로 정하든 **코드 기본값과 실행 스크립트를 일치시킨다.**

**공수**: 1일 (양자화 검증 + 벤치)

## B-8. 자잘하지만 공짜인 것들

### (a) 추론마다 도는 정렬 제거 — `detector_ort.c:574-596`

```c
double sorted[LATENCY_BUF_SIZE];              /* 스택에 2KB — L1 오염 */
memcpy(sorted, d->latency_buf, n * sizeof(double));
for (i = 1; i < n; ++i) { ... }               /* 삽입 정렬, 평균 ~16,000회 비교 */
```

**추론 1회마다 256개 원소를 복사하고 삽입 정렬한다.** p50/p95는 metrics를 쓸 때만 필요한 값이다.

→ 링 버퍼에 기록만 하고, **백분위 계산은 metrics 출력 시점 또는 10초 주기로만** 수행한다. 2KB 스택 사용도 사라진다.

### (b) `max_candidates` 1024 → 128

`main.c:258`. 7~10평 매장에서 confidence를 넘는 후보가 1024개일 일이 없다.

```
DetectionList: 1024 × 224 B = 229 KB   → L2(256KB)를 혼자 다 씀
                128 × 224 B =  29 KB   → L2에 여유롭게 상주
```

`append_candidate()`의 "가장 약한 후보 찾기" O(n) 선형 탐색도 짧아진다.

### (c) `Detection` 구조체 224바이트 문제

```c
typedef struct {
    float x1, y1, x2, y2, score;      /*  20 B */
    int keypoint_count;               /*   4 B */
    Keypoint kp[17];                  /* 204 B */   ← detection 전용 모델에선 전부 낭비
} Detection;
```

detection 전용 모델을 쓰면 **91%가 죽은 바이트**다. NMS의 `qsort`는 이 224바이트를 통째로 스왑하고, `tracks.c`의 `t->box = detections->items[j]`도 224바이트를 복사한다.

**개선**: keypoint를 별도 배열로 분리하고 `Detection`에는 인덱스만 둔다. pose 모델일 때만 그 배열을 할당한다. `Detection`이 24바이트가 되어 **캐시 라인 하나에 2.6개**가 들어간다.

## 4. 서멀 스로틀링 — 15W 기기의 숨은 병목

`회의정리노트`(7/6)의 *"4020U 모바일 CPU → 발열 해결이 중요"*, CLAUDE.md의 *"스로틀링 발생 시 프레임이 끊겨 보이는 현상"* 이 여기에 해당한다.

Haswell은 AVX2 지속 부하에서 **AVX 오프셋**을 적용해 클럭을 낮춘다. 여기에 15W 패키지 한계가 겹치면 장시간 운전 시 기본 클럭 아래로도 내려간다. **벤치마크 첫 1분의 수치는 실제 운영 성능이 아니다.**

### 완화

1. **스핀 대기 금지** — 이미 적용됨(`main.c:264`). 유지할 것.
2. **듀티 사이클링** — Part A 전체가 여기에 기여한다. 추론 빈도를 낮추면 열이 식을 시간이 생긴다.
3. **iGPU 미사용** — B-6. DirectML을 끄면 패키지 예산을 코어가 독점한다.
4. **버스트 회피** — `--warmup`으로 시작 피크를 서비스 전으로 옮기는 것은 이미 구현됨(`detector_ort.c:451-479`).

### 드라이버 없이 스로틀링을 검출하는 방법

MSR 읽기는 커널 드라이버가 필요해 배포에 부적합하다. 대신 **이미 수집 중인 지표로 추정**한다.

```
기동 후 첫 5분의 inference_p50_ms 를 기준선으로 저장
이후 10분 단위로 p50 을 비교

p50 이 기준선 대비 25% 이상 상승 + 추론 빈도는 그대로
  → 서멀 스로틀링 의심
```

```
2026-08-30T15:42:11 WARN  thermal  throttle_suspected p50=142ms baseline=98ms
  ratio=1.45 inference_rate=0.4/s uptime=3720s
```

부하가 늘지 않았는데 지연만 오르는 상황은 스로틀링 외에 설명이 어렵다. CLAUDE.md의 로깅 요구사항("문제 발생 시 스텝 단위 디버깅 없이 원인 파악")을 만족하며, 현장에서 "프레임이 끊긴다"는 신고를 받았을 때 로그 한 줄로 원인을 구분할 수 있다.

**공수**: 0.5일

## 5. 누적 효과 추정

> **다시 강조: 아래는 코드 분석 기반 추정치이며 실측이 아니다.**
> 8절 프로토콜로 각 단계마다 검증하고, 빗나가면 이 표를 갱신한다.

### 메모리 트래픽 (2절 대비)

| 단계 | 조치 | 초당 트래픽 |
|---|---|---:|
| 현재 | — | 310 MB/s |
| +A-1 | Y 평면 직접 사용 | 291 MB/s |
| +B-1 | 파이프라인 640×360 | 82 MB/s |
| +B-7 | 미리보기 OFF, 관찰자 없으면 스트림 생략 | **23 MB/s** |

**약 13배 감소.** 그리고 결정적으로 프레임 버퍼가 0.69MB가 되어 **L3 3MB 안에서 파이프라인 전체가 돈다.**

### 추론 비용

| 축 | 조치 | 배수 |
|---|---|---:|
| 1회 추론 비용 | B-2 종횡비 정합 모델 (16:9 → 416×256) | ×0.62 |
| 1회 추론 비용 | B-6 INT8 | ×0.57 |
| **추론 빈도** | **A-3 4단계 게이트** | **×0.08** |
| | **누적** | **×0.028** |

B-2의 배수는 **카메라 종횡비에 따라 달라진다** — 16:9 ×0.62, 4:3 ×0.77, 5:4 ×0.85. 위 누적치는 16:9 기준이다. 정사각형에 가까운 카메라일수록 이 항목의 이득이 작아지므로, 그런 매장에서는 검출 영역 크롭(B-2 확장)이 상대적으로 더 중요해진다.

추론 빈도 감소가 나머지 전부를 합친 것보다 크다. **이것이 "룰 우선, AI 최소" 방침이 정확도 정책인 동시에 최고의 최적화 수단인 이유다.**

### 목표 대비

`회의정리노트`(8/7)의 목표는 *"현재 사용량의 1/4 ~ 1/8"* 이다. 위 추정이 절반만 맞아도 목표를 넘긴다. **초과분은 성능 여유로 쓰지 말고 다음 두 가지에 재투자한다.**

1. **발열 여유** — 15W 기기에서 낮은 지속 부하는 클럭 안정성으로 돌아온다
2. **정확도** — 남는 예산으로 `detect_every`를 낮추거나 pose 모델을 상시화해 오탐을 줄인다

## 6. 적용 순서

각 단계는 **독립적으로 롤백 가능**하고 끝날 때 측정 가능한 결과를 남긴다.

### 1차 — 설정과 빌드만 (코드 변경 거의 없음, 0.5일)

| 조치 | 위험도 |
|---|---|
| `run.bat`/`run.ps1`에서 미리보기 기본값 OFF | 없음 |
| `--camera-size 640x480` | 없음 (ROI 재설정 필요) |
| 종횡비별 모델 세트 export 후 매장 종횡비에 맞는 것 지정 | 낮음 (정확도 비교 필요) |

| `max_candidates` 128 | 없음 |
| `/GL /Gw` 추가 | 없음 |

**측정 없이도 대부분 즉시 이득이다.** 여기서 나오는 수치가 이후 모든 비교의 기준선이 된다.

### 2차 — 추론 회피 (4일)

A-1(Y 평면) → A-2(블록 맵) → A-3(4단계 게이트)

**가장 큰 효과가 여기서 나온다.** 순서를 지킨다 — A-1이 A-2의 전제이고, A-2가 A-3의 전제다.

### 3차 — 연산 최적화 (3일)

B-1(파이프라인 해상도 + ROI 마이그레이션) → B-3(전처리 재작성) → B-8(a)(b)

### 4차 — SIMD와 플랫폼 (3일)

B-5(J1900 크래시 수정 + 런타임 디스패치) → B-4(AVX2 커널) → B-6(INT8)

**B-5의 J1900 문제는 최적화가 아니라 버그 수정이다.** 4차까지 미룰 수 없다면 1차로 당긴다.

### 5차 — 관측 (1.5일)

B-7(스트림) → 4절(스로틀링 검출)

## 7. 측정 프로토콜

추정치를 믿지 않기 위한 절차다. **모든 측정은 실제 i5-4200U 기기에서** 한다. 개발 PC 수치는 의미가 없다.

### 고정 조건

```
입력   : 동일한 녹화 파일 (실매장 10분 클립, 손님 있음/없음 구간 포함)
         카메라 실시간 입력은 프레임 드롭 때문에 비교 불가 — 반드시 파일로
반복   : 각 설정 3회, 중앙값 채택
지속   : 최소 10분 (서멀 스로틀링을 측정에 포함시키기 위해)
배경   : 대시보드 접속 있음/없음 두 조건 모두
```

### 수집 지표

| 지표 | 출처 | 왜 필요한가 |
|---|---|---|
| `machine_capacity_percent` | metrics JSON (`main.c:891`) | 목표 달성 여부의 최종 판정 |
| `cpu_ms_per_frame` | metrics JSON | 프레임당 절대 비용 |
| `inference_p50/p95_ms` | metrics JSON | **처음 1분 vs 마지막 1분 비교 → 스로틀링** |
| 단계별 시간 백분율 | **미수집 — 추가 필요** | 병목 식별 |
| `inference_runs / frames` | metrics JSON | Part A 게이트의 실제 효과 |
| `gated_frames` | metrics JSON | 게이트가 실제로 작동하는지 |

### 지금 없어서 추가해야 하는 계측

현재 metrics는 전처리/추론/후처리/추적/그리기/출력만 나눈다. **최적화 대상인 구간이 계측되지 않고 있다.**

```json
"stream_encode_seconds": 0.0,
"stream_copy_seconds":   0.0,
"gray_analyze_seconds":  0.0,
"door_check_seconds":    0.0,
"gate_l1_hits":          0,
"gate_l3_hits":          0,
"inference_skipped_by_gate": 0
```

**이 계측 추가를 1차 작업에 포함한다.** 측정할 수 없는 것은 최적화할 수 없다.

### 정확도 회귀 검증

성능 최적화가 검출을 망가뜨리지 않았는지 매 단계 확인한다.

```
동일 클립에 대해 --detections CSV 생성
기준선 대비:
  - 프레임별 person 수 차이
  - 박스 IoU 평균 (동일 프레임, 동일 순번)
  - 10m 거리 대상의 검출 누락률   ← B-2 해상도 변경의 핵심 검증 항목
```

B-2(416×256)와 B-6(INT8)은 **정확도에 영향을 줄 수 있는 유일한 항목**이다. 나머지는 수치적으로 동일한 결과를 내야 하며, 다르다면 버그다.

## 9. J1900 별도 프로파일

Celeron J1900(Bay Trail, 4C/4T, 10W, DDR3L-1333 **싱글채널**)은 i5-4200U와 다른 기기로 취급한다.

| 항목 | i5-4200U | J1900 |
|---|---|---|
| AVX2 | 있음 | **없음** (SSE4.2까지) |
| 싱글스레드 성능 | 기준 | 약 50% |
| L2 | 256KB/코어 | 1MB/2코어 공유 |
| **L3** | 3MB | **없음** |
| 메모리 | 듀얼채널 1600 | **싱글채널 1333** (대역폭 약 40%) |
| 코어 | 2C/4T | 4C/4T (HT 없음, 진짜 4코어) |

### 프로파일 차이

```
--provider cpu              (DirectML 불가 — HD Graphics(Bay Trail)는 대상 외)
모델 입력 Tier S            (16:9=320×192, 3:2/16:10=320×224, 4:3=320×256)
--camera-size 640x480
파이프라인 해상도 짧은 변 270 기준 (16:9=480×270, 4:3=360×270)
--threads 2                 (L2 공유 4코어 — 2개까지만)
INT8 필수
SSE2 베이스라인 바이너리    (B-5)
```

Tier S도 B-2와 같은 종횡비 세트를 갖는다. 파이프라인 해상도 역시 종횡비를 보존해야 하므로 고정 해상도가 아니라 **짧은 변 기준**으로 정의한다. 16:9 프레임을 4:3 크기로 억지로 맞추면 sws_scale이 늘려 버려 사람 형태가 왜곡되고 검출률이 떨어진다.

**L3가 없다는 점이 결정적이다.** 1절의 캐시 논의가 여기서는 L2 1MB 기준이 되므로, 프레임 버퍼를 480×270×3 = 389KB까지 줄여야 같은 효과를 얻는다.

반면 **진짜 4코어**라는 장점이 있어, i5-4200U에서 미루기로 한 멀티스레드 파이프라인은 J1900에서 오히려 실효가 있을 수 있다. 단 메모리 대역폭이 40% 수준이라 Part A/B의 트래픽 감소가 선행되어야 한다.

`--low-power` 플래그 하나로 위 값들을 한 번에 적용하고, 기동 로그에 적용된 프로파일을 남긴다.

```
profile: low-power (J1900) — model 320x192, pipeline 480x270, threads 2, simd SSE2
```

## 10. 요약

**이 기기에서 이겨야 할 상대는 FLOPS가 아니라 3MB L3와 15W다.**

1. **가장 큰 레버는 추론을 안 하는 것이다.** Part A의 4단계 룰 게이트가 추론 빈도를 약 1/12로 줄인다. 나머지 모든 최적화를 합친 것보다 크다.
2. **두 번째 레버는 프레임을 L3에 넣는 것이다.** 640×360으로 내리면 검출 성능 손실 없이 프레임 버퍼가 2.76MB → 0.69MB가 된다. 720p 캡처는 모델 입력 해상도에 아무것도 기여하지 않는다.
3. **세 번째는 낭비 제거다.** 같은 그레이스케일을 3번 만들고, 회색 패딩에 YOLO를 43% 돌리고, 아무도 안 보는 영상을 인코딩하고 있다.
4. **J1900에서 현재 바이너리는 실행되지 않는다.** `/arch:AVX2` 전역 적용은 최적화 이전에 버그다.
5. **모든 수치는 추정이다.** 7절 프로토콜로 실제 기기에서 검증하기 전까지는 계획일 뿐이다.
