# 로깅 v2 — 분석하기 쉬운 이벤트·성능 기록 (2026-11-07)

판정(룰·추론)은 바꾸지 않고 **기록만** 늘렸다. 같은 클립 3개에서 검출·관절·쓰러짐 추적 CSV와 룰 이벤트가 바이트 단위로 같다.

## 왜
10/06 현장 로그 분석과 이번 AI-Hub 평가에서 반복된 불편:
- 이벤트가 문자열 하나라 분석 스크립트마다 정규식으로 다시 파싱했다.
- 영상 시각이 `replay_events` 에 기록되는 일부 모듈에만 있어, 그 밖의 이벤트는 "어느 프레임인지" 몰랐다.
- 어떤 빌드·설정에서 나온 기록인지 로그만으로 알 수 없었다(시간별 파일 143개를 합칠 때 특히).
- perf 에 추론·추적 시간이 없고 `cam_fps` 가 부풀려져(30fps 카메라에서 중앙값 34.6, 최대 103) 있었다.
- 6일치를 읽으려면 매번 분석 스크립트를 돌려야 했다.

## 바뀐 것

### 1. events 테이블 — 구조화 열 6개 (`include/log.h`, `src/log.c`)
`message` 는 그대로 두고 같은 정보를 질의하기 쉬운 열로 함께 저장한다. 옛 DB 는 열 때 `ALTER TABLE ADD COLUMN` 으로 이전되고 옛 행은 NULL 이다.

| 열 | 내용 |
|---|---|
| `run` | 프로세스 시작 시각(epoch 초). 시간별 파일을 합쳐도 같은 실행임을 안다 |
| `mono`, `frame` | 이벤트가 나온 프레임의 룰 시각·번호. 프레임 밖 이벤트(시작·종료)는 NULL |
| `kind` | 메시지 첫 단어(알림 모드가 쓰는 토큰과 같음). `state=ok` 처럼 key=value 로 시작하면 module 이름 |
| `track` | 메시지의 `track=N` |
| `data` | 메시지의 `key=value` 쌍을 JSON 객체로. 숫자 뒤 단위(`s`,`ms`,`px`,`%`)는 떼고 숫자로, `3/5`·`007` 은 문자열 |

- `kind` 인덱스(`idx_events_kind`)가 있다.
- `data` 는 분석 대상 모듈(rules, door, slot_monitor, residue, surface, camera, summary, config)만 만든다 — 시작 안내문 같은 일회성 문장은 `message` 와 같은 내용을 되풀이할 뿐이다. 400바이트 상한(넘으면 남는 쌍 생략).
- 메시지를 파싱하는 방식이라 `door=on(quiet=20s` 처럼 중첩된 `=` 는 어색하게 나올 수 있다. 정확한 값이 필요하면 `message` 를 본다. 호출 지점 130여 곳을 바꾸지 않으려는 선택이다.
- `mono` 의 기준: 실시간은 단조 시계, `--video-clock` 은 영상 시간(`1000 + frame/fps`) — `replay_events.mono` 와 같다.
  **비동기 추론(`--async-infer 1`)에서는 룰이 추론한 프레임 시각으로 평가되므로 `events.mono` = 추론한 프레임, `replay_events.mono` = 결과를 반영한 프레임이다. 둘의 차이가 추론 지연이다.**

```sql
SELECT kind, count(*), count(DISTINCT track) FROM events WHERE level='WARN' GROUP BY kind ORDER BY 2 DESC;
SELECT frame, json_extract(data,'$.score') FROM events WHERE kind='person_fallen';
```

### 2. run_info 테이블 — 파일마다 실행 정보 한 행 (`src/app_logging.c`)
로그 파일(시간별 파일 포함)마다 한 행: `{"run","segment","static","effective","config"}`.
- `static`: 버전(`HUNIK_VERSION`), 빌드 시각, 실행 인수, 모델 경로·해시, 입력 크기, 스레드, provider
- `effective`: 지금 실제로 쓰는 주요 값(신뢰도 4종, detect_every(_obj), tracking, async_infer, 쓰러짐 임계값, 체류 한도, fight 사용 여부 등) — 설정 파일에 없으면 기본값이 쓰이므로 파일만으로는 알 수 없는 값
- `config`: 설정 파일에 명시된 key=value 전부. **PIN·비밀번호·토큰 계열 키는 `"***"`**. 12KB 를 넘으면 남는 키를 생략하고 `"truncated":true`
- 설정을 저장하면(핫리로드) 바뀐 키만 `module=config` 이벤트 한 건(`config_changed n=2 fall_hold_seconds=5->8 ...`, 최대 12개). 비밀 키는 값을 가린다.
- 한계: `HUNIK_VERSION` 은 CMake 캐시 값이라 개발 빌드 폴더에서는 처음 설정한 값이 남는다. 설치본(`build-installer.ps1 -Version`)은 항상 맞다.

### 3. perf 테이블 — 열 9개 추가 (`include/perf_log.h`, `src/perf_log.c`)
`pre_ms`, `inf_ms`, `post_ms`(Tier 1 전처리·추론·후처리), `t2_ms`(Tier 2), `track_ms`, `frames`, `cam_bad_s`(카메라 상태가 OK 가 아니었던 시간), `wait_frames`·`dropped`(비동기 대기·버림).
- `inf_ms / inf_runs` = 추론 1회 평균 시간. 비동기에서는 결과를 반영한 추론만 센다.
- **`cam_fps` 의 뜻이 바뀌었다**: 이제 "주기 내 처리한 프레임 수 ÷ 경과 시간"(처리 FPS)이다. 예전 값은 `1/Δt` 의 EMA 라 프레임이 몰려 오면 실제보다 크게 나왔다. 대시보드·HUD 의 FPS 도 같은 방식(1초 창)으로 바꿨다.
- 옛 perf DB 도 열 때 ALTER 로 이전된다.

### 4. 시간별 summary 이벤트 (`module=summary`)
파일 하나(보통 1시간)를 한 줄로: 로그 전환 직전에 옛 파일에, 종료 때 마지막 파일에 남긴다(`final=1`).
```
summary window=3599s final=0 alerts=12 kinds=overstay:5/2,person_fallen:1/1 cam_bad_pct=0.0 longest_track_s=1234
        cpu_med=58 cpu_max=102 fps_med=29.8 inf_runs=21600 inf_ms_avg=63.2 async_wait=0 async_drop=0 perf_rows=60
```
- `kinds` 는 `종류:건수/서로 다른 트랙 수`, 건수 많은 순 최대 10개. 알림성 이벤트(WARN 이상, rules/door/slot_monitor/residue/surface)만 센다.
- 값은 이미 쌓인 events/perf 행과 메모리 카운터에서 모은다(새 계측 없음).
- 전환 시점에 맞추려고 `LogRotation` 에 훅(`log_rotation_set_hooks`)을 뒀다 — 별도 타이머는 전환 시각과 어긋나거나 전환 실패 재시도 때 요약이 반복된다.

## 용량 (제약: 로그가 커지면 안 된다)
프레임마다 쓰는 기록은 만들지 않았다. 새 기록은 전부 저빈도다.

| 항목 | 증가분 | 근거 |
|---|---|---|
| events 구조화 열 | 이벤트당 평균 약 62B → **시간당 약 7KB** | 현장 10/06 실제 이벤트 메시지 16,994건에 같은 규칙 적용(`E:\...\field_size_estimate.py` 방식): 143.5시간에 +1.06MB |
| kind 인덱스 | 행당 약 25B → 시간당 약 3KB | 계산 |
| perf 열 9개 | 분당 1행 × 약 75B → 시간당 약 4.5KB | 계산 |
| run_info | 파일(시간)당 약 2~4KB | 설정 키 25개에서 1.6KB 실측 |
| summary | 시간당 약 0.7KB | 실측 메시지 길이 |
| **합계** | **시간당 약 15~20KB** | |

비교: 같은 현장 로그의 event DB 합계는 **1,974MB**(좌표 포함, 시간당 약 14MB) — 증가분은 **약 0.1%** 다.
용량 상한 장치는 그대로다(`log_max_total_mb`, 30일 보존, 시간별 파일·replay 128MB 상한). 새 데이터는 같은 파일에 들어가므로 별도 정리 대상이 없다.

## 하지 않은 것
- 디코드 시간 컬럼(미디어 계층이 따로 재고 있지 않다), CPU 온도(Windows 구현 없음 — 실기 확인 필요), 분석 도구 통합·대시보드 진단 탭.
- replay 좌표 저장량 절감(같은 (규칙, 트랙)의 중복 저장 제거) — 로그 용량의 대부분이 여기라 필요하면 따로.
- 실제 1시간 전환은 단위 테스트(훅)로만 확인했다. 현장에서 두 번째 파일의 `run_info`(`segment=1`)와 첫 파일 끝의 `summary` 를 확인해야 한다.
