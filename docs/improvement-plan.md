## 0. 이 문서의 목적과 원칙

`checklist.md`·`order-group-verification-design.md`·`시나리오.md`는 **무엇을 만들 것인가**를 정의한다. 이 문서는 **현재 코드에서 무엇이 실제로 동작하고 무엇이 동작하지 않는지**를 파일·라인 단위로 확인한 뒤, 남은 일정과 저사양 하드웨어 제약 안에서 **실행 가능한 순서**를 정한다.

작성 원칙은 세 가지다.

1. **모든 진단은 코드 근거를 단다.** 추측으로 과제를 만들지 않는다.
2. **새 모델을 전제하는 과제는 뒤로 민다.** 학습 데이터가 없는 항목(시럽 과다, 구토, 기물 파손)은 현재 일정에서 구현 대상이 아니다.
3. **오탐을 줄이는 일이 기능을 늘리는 일보다 우선한다.** 점주가 알림을 신뢰하지 않으면 기능 수는 의미가 없다.

## P0 — 배포 차단 항목

### P0-1. 입출력 경로 검증 (영상 외부 전송 차단)

**현상**

`--output`/`--input` 문자열은 검증 없이 `avformat_open_input()`·출력 muxer로 전달된다(`main.c:293-298`, `media_ffmpeg.c:648`). FFmpeg는 `rtmp://`, `rtsp://`, `http://`, `srt://`를 파일 경로와 동일하게 처리하므로, 실행 인자 한 줄로 매장 영상이 외부로 송출된다. CLAUDE.md의 **"영상 외부 전송 금지"** 원칙을 코드가 강제하지 않는다.

**개선안 — 2중 방어**

1차: 애플리케이션 레벨 검증 (`src/path_util.c` 신설)

```c
/* 반환 0 = 로컬 파일로 안전, -1 = 거부.
 * path: 호출자 소유 문자열, 이 함수는 읽기만 하고 보관하지 않음. */
int validate_local_path(const char *path, char *error, size_t error_size);
```

거부 규칙:

| 패턴 | 이유 |
|---|---|
| `://` 포함 | 모든 네트워크 프로토콜 |
| `\\`로 시작 (Windows UNC) | 네트워크 공유 |
| `pipe:`, `-`, `fd:` | 표준입출력 우회 |
| 확장자가 화이트리스트 밖 (`.mp4`, `.mkv`, `.avi`, `.jpg`, `.png`) | 임의 파일 덮어쓰기 방지 |

2차: FFmpeg 레벨 프로토콜 제한 (`media_ffmpeg.c`)

```c
/* 1차 검증을 통과해도 FFmpeg 내부 리다이렉트(예: concat 스크립트)로
 * 네트워크에 닿을 수 있으므로, demuxer 자체에 프로토콜 화이트리스트를 건다. */
av_dict_set(&input_options, "protocol_whitelist", "file,pipe", 0);
```

카메라 모드는 `input_format`이 지정되므로 이 검증에서 제외한다(장치명은 경로가 아님).

**검증 방법**

`tests/test_core.c`에 순수 함수 테스트 추가 — FFmpeg·ORT 불필요.

```
validate_local_path("out.mp4")            → 0
validate_local_path("rtmp://a/b")         → -1
validate_local_path("\\\\srv\\share\\a")  → -1
validate_local_path("C:\\a\\out.exe")     → -1
```

**공수**: 0.5일

### P0-2. 로컬 HTTP 서버의 메서드 검증 및 CSRF 방어

**현상**

`stream.c:271`에서 HTTP 메서드를 파싱하지만, **라우팅에는 사용하지 않는다**.

```c
sscanf(req, "%15s %255s", method, url);   /* method는 이후 어디에도 안 쓰임 */
...
} else if (strcmp(url, "/door/save") == 0) {   /* GET이든 POST든 실행됨 */
```

여기에 `Access-Control-Allow-Origin: *`가 붙어 있다(`stream.c:126`). 점주가 대시보드를 켜 둔 채 아무 웹페이지나 열면, 그 페이지의 이미지 태그 한 줄로 문 기준 이미지가 덮어써진다.

```html
<img src="http://localhost:8081/door/save?state=open">
```

`dashboard/server.c`의 `POST /api/config`(`server.c:588`)도 동일한 CORS 정책이라 설정값이 외부 페이지에서 변조될 수 있다.

바인딩 자체는 `127.0.0.1`로 제한되어 있어(`stream.c:388`) 외부 네트워크에서 직접 접근은 안 된다. 문제는 **로컬 브라우저를 경유한 요청**이다.

**개선안**

1. 상태를 바꾸는 엔드포인트(`/door/save`, `/api/config`)는 `POST`만 허용하고, 아니면 `405`를 반환한다.
2. `Access-Control-Allow-Origin`을 `*` 대신 `http://localhost:<dashboard_port>`로 고정한다.
3. 상태 변경 요청에 `Origin` 헤더를 검사해 대시보드 출처가 아니면 거부한다.
4. 기동 시 랜덤 토큰을 생성해 `data_dir`에 쓰고, 대시보드가 이를 읽어 헤더에 실어 보낸다. (로컬 파일 접근 권한 = 신뢰 경계)

1~3만 해도 브라우저 경유 공격은 막힌다. 4는 여유가 있을 때 추가한다.

**검증 방법**

`curl -X GET http://localhost:8081/door/save?state=open` → `405`
`curl -X POST -H "Origin: http://evil.example" ...` → `403`

**공수**: 0.5일

## P1 — 오탐 제거 (신뢰도 확보)

### P1-1. `unordered_seated`를 "주문 확인 필요"로 재정의

**현상**

`rules.c:187-196`의 발화 조건은 다음이 전부다.

```
track이 active AND order == TRACK_UNORDERED AND dwell > unordered_grace_seconds
```

그런데 `TRACK_ORDERED`로 전환하는 유일한 경로인 키오스크 ROI 검사(`rules.c:159`)는 `roi_kiosk_set`이 참일 때만 실행되고, **`roi_kiosk_set`에 1을 대입하는 코드가 프로젝트 어디에도 없다**. `main.c:1030-1035`는 `dwell_limit_seconds`·`unordered_grace_seconds`·`fall_hold_seconds` 세 개만 채우고, `config.c`에는 `x,y,w,h` 형태의 사각형을 파싱하는 함수 자체가 없다.

즉 현재 이 이벤트는 **"5분 이상 머문 모든 사람"** 을 뜻한다. `시나리오.md`가 명시적으로 금지한 "미주문 확정"에 해당한다.

**개선안 — 3단계**

**1단계 (0.5일): 설정 경로를 살린다.**

`config.c`에 사각형 파서를 추가한다. flat JSON 파서는 문자열 값을 지원하므로 별도 문법이 필요 없다.

```c
/* "589,203,555,517" 형식의 문자열 값을 사각형으로 읽습니다.
 * 키가 없거나 형식이 틀리면 0을 반환하고 out은 건드리지 않습니다.
 * 값 배열 대신 문자열을 쓰는 이유: 기존 flat JSON 파서가 배열을
 * 지원하지 않고, 파서를 확장하는 비용보다 문자열 파싱이 싸기 때문입니다. */
int config_rect(const Config *c, const char *key, ConfigRect *out);
```

`main.c`의 config 로드 블록과 `reload_config()` 양쪽에서 `roi_kiosk`를 읽어 `rules_cfg`에 채운다. **두 곳 모두 고쳐야 한다** — `reload_config()`는 `app->rules.config`를 복사해 시작하므로(`main.c:569`) 최초 로드에서 비어 있으면 영원히 빈 채로 남는다.

**2단계 (1일): 상태를 3단계로 확장한다.**

`시나리오.md` 2.1을 코드로 옮긴다.

```c
/* tracks.h */
typedef enum {
    ORDER_UNVERIFIED = 0,   /* 주문 근거 부족 — 기존 TRACK_UNORDERED */
    ORDER_LIKELY     = 1,   /* 키오스크 ROI 체류는 확인, 결제 미확인 */
    ORDER_CONFIRMED  = 2    /* POS 결제 이벤트와 매칭됨 */
} OrderState;
```

전환 규칙:

| 관찰 | 전이 |
|---|---|
| 키오스크 ROI에 `kiosk_dwell_seconds`(기본 8초) 이상 체류 | `UNVERIFIED → LIKELY` |
| POS 결제 이벤트 수신 + 결제 시각 ±30초에 ROI 체류 트랙 유일 | `LIKELY → CONFIRMED` |
| POS 어댑터 미연결 | `LIKELY`에서 멈춤 (알림 보류) |

`LIKELY`는 알림을 내지 않는다. 키오스크 앞을 8초 이상 서성인 사람은 최소한 주문 시도를 한 것이므로, 미주문 알림 대상에서 빼는 것이 오탐을 크게 줄인다.

**3단계 (0.5일): 이벤트 문구와 근거를 바꾼다.**

```
# 현재
unordered_seated track=1 dwell=301s grace=300s

# 개선
order_unverified track=1 dwell=301s grace=300s kiosk_visit=no
  state=UNVERIFIED confidence=low reason=no_kiosk_roi_entry
```

`시나리오.md` 7절 요구대로 **"미주문"이 아니라 "주문 확인 필요"** 로 표기하고, 판단 근거를 key=value로 남긴다. 근거가 없으면 점주는 알림을 신뢰하지 않는다.

`roi_kiosk`가 설정되지 않은 매장에서는 이 이벤트를 **아예 발화시키지 않는다.** 근거 없이 알리는 것보다 침묵이 낫다. 기동 로그에 다음을 남긴다.

```
rules: roi_kiosk 미설정 — order_unverified 이벤트 비활성화
```

### P1-2. 트랙 소멸 기준을 프레임 수에서 시간으로 변경

**현상**

`main.c:1054`에서 `max_misses = 5`로 초기화하고, `tracks.c:92-93`이 이를 **연속 미매칭 횟수**로 쓴다. 그런데 `tracks_update()`는 추론이 실행된 프레임에서만 호출된다(`main.c:778`). 기본 설정은 `--detect-fps 10`이므로:

```
5 misses ÷ 10 회/초 = 0.5초
```

**손님이 0.5초만 기둥이나 다른 사람에 가려져도 트랙이 소멸하고, 재등장 시 새 ID로 `dwell_seconds = 0`부터 다시 센다.** 체류 시간 기반 룰(초과 체류, 주문 확인 필요) 전체가 이 값에 걸려 있다.

여기에 모션 게이트(`main.c:712-726`)가 겹치면 더 나빠진다. 매장이 조용하면 추론이 최대 `idle_refresh_seconds`(기본 10초)까지 멈추므로, 미검출 판정 간격 자체가 들쭉날쭉해진다.

**개선안**

```c
/* tracks.h — 프레임 수가 아니라 실제 경과 시간으로 소멸을 판정합니다.
 * 추론 주기(detect_every, detect_fps, 모션 게이트)가 바뀌어도
 * 체류 측정이 흔들리지 않게 하기 위한 변경입니다. */
typedef struct {
    ...
    double lost_grace_seconds;   /* 기본 3.0 — 이 시간 넘게 미매칭이면 소멸 */
} TrackList;
```

`tracks_update()`에서 `t->misses++` 대신 `now - t->last_seen > tl->lost_grace_seconds`로 판정한다. `시나리오.md` 4절의 "일시 가림 유예 10초"와 일관되게 config로 노출한다.

**추가 — 간이 트랙 승계 (0.5일)**

소멸 후 `reid_window_seconds`(기본 5초) 안에, 소멸 지점 반경 내에서 크기가 비슷한 새 detection이 나오면 기존 ID와 `dwell_seconds`를 승계한다.

```
승계 조건 (모두 만족):
  - 소멸 후 경과 < 5초
  - 중심 거리 < bbox 대각선 × 1.5
  - 면적 비 0.6 ~ 1.6
```

`order-group-verification-design.md` 3.1이 지적한 대로 이것은 **영구 신원 확인이 아니다.** 짧은 가림을 넘기기 위한 보정이며, 승계된 트랙은 이벤트 로그에 `reid=inherited`를 남겨 근거를 구분할 수 있게 한다.

**검증 방법**

`tests/test_core.c`에 합성 시나리오 추가 — 박스 시퀀스를 만들어 2초 공백 후 같은 위치 재등장 시 ID·dwell이 유지되는지 확인. FFmpeg 불필요.

**공수**: 1.5일

### P1-3. 그리디 매칭의 순서 의존성 제거

**현상**

`tracks.c:73-95`는 트랙 배열 순서대로 각 트랙이 최선의 detection을 선점한다. 두 사람이 스쳐 지나갈 때 앞 순번 트랙이 뒷사람 박스를 가져가면 **ID가 서로 뒤바뀐다.** 체류 시간이 두 사람 사이에서 섞인다.

**개선안**

전역 그리디로 바꾼다. IoU가 높은 쌍부터 순서와 무관하게 확정한다.

```
1. 모든 (track, detection) 쌍의 IoU를 계산 (최대 64 × 64 = 4096회, 부하 없음)
2. IoU 내림차순으로 정렬 대신, 최대값 선택을 매칭 수만큼 반복
3. 임계값 미만이면 중단
```

### P1-4. 쓰러짐 판정을 카메라 각도에 덜 의존하게 개선

**현상**

`rules.c:104-139`의 1차 관문은 `bbox 가로 > 세로 × 1.8`이다. 이 조건은 다음 두 상황에서 틀린다.

| 상황 | 결과 |
|---|---|
| 카메라를 향해 머리를 두고 누움 | bbox가 세로로 길어 **미검출** |
| 천장 근접 설치로 내려다보는 화각 | 서 있는 사람도 가로가 길어 **오검출** |

keypoint가 있어도 y 표준편차만 보므로(`rules.c:134-138`) 화면 좌표계 기준 판정에서 벗어나지 못한다.

**개선안**

bbox 비율을 1차 필터로만 쓰고, **몸통 축 벡터**를 주 판정으로 삼는다.

```
어깨 중점 = (kp[5] + kp[6]) / 2
엉덩이 중점 = (kp[11] + kp[12]) / 2
몸통 벡터 v = 엉덩이 중점 - 어깨 중점
수직 성분 비율 = |v.y| / |v|

서 있음: 0.85 이상
누움  : 0.45 이하
```

이 값은 bbox 방향과 무관하므로 머리를 어느 쪽으로 두고 누워도 판정된다. 여기에 두 가지 가드를 더한다.

1. **바닥 ROI 교차**: `roi_floor`를 설정한 매장에서는 몸통 중점이 바닥 영역 안에 있을 때만 발화한다. 소파에 눕는 손님과 구분된다.
2. **pose 모델 필수화**: `fall_requires_pose = 1`(기본값)이면 detection 전용 모델에서는 쓰러짐 판정을 아예 하지 않는다. 현재의 `FALL_RATIO_NOKP = 2.2` 경로는 근거가 약해 오탐만 만든다.

**공수**: 1일 (합성 keypoint 테스트 포함)

### P1-5. 문 개방 감지의 조명·가림 대응

**현상 1 — 사람이 문을 가리면 개방으로 오판**

`door.c:112`는 ROI 픽셀만 비교한다. 손님이 문 앞에 서면 ROI가 닫힘 기준과 크게 달라지므로 "열림 기준에 더 가깝다"는 판정이 나올 수 있다. `door_confirm_frames = 5`(약 0.33초)로는 걸러지지 않는다. 문 앞에 서서 통화하는 손님 한 명이 `door_open` 경고를 만든다.

**현상 2 — 조명 변화에 취약**

`avg_l1()`(`door.c:90`)은 절대 밝기 차이의 평균이다. 낮/밤, 조명 점등, 카메라 자동 노출로 전체 밝기가 변하면 두 기준 이미지 모두에서 멀어지고, 어느 쪽이 가까운지는 사실상 우연이 된다.

**개선안**

1. **사람 가림 시 판정 보류**
   현재 프레임의 person detection 중 하나라도 문 ROI와 `occlusion_ratio`(기본 0.25) 이상 겹치면 `door_check()`를 건너뛰고 직전 상태를 유지한다. 이벤트 로그에 `door: occluded, hold` 를 남긴다. detection 결과는 이미 `app->detections`에 있으므로 추가 연산이 없다.

2. **조명 불변 지표로 교체**
   L1 거리 대신 ROI 내 **정규화 상호상관(ZNCC)** 을 쓴다. 평균과 표준편차를 제거하므로 전역 밝기·대비 변화에 강하다.

   ```
   ZNCC = Σ((a - mean_a)(b - mean_b)) / (N × std_a × std_b)
   state = ZNCC(현재, 열림기준) > ZNCC(현재, 닫힘기준) ? 열림 : 닫힘
   ```

   ROI 크기가 555×517이면 약 28만 픽셀 × 2회. 매 프레임 수행하면 부담되므로 **문 감지도 추론 주기에 맞춰 실행한다**(초당 10회면 충분하다 — 문은 30fps로 볼 대상이 아니다).

3. **기준 이미지 유효성 경고**
   기준 이미지 캡처 시각과 현재 시각의 조명 조건이 크게 다르면(전체 평균 luma가 ±30 이상 차이) 대시보드에 재캡처를 권고한다. 시간대별로 기준 이미지를 2세트(주간/야간) 두는 것도 가능하나, 1단계에서는 경고만 한다.

**공수**: 1.5일

### P1-6. 카메라 장애 판정을 절대값에서 상대값으로

**현상**

`config.json`의 `luma_black_threshold`가 `40 → 10`으로 낮춰져 있다. 문을 연 어두운 출입구가 blackout으로 오탐되어 임계값을 내린 결과다(`2026-08-30.md` 6절). 그런데 10까지 내리면 **렌즈가 실제로 가려져도 알림이 안 나온다.** 오탐을 줄이려다 감지 자체를 껐다.

**개선안 — 캘리브레이션 기반 상대 판정**

기동 후 `calibration_seconds`(기본 60초) 동안 정상 프레임의 평균 luma와 표준편차를 수집해 `data_dir/camera_baseline.json`에 저장한다.

```json
{
  "luma_mean": 118.4,
  "luma_stddev": 21.7,
  "captured_at": "2026-08-30T09:12:00+09:00"
}
```

판정을 절대 임계값이 아니라 기준선 대비로 바꾼다.

```
blackout : luma_mean_now < baseline.mean - 3.5 × baseline.stddev
whiteout : luma_mean_now > baseline.mean + 3.5 × baseline.stddev
```

매장마다 조명이 다른 문제를 설정 파일 손대기 없이 흡수한다. `회의정리노트`(8/3) 및 `checklist.md` 장기 목표의 "캘리브레이션" 항목을 가장 싼 형태로 먼저 실현하는 것이기도 하다.

기준선 파일이 없으면 현재 절대 임계값 방식으로 폴백한다. 조명 정책이 바뀐 매장은 대시보드에서 재캘리브레이션 버튼을 누르면 된다.

**공수**: 1일

### P2-1. MJPEG 스트림의 중복 인코딩·복사 제거 (효과 최대, 비용 최소)

**현상**

`main.c:798`이 **매 프레임** `stream_push()`를 호출한다. 그 안에서 전체 RGB를 통째로 복사한다(`stream.c:421`).

```
1280 × 720 × 3 = 2.76 MB/frame
30 fps × 2.76 MB = 82 MB/s  ← 순수 메모리 대역폭
```

여기서 끝이 아니다. `encode_jpeg()`(`stream.c:77`)는 락 안에서 **또 한 번 전체 프레임을 malloc + memcpy** 하고, 그 다음 JPEG 인코딩을 한다. 그리고 이 함수는 **클라이언트 스레드마다 개별 호출된다**(`stream.c:307`). 브라우저 탭 2개를 열면 같은 프레임을 2번 인코딩한다.

DDR3L 대역폭을 공유하는 저전력 CPU에서 이 낭비는 그대로 추론 성능을 깎는다.

**개선안**

| 조치 | 기대 효과 |
|---|---|
| `stream_push()`에 `STREAM_FPS`(10) 기준 시간 게이트 추가 — 100ms 안에 들어온 프레임은 버림 | 복사량 82 → 27 MB/s (**-67%**) |
| `encode_jpeg()`의 임시 버퍼를 매번 malloc 하지 말고 고정 버퍼 재사용 | 프레임당 malloc/free 1회 제거 |
| 시퀀스 번호별로 JPEG을 **1회만 인코딩**해 캐시하고, 모든 클라이언트가 공유 | 클라이언트 N명일 때 인코딩 N회 → 1회 |
| 클라이언트가 0명이면 인코딩·복사 전체를 건너뜀 | 평상시(대시보드 미접속) 스트림 비용 0 |

마지막 항목이 특히 크다. 점주가 대시보드를 항상 열어 두지는 않는다. **아무도 보지 않는 영상을 계속 인코딩하는 것이 현재 구조다.**

CLAUDE.md의 "모든 버퍼는 시작 시 한 번만 할당" 원칙에도 `stream.c`가 유일하게 어긋나 있다.

**공수**: 0.5일 / **예상 효과: 전체 CPU의 8~15%p 절감**

### P2-3. 그레이스케일 순회 통합 및 중복 버퍼 제거

**현상**

같은 gray 버퍼를 **매 프레임 3번 순회**하고, **이전 프레임 사본을 2벌 유지**한다.

| 위치 | 작업 | 이전 프레임 버퍼 |
|---|---|---|
| `camera_health.c:66` | 평균 luma 합산 | — |
| `camera_health.c:71` | 변화 픽셀 수 (freeze 감지) | `h->prev_gray` |
| `main.c:716` | 변화 픽셀 수 (모션 게이트) | `app->gray_prev` |

`gray_prev`와 `h->prev_gray`는 **같은 시점의 같은 데이터**다(`main.c:852` vs `camera_health.c:78`). 임계값만 다르다(모션 게이트 8, 헬스 12).

**개선안**

단일 패스로 통합한다.

```c
/* 한 번의 순회에서 세 통계를 모두 냅니다.
 * gray는 4배 다운샘플이라 절대 연산량은 작지만, 프레임마다 같은
 * 메모리를 3번 읽는 것은 DDR3L 대역폭이 병목인 기기에서 낭비입니다. */
typedef struct {
    unsigned long luma_sum;
    size_t changed_motion;   /* diff > 8 */
    size_t changed_health;   /* diff > 12 */
} GrayStats;

void gray_analyze(const GrayBuf *cur, const uint8_t *prev, GrayStats *out);
```

`camera_health`의 `prev_gray`를 제거하고 `app->gray_prev` 하나만 남긴다.
**소유권**: `gray_prev`는 `AppContext`가 소유하고 `main()`의 `done:` 라벨에서 `free()`한다. `camera_health`는 읽기만 하는 차용 포인터로 받는다.

**공수**: 0.5일 / **예상 효과: 2~4%p, 메모리 -57KB**

### P2-4. 모션 게이트가 사람이 있을 때 오작동하지 않도록

**현상**

`main.c:712-726`의 모션 게이트는 화면 전체 변화율만 본다. 손님이 앉아서 폰을 보고 있으면 변화율이 임계값 아래로 떨어져 **추론이 `idle_refresh_seconds`(10초)까지 멈춘다.** 그 사이 트랙 매칭이 끊기거나(P1-2와 결합해 악화), 쓰러짐 판정이 최대 10초 늦어진다.

반대로 매장이 정말 비었을 때는 게이트가 잘 작동한다. 문제는 **"사람이 있는데 안 움직이는 상태"** 를 "빈 매장"과 구분하지 못하는 것이다.

**개선안 — 상태별 2단 게이트**

```
active 트랙 수 == 0  (빈 매장)
  → 현재 동작 유지. 변화율 미달이면 최대 10초까지 추론 생략.

active 트랙 수 > 0   (사람 있음)
  → 추론을 끊지 않되 주기를 늘린다. detect_fps를 10 → 2로 낮춘다.
     체류·쓰러짐 판정에 필요한 최소 갱신은 보장된다.
```

`tiered-inference.md`의 Tier 0/Tier 1 구분을 "사람 유무"라는 실제로 확보 가능한 신호로 구현한 것이다.

**공수**: 0.5일 / **예상 효과: 빈 매장 시 절감은 유지하면서 P1-2의 정확도 문제 동시 해결**

### P2-5. 멀티스레드 파이프라인 (마지막에 한다)

**현상**

디코딩 → 전처리 → 추론 → 후처리 → 룰 → 그리기 → JPEG → 출력이 전부 `process_frame()` 한 콜백 안에서 직렬 실행된다(`main.c:613-859`).

**개선안 — 2스레드 분리부터**

`TODO.md`는 3스레드 안을 제시하지만, **먼저 2스레드로 나눈다.** 이유는 다음과 같다.

- 3스레드 안(디코딩 / 추론 / 출력)은 스레드 간 버퍼가 2개 필요하고 동기화 지점이 2곳이다.
- 2코어 4스레드 기기에서 스레드 3개 + OS는 컨텍스트 스위칭 손실이 커진다.
- **P2-1~P2-4를 먼저 적용하면 목표 절감분의 상당 부분이 확보된다.** 멀티스레드는 남은 격차를 메우는 수단이지 첫 수단이 아니다.

```
Thread A (생산): FFmpeg 디코딩 + gray 통계 + 카메라 헬스
                  ↓ 링 버퍼 2슬롯 (ping-pong)
Thread B (소비): YOLO 추론 + tracks + rules + 그리기 + 스트림 push
```

동기화는 슬롯 2개짜리 링 버퍼 + 조건 변수 1쌍으로 한정한다. `회의정리노트`(7/10)에서 논의한 "이벤트 방식"에 해당하며, 세마포어보다 상태가 단순해 디버깅이 쉽다.

**선행 조건**: P2-1~P2-4 적용 후 실측. 목표 미달분이 20%p 이상일 때만 착수한다.

**공수**: 3일 (ASan/TSan 검증 포함)

### P2-6. 계측 정합성 수정

**현상 (경미하나 혼란을 만듦)**

`main.c:71-73`의 주석은 `detect_fps_limit`이 `detect_every`와 **OR** 조건이라고 적혀 있으나, 실제 코드(`main.c:669-672`)는 **AND**다. 두 조건 모두 통과해야 추론한다. 성능 튜닝 시 잘못된 예측으로 이어진다.

**개선안**

- 주석을 코드에 맞춰 AND로 수정한다.
- metrics JSON에 `stream_encode_seconds`, `stream_copy_seconds`, `gray_analyze_seconds`, `door_check_seconds`를 추가한다.
- 각 단계의 `wall_seconds` 대비 백분율을 함께 기록해 사람이 바로 병목을 읽을 수 있게 한다.

## P3 — 그룹·테이블 단위 판정 (설계 문서의 코드화)

> `order-group-verification-design.md`와 `시나리오.md`는 완성도가 높다.
> 문제는 **한 번에 다 구현하려면 POS 연동과 컵·트레이 검출 모델이 동시에 필요하다**는 점이다.
> 둘 다 현재 없다. 따라서 **없어도 되는 부분부터** 쪼갠다.

### P3-1. 다중 ROI 인프라 (모든 후속 기능의 전제)

현재 ROI는 문(`door_roi_*`) 하나뿐이고 그마저 개별 키 4개로 흩어져 있다. 테이블·키오스크·바닥·의자 ROI를 각각 4키씩 늘리면 config가 감당이 안 된다.

**설계**

```json
{
  "roi_kiosk":   "820,120,300,420",
  "roi_door":    "589,203,555,517",
  "roi_floor":   "0,400,1280,320",
  "roi_table_1": "T-01,120,380,260,200",
  "roi_table_2": "T-03,640,380,300,220"
}
```

```c
/* include/roi.h
 * 사각형 ROI 목록. 폴리곤은 지원하지 않습니다 —
 * 매장 테이블은 대부분 사각형이고, 폴리곤 교차 판정 비용을 지불할
 * 만큼의 정확도 이득이 없기 때문입니다. 필요해지면 그때 확장합니다. */
typedef struct {
    char  name[16];        /* "T-01" 등 표시용 이름 */
    float x, y, w, h;
} Roi;

typedef struct {
    Roi   *items;          /* RoiSet 소유, roi_set_destroy 에서 free */
    size_t count;
    size_t capacity;
} RoiSet;

int  roi_set_load(RoiSet *set, const Config *cfg, const char *prefix,
                  char *error, size_t error_size);
void roi_set_destroy(RoiSet *set);

/* box 중심이 어느 ROI 안에 있는지 반환. 없으면 -1.
 * 반환값은 set->items 의 인덱스이며, set 이 살아 있는 동안만 유효합니다. */
int  roi_set_find(const RoiSet *set, const Detection *box);
```

**공수**: 1일

### P3-2. 테이블별 인원 카운트 — 알림 없이 관측만

`order-group-verification-design.md` 11절 **1단계**를 그대로 따른다. 자동 알림을 내지 않고 관측 데이터만 쌓는다.

```
매 추론 주기:
  각 active 트랙의 bbox 중심이 어느 테이블 ROI에 속하는지 판정
  테이블별 인원 수를 갱신
  변화 시 이벤트 로그에 기록
```

```
2026-08-30T14:30:12 INFO  table    T-03 occupancy=3 tracks=4,7,9
2026-08-30T14:45:31 INFO  table    T-03 occupancy=0 vacated_after=920s
```

이 단계에서 얻는 것:

- 테이블 ROI 설정이 화각상 실제로 가능한지 검증된다 (`시나리오.md` 6절의 가시성 등급 A~D 판정 근거)
- POS 연동 전에 **인원 수 측정 오차**를 실측할 수 있다 (`order-group-verification-design.md` 12절 검증 지표)
- 인원 초과 감지(`checklist.md` 중기 목표)가 부수적으로 완성된다 — `max_occupancy` 비교 한 줄

**공수**: 1일

### P3-3. POS 어댑터 인터페이스 — 구현체는 나중

주문 데이터 원본(DB / 로그 / API)이 아직 정해지지 않았다(`order-group-verification-design.md` 13절 미결 항목). 원본이 정해질 때까지 detector 쪽 작업이 멈추지 않도록 **경계면만 먼저 고정**한다.

```c
/* include/order_source.h
 *
 * detector는 주문 데이터의 출처를 모릅니다. 파일 감시든 DB 폴링이든
 * 소켓 수신이든, 이 구조체 하나로만 접근합니다.
 * 키오스크 SW를 수정하지 않는다는 전제(설계 문서 2절)를 지키려면
 * 원본이 바뀌어도 detector 본체가 흔들리지 않아야 합니다. */
typedef struct {
    char   event_id[40];   /* 중복 수신 방지 키 */
    char   order_id[32];
    double paid_at;        /* platform_monotonic_seconds() 기준으로 변환된 값 */
    int    cover_count;    /* 주문 커버 인원 수 */
    int    is_takeout;     /* -1 = 불명 */
    int    is_refund;      /* 취소·환불이면 1 */
} OrderEvent;

/* 새 주문 이벤트를 폴링합니다. 0 = 없음, 1 = out 채움, -1 = 오류.
 * out은 호출자 스택 메모리이며 이 함수는 보관하지 않습니다. */
int order_source_poll(OrderSource *src, OrderEvent *out,
                      char *error, size_t error_size);
```

**첫 구현체는 파일 감시**로 한다. 원본이 무엇으로 정해지든, 중간에 JSON Lines 파일을 떨구는 어댑터를 두면 detector는 바뀌지 않는다.

```
data_dir/orders.jsonl 에 한 줄씩 append
{"event_id":"...","order_id":"A20260830-1042","paid_at":"...","cover_count":4}
```

파일 크기가 아니라 **읽은 오프셋**을 기억해 증분만 파싱한다. 중복은 `event_id`로 거른다.

이 단계까지 오면 P1-1의 `LIKELY → CONFIRMED` 전이가 살아난다.

**공수**: 1.5일 (인터페이스 + 파일 어댑터)

### P3-4. 하지 않을 것 (명시적 비목표)

다음은 **이번 사이클에서 구현하지 않는다.** 이유를 남겨 두어야 나중에 다시 논의하지 않는다.

| 항목 | 하지 않는 이유 |
|---|---|
| 컵·트레이 검출 | COCO `cup` 클래스의 실제 매장 검출률을 아직 측정하지 않았다. 측정 없이 점수 공식(설계 문서 7.2)을 넣으면 근거 없는 숫자만 늘어난다 |
| 주문 크레딧 자동 배정 | P3-2의 인원 수 오차와 P3-3의 주문 데이터 정확도를 먼저 실측해야 한다. 두 입력이 모두 불확실한 상태에서 배정 알고리즘을 만들면 검증이 불가능하다 |
| 시럽 과다 / 구토 / 기물 파손 | 학습 데이터가 없다. `checklist.md`에 남겨 두되 일정에 넣지 않는다 |
| 노키즈존 나이 추정 | 개인정보 처리방침 검토(`회의정리노트` 7/6 액션 아이템)가 선행되어야 한다. 얼굴 데이터를 다루는 순간 ISMS 요건이 달라진다 |
| 3스레드 파이프라인 | P2-1~P2-4 실측 후 격차가 남을 때만 (P2-5 참조) |

## 3. 실행 순서

각 단계가 끝날 때 **측정 가능한 결과물**이 남도록 배치했다.

### 1주차 — 설치 가능 상태 만들기

| 과제 | 공수 |
|---|---|
| P0-1 경로 검증 | 0.5일 |
| P0-2 HTTP 메서드·CSRF | 0.5일 |
| P2-1 스트림 인코딩 최적화 | 0.5일 |
| P2-2 출력 없으면 그리기 생략 | 0.5일 |
| P2-3 gray 단일 패스 | 0.5일 |
| P2-6 계측 정합성 | 0.5일 |

**완료 기준**: `rtmp://` 출력이 거부된다. 대시보드 미접속 상태에서 metrics JSON의 `machine_capacity_percent`가 이전 대비 **25% 이상 감소**한다.

### 2주차 — 오탐 제거

| 과제 | 공수 |
|---|---|
| P1-2 시간 기반 트랙 소멸 + 간이 승계 | 1.5일 |
| P1-3 전역 그리디 매칭 | 0.5일 |
| P1-1 주문 상태 3단계 + roi_kiosk 살리기 | 2일 |
| P2-4 상태별 2단 모션 게이트 | 0.5일 |

**완료 기준**: 30분 실매장 영상에서 동일인의 트랙 ID 변경 횟수가 이전 대비 절반 이하. `roi_kiosk` 미설정 매장에서 `order_unverified` 이벤트가 0건.

### 3주차 — 환경 적응

| 과제 | 공수 |
|---|---|
| P1-5 문 감지 가림·조명 대응 | 1.5일 |
| P1-6 카메라 헬스 캘리브레이션 | 1일 |
| P1-4 쓰러짐 몸통 축 판정 | 1일 |

**완료 기준**: 문 앞 3초 이상 체류 상황에서 `door_open` 오탐 0건. `luma_black_threshold`를 손대지 않고도 야간 오탐이 없다.

### 4주차 이후 — 그룹 판정 기반

| 과제 | 공수 |
|---|---|
| P3-1 다중 ROI 인프라 | 1일 |
| P3-2 테이블 인원 카운트 (관측 전용) | 1일 |
| P3-3 POS 어댑터 인터페이스 + 파일 구현 | 1.5일 |

**완료 기준**: 하루치 로그에서 테이블별 인원 수와 실제 방문 기록의 오차율을 산출할 수 있다.

## 4. 측정 지표

개선 여부를 주장하려면 숫자가 있어야 한다. 각 지표의 수집 위치를 함께 정한다.

### 리소스

| 지표 | 현재 수집 여부 | 목표 |
|---|---|---|
| `machine_capacity_percent` | 수집 중 (`main.c:890`) | 현재 값의 1/4 이하 |
| `inference_p95_ms` | 수집 중 | 카메라 FPS 대비 여유 확보 |
| 단계별 시간 백분율 | **미수집** → P2-6에서 추가 | 병목 단계 식별 가능 |
| 유휴 시(빈 매장) CPU | **미수집** | 5% 미만 |

### 정확도

| 지표 | 수집 방법 | 목표 |
|---|---|---|
| 트랙 ID 변경 횟수 / 인분 | `--detections` CSV 사후 분석 | 개선 전 대비 -50% |
| `door_open` 오탐 건수 | 이벤트 로그 + 영상 대조 | 0건 (사람 가림 시나리오) |
| 카메라 헬스 오탐 | 이벤트 로그 야간 구간 | 0건 |
| 테이블 인원 수 오차 | P3-2 로그 vs 육안 카운트 | ±1명 이내 |

### 검증 자산

현재 테스트는 `test_core`(단위) / `test_detector`(ONNX 통합) 2개다. 다음을 추가한다.

- **합성 트랙 시퀀스**: 박스 좌표 배열을 입력해 트랙 ID·dwell 동작을 검증. FFmpeg·ORT 불필요하므로 CI에서 항상 돈다.
- **기준 영상 세트**: 매장에서 촬영한 짧은 클립(문 앞 체류 / 두 사람 교차 / 야간 / 쓰러짐 재현)을 고정해 두고, 변경 전후 이벤트 로그를 diff한다. `시나리오.md` 8절의 "운영 전 검증" 체크리스트를 이 세트로 자동화한다.

## 5. 코드 작성 시 지킬 것

CLAUDE.md 규칙을 이번 작업 범위에 맞춰 구체화한다.

**포인터 주석**: 새로 추가하는 `RoiSet`, `OrderSource`, `GrayStats`는 모두 소유권·수명·해제 책임을 헤더에 명시한다. 특히 P2-3에서 `camera_health`가 `gray_prev`를 **차용**하도록 바뀌므로, 이 변경은 주석에 반드시 남긴다 — 해제 책임이 이동하는 변경은 나중에 이중 free를 만든다.

**사유 명시**: 이 문서에서 "왜 A 대신 B인가"를 적은 항목(폴리곤 대신 사각형 ROI, 헝가리안 대신 전역 그리디, 3스레드 대신 2스레드, L1 대신 ZNCC)은 구현 시 해당 코드 위에 같은 근거를 옮겨 적는다.

**로깅**: 새 기능은 정상/비정상 상태를 구분하는 로그를 함께 만든다. 특히 **기능이 조용히 비활성화되는 경우**를 반드시 로그로 남긴다. `roi_kiosk`가 설정되지 않아 주문 판정이 죽어 있던 이번 문제가 정확히 그 사례다 — 코드는 정상 동작했지만 아무도 그것이 꺼져 있다는 것을 몰랐다.

```
rules:  roi_kiosk 미설정 — order_unverified 이벤트 비활성화
door:   기준 이미지 없음 — 문 감지 비활성화
camera: baseline 없음 — 절대 임계값 모드로 폴백
order:  orders.jsonl 없음 — 주문 확정(CONFIRMED) 전이 비활성화
```

기동 시 이 로그들을 한 블록으로 모아 출력하면, 현장에서 "왜 이 기능이 안 되죠"라는 질문에 로그 한 장으로 답할 수 있다.
