# 구현 현실성 및 개선 사항 검토

검토일: 2026-09-10

## 결론과 검토 범위

현재 시스템은 **이상 상황 후보를 찾아 점주에게 알려주는 보조 시스템으로는 현실적인 구조**다. 다만 무인 매장의 위반·응급상황을 자동 확정하는 수준으로 보기는 어렵다. 모델 정확도 이전에 수정해야 할 실행 로직 문제도 있다.

검토 당시 작업 폴더의 미커밋 수정 사항까지 포함해 코드를 확인했다. 검토 과정에서 구현 코드는 변경하지 않았다. 테스트를 빌드하고 단위 테스트 66개 통과를 확인했다. 실제 i5-4200U에서의 성능이나 매장 영상 기준 정확도를 실측한 결과는 아니다.

아래 소스 링크의 줄 번호는 검토 시점 기준이며, 이후 수정에 따라 달라질 수 있다.

## 기능별 현실성

| 장기 체류 | 조건부 가능 | 사람 ID가 안정적으로 유지되어야 함 |

## 우선 개선 사항

### 1. 현재 실행 설정에서 Tier 2 물체 감지가 실행되지 않음

[src/main.c](../src/main.c)의 Tier 2 실행 조건(검토 시점 1342행)은 사람 감지 주기 5, 물체 감지 주기 90에서 다음과 같다.

```c
(frame_index + 45) % 90 == 0
&& frame_index % 5 != 0
```

앞 조건에 해당하는 45, 135, 225…는 모두 5의 배수여서 뒤 조건을 통과하지 못한다. 현재 [run.bat](../run.bat)의 주기 5와 물체 감지 기본 주기 90에서 성립하는 문제다. 0~899프레임에 대해 조건을 계산했을 때 실행 가능 프레임은 0개였다.

또한 Tier 2 호출 자체가 `if (run_detector)` 안에 있어, 주기만 변경해도 사람 감지 실행에 종속된다. 이 문제는 물체 룰뿐 아니라 물체 감지 결과의 가구 박스를 사용하는 후속 기능에도 영향을 준다.

**개선 방향**

- Tier 2 스케줄을 사람 감지 분기 밖으로 옮긴다.
- 마지막 실행 시각을 기준으로 실행을 예약한다.
- 개별 룰 테스트 외에, 설정된 시간 안에 실제 물체 추론이 호출되는지 검사하는 통합 테스트를 추가한다.

### 2. 주문·외부 반입 판단이 실제 관측 정보보다 강함

[src/rules.c](../src/rules.c)의 키오스크 처리(324행)는 키오스크 영역에 사람 중심점이 들어오면 주문 완료로 처리한다. 메뉴만 보고 돌아가도 주문자로 기록될 수 있다. `unordered_seated`에는 실제 착석 확인 조건도 없다.

또한 병이 보이면 `external_drink`, 사람 수가 컵 수와 여유값의 합보다 많으면 `no_cup_seated`를 발생시킨다. 매장 판매 병, 컵 가림, 주문 대기자도 영향을 준다.

**개선 방향**

- 결제 연동 전에는 “주문 미확인”, “병 감지”, “컵 수 부족 의심”처럼 관측 수준에 맞게 표시한다.
- 실제 위반 판정에는 결제 시각·수량, 테이블별 인원, 주문 대기 유예를 연결한다.
- 물체 종류와 매장 외부에서 반입되었다는 사실을 구분한다.

### 3. 추적 실패 후 오래된 사람 정보가 너무 오래 유지될 수 있음

[src/tracks.c](../src/tracks.c)의 추적 실패 처리(206행)는 실패를 횟수로 세며, 현재 초기 설정은 `max_misses=150`이다. 이 횟수는 카메라 프레임마다가 아니라 사람 추론 실행 때 증가한다.

추론이 초당 3회라면 비활성화까지 약 50초, 정적 장면에서 10초마다 실행된다면 약 25분이 걸릴 수 있다. 이는 해당 추론 간격이 유지된다는 가정에 따른 계산이며 실측치는 아니다. 그동안 예전 박스가 인원 집계·잔류물 제외 영역·쓰러짐 판정에 사용된다.

**개선 방향**

- `last_seen` 기준의 초 단위 만료를 적용한다.
- “현재 관측됨 / 일시적으로 놓침 / 퇴장 추정” 상태를 나눈다.
- 관측이 오래된 트랙은 인원·잔류물·쓰러짐 판정에서 다르게 취급한다.
- 색상 히스토그램 재식별에는 위치와 이동 이력도 함께 사용한다. 같은 옷 색의 다른 사람에게 체류·주문 상태가 전달될 수 있기 때문이다.

낮은 신뢰도 검출까지 연결하는 방식은 [ByteTrack 원 논문](https://arxiv.org/abs/2110.06864)을 참고할 수 있다. 도입 효과는 매장 영상에서 별도 검증해야 한다.

### 4. 쓰러짐 보조 로직의 오탐과 연산 급증 가능성

현재는 수평 자세 외에 머리 패치 추적과 급격한 하강도 사용한다. [src/tracks.c](../src/tracks.c)의 패치 추적(447행)이 실패했을 때 기존 머리 상태를 무효화하는 처리가 없어, 오래된 위치가 판단에 남을 수 있다. 급격한 하강 분기는 유지 시간 없이 즉시 알림을 낸다.

[src/main.c](../src/main.c)의 회전 재탐지 경로(1223행 부근)는 사람을 놓쳤을 때 영상을 양방향으로 회전해 재추론한다. 조건에 따라 한 처리 프레임에서 사람 모델을 최대 3번 실행하지만, 추가 호출이 기존 추론 횟수·누적 시간 집계에 반영되지 않는다.

**개선 방향**

- 관절·머리 위치에 유효 시간을 부여한다.
- 추적 실패 시 판단을 유보하거나 신뢰도를 낮춘다.
- 회전 재추론의 실행 횟수와 시간 예산을 제한한다.
- 추가 추론도 성능 지표에 포함한다.
- 청소·물건 줍기·착석·눕기·실제 쓰러짐을 포함한 영상으로 오탐과 미탐을 평가한다.

Pose 모델 자체가 제공하는 것은 관절 위치이므로, 쓰러짐 판단 성능은 별도 검증해야 한다. [Ultralytics Pose 문서](https://docs.ultralytics.com/tasks/pose/)

### 5. 로컬 전용 목표와 서버 설정의 불일치

[src/stream.c](../src/stream.c)의 471행과 [dashboard/server.c](../dashboard/server.c)의 742행은 모든 네트워크 인터페이스에 바인딩한다. 영상 조회, 기준 이미지 저장, 설정 변경 경로에 인증 검사도 보이지 않는다.

방화벽이 허용하면 다른 장치에서 접근할 수 있는 상태다. 인터넷에 자동 공개된다는 뜻은 아니지만, 로컬 전용은 보장되지 않는다.

**개선 방향**

- 기본 바인딩을 `127.0.0.1`로 설정한다.
- LAN 접근이 필요한 경우에만 명시적으로 활성화한다.
- 원격 접근을 허용할 경우 영상 조회와 설정 변경에 인증을 추가한다.

### 6. 청결 기준과 카메라 장애 판정의 현장 조건 반영 부족

[src/slot_monitor.c](../src/slot_monitor.c)의 기준 이미지 생성(228행)은 사람이 겹치지 않으면 현재 모습을 기준으로 채택한다. 시작할 때 이미 쓰레기가 있으면 그것이 정상 기준이 될 수 있다.

[src/camera_health.c](../src/camera_health.c)의 카메라 정지 판정은 픽셀 변화량 기반이므로 빈 매장의 정적인 영상도 장애로 판단할 수 있다. 프레임 자체가 오지 않는 상태는 별도의 수신 시간 감시가 필요하다.

**개선 방향**

- 청결 확인 후 기준을 확정한다.
- 가구 검출 박스의 흔들림 영향을 줄이기 위해 고정된 테이블 영역 사용을 검토한다.
- 카메라는 영상 변화량과 마지막 프레임 수신 시각을 함께 감시한다.

## 성능 현실성

C 구현, 버퍼 재사용, 움직임 기반 추론 생략, 최신 프레임을 가져오는 캡처 구조는 제한된 하드웨어에서 유리한 선택이다.

다만 C로 작성했다고 YOLO 연산량 자체가 크게 줄지는 않는다. 현재 스레드 3개 설정도 OS용 스레드 하나를 보장하는 방식은 아니다. ONNX Runtime 내부 스레드와 캡처·스트리밍 부하를 함께 측정해야 한다. [ONNX Runtime 스레드 관리 문서](https://onnxruntime.ai/docs/performance/tune-performance/threading.html)

실제 i5-4200U에서 다음 조건을 비교해야 한다.

- 빈 매장과 여러 사람이 움직이는 장면
- 사람 감지만 실행하는 경우와 Tier 2를 함께 실행하는 경우
- 스트리밍 클라이언트가 없는 경우와 연결된 경우
- 정상 추론 경로와 회전 재추론·머리 추적이 발생하는 경우
- 시작 직후와 장시간 실행 후의 처리 시간 및 리소스 사용량

이번 검토만으로 목표 CPU 사용률이나 실시간 처리 성능 달성을 보장할 수는 없다.

## 권장 진행 순서

1. Tier 2 실행 문제와 관측 상태 만료를 수정한다.
2. 네트워크 접근을 제한한다.
3. 핵심 기능만 실제 매장에서 검증한다.
4. 검증 결과를 바탕으로 기능을 확대한다.

초기 제품 범위는 사람·장기 체류, 문 개방, 카메라 이상, 청소 필요 의심 정도가 현실적이다. 주문 위반·외부 반입·응급상황 확정은 추가 정보와 검증이 필요한 별도 목표로 두는 것이 적절하다.

## 검증 지표 및 확인 결과

현장 검증에서는 단순 FPS보다 다음 지표가 중요하다.

| 지표 | 확인 목적 |
|---|---|
| 매장 하루당 오탐 수 | 점주가 감당할 수 있는 알림 수준인지 확인 |
| 실제 사건 미탐률 | 중요한 상황을 놓치는 정도 확인 |
| 알림 지연 | 사건 발생부터 알림까지의 시간 확인 |
| ID 변경 횟수 | 체류·주문 상태 연결의 안정성 확인 |
| 장시간 CPU·메모리 변화 | 지속 운용 가능성 확인 |
| 추론 호출 횟수·소요 시간 | 보조 추론을 포함한 실제 연산 비용 확인 |

이번 검토에서 확인한 결과:

- 현재 소스로 `test_core` 빌드 성공
- 단위 테스트 66개 통과
- CTest의 `core_unit` 통과
- 현재 실행 주기 조합에서 0~899프레임 중 Tier 2 실행 가능 프레임 0개

단위 테스트 통과는 개별 코드의 기본 동작을 뒷받침하지만, 실행 루프 전체와 실제 매장의 감지 신뢰도까지 입증하지는 않는다. 실제 대상 장치 성능, 현장 영상의 오탐·미탐률, 장시간 운용 안정성은 추가 검증이 필요하다.
