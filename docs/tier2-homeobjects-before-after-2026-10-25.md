# Tier 2 × HomeObjects-3K 활용 전후 비교 (2026-10-25)

`TODO/HomeObjects-3K Dataset.md`의 데이터셋을 Tier 2(cat/dog/bottle/cup/food/chair/dining table, YOLO11n 320px)에 쓸 수 있는지, 그리고 C 런타임을 유지한 채 성능을 올릴 수 있는 레버가 무엇인지 같은 조건에서 측정한 기록이다. 모든 수치는 `scripts/`의 스크립트로 재현되며, 측정하지 못한 것은 "미측정"으로 적었다.

## 결론

1. **HomeObjects를 넣어도 우리가 신경 쓰는 지표는 오르지 않았다.** COCO 계열 검증(v3 val)에서 의자 AP50은 0.336 → 0.337, mAP50은 0.5081 → 0.5046(−0.0035), mAP50-95는 0.3434 → 0.3434로 사실상 같다. 회귀(기존 클래스가 망가지는 일)는 없었다.
2. **HomeObjects val에서의 큰 상승(식탁 AP50 0.339 → 0.710, 의자 0.529 → 0.663)은 일반화가 아니다.** A1은 HomeObjects *train*으로 학습했으므로 그 val은 같은 분포(거실 사진, 같은 라벨 기준)다. 학습 데이터에 거실 커피테이블을 `dining table`로 넣었으니 오르는 것이 당연하다. 카페에서 의자·식탁이 더 잘 잡힌다는 증거는 이 실험에 없다.
3. **효과가 큰 쪽은 입력 해상도다.** 재학습 없이 같은 A0 모델의 입력만 320 → 416으로 키워도 병 AP50 0.329 → 0.401, 컵 0.397 → 0.454, 의자 0.336 → 0.372로 오른다(외부 음료 알림의 근원인 병·컵이 가장 크게 오름). 비용은 추론 지연 10.5ms → 17.2ms(×1.64, 개발 PC). 단 **식탁의 박스 정확도(AP50-95)는 0.371 → 0.269로 떨어진다**(320으로 학습한 모델에 큰 물체를 더 크게 보여 줘서 생기는 것으로 보이며 원인은 검증하지 않았다). 416으로 *재학습*하면 달라질 수 있지만 이번에는 하지 않았다.
4. **클래스별 NMS 수정(C 변경)은 모델과 무관하게 맞는 수정이지만 효과는 작다.** 앱 경로를 재현해 3,719장에 적용하면 식탁 재현율 0.496 → 0.536이 가장 크고, 고양이·개는 재현율이 +1.5%p 오르는 대신 정밀도가 −2.5%p 떨어진다. 의자는 사실상 그대로다.
5. **배포 모델(`models/yolo11n_tier2_fp32.onnx`)은 바꾸지 않았다.** 위 1·2 때문에 A1을 채택할 근거가 없고, 416은 재학습·4200U 지연 실측이 먼저 필요하다. 계획서의 "모델 교체" 단계는 채택 기준(AP가 더 높고 지연 예산 안)을 통과한 후보가 없어서 수행하지 않았다.

## 1. C 후처리: 클래스별 NMS

**문제**: `postprocess.c`의 NMS는 `class_id`를 보지 않아, IoU가 0.45를 넘는 서로 다른 클래스의 박스를 점수가 낮은 쪽부터 지웠다.

**단위 테스트 전후** (`test_nms_keeps_overlapping_boxes_of_different_classes`, 같은 위치에서 IoU≈0.68로 겹친 박스 2개):

| 입력 | 수정 전 | 수정 후 |
|---|---|---|
| 의자(0.9) + 식탁(0.8) | 1개 남음 (`list.count==2: 1!=2`) | 2개 |
| 고양이(0.9) + 의자(0.7) | 1개 남음 | 2개 |
| 의자 + 의자(같은 클래스) | 1개 | 1개(중복 제거 유지) |
| `test_core` 전체 | 117 통과 / 2 실패 | **119 통과 / 0 실패** |

수정 전 코드에서 새 테스트가 실패하는 것을 확인한 뒤 고쳤다. 원본 코드로 되돌려 실행한 출력은 `before` 두 줄(`tests/test_core.c:1511`, `:1522`의 `1!=2`)로 남아 있다.

**기존 테스트 하나의 기대값을 바꿨다.** `test_decode_embedded_nms`는 "person이 아닌 row는 필터링된다"고 주장했지만, 코드 주석(`postprocess.c:395`)은 필터링을 호출자에게 위임한다고 적고 있었다. 테스트는 클래스 비구분 NMS가 우연히 그 row를 지워서 통과하고 있었다. 이제 클래스를 보존해 둘 다 돌려준다. Tier 1(pose)은 `class_id`가 항상 0이라 이 변경으로 동작이 달라지지 않는다.

**앱 경로 재현** (`scripts/compare_nms_app_path.py`: ONNX 원시 출력 → 앵커별 argmax → 신뢰도 컷 → NMS(IoU 0.45)를 파이썬으로 재현해 NMS만 바꿔 적용, 모델 A0): 아래 부록의 표를 보면 conf 0.20에서 클래스별 NMS가 추가로 살린 박스는 v3 val 268개, HomeObjects val 5개다.

| 클래스 (v3 val, conf 0.20) | 재현율 전 → 후 | 정밀도 전 → 후 |
|---|---|---|
| dining table | 0.496 → **0.536** | 0.631 → 0.624 |
| dog | 0.646 → 0.664 | 0.754 → 0.726 |
| cat | 0.789 → 0.804 | 0.813 → 0.788 |
| chair | 0.320 → 0.322 | 0.528 → 0.527 |
| bottle / cup / food | 변화 ≤ 0.007 | 변화 ≤ 0.005 |

"의자가 식탁 앞에서 지워질 것"이라는 처음의 예상은 데이터로는 크게 확인되지 않았다. 변경 자체는 클래스 비구분이 정당한 경우(사람 한 클래스뿐인 Tier 1)에만 쓰도록 바로잡은 것이고, 이득은 식탁 재현율과 동물이 가구 위에 있을 때에 한정된다.

**라벨 누락 문제와 대응**: HomeObjects 이미지에는 cup/bottle/food/cat/dog 라벨이 없어, 그대로 학습하면 그 물체가 "배경"으로 학습된다. COCO 사전학습 `yolo11x`를 교사로 train 이미지에서 이 5클래스만 자동 라벨했다(conf≥0.5, 클래스는 ID가 아니라 *이름*으로 조회 — 과거 `docs/2026-09-10-tier2-dataset-labeling-issue.md`의 ID 밀림 사고를 피하려고). 추가된 교사 라벨은 cup 206, bottle 155, food 34, dog 32, cat 28개로 많지 않다.

**교사 라벨 육안 확인**: 교사 라벨이 붙은 이미지 286장 중 무작위 12장(시드 0)을 박스를 그려 확인했다(`runs/tier2-v4/teacher_preview.jpg`). 개 2건, 사람이 든 머그컵, 병은 타당해 보였다. **접시 위 흰 그릇이 `cup`으로 잡힌 것과 선반 위 작은 박스 줄은 의심스러웠다.** 12장만 본 것이라 라벨 품질의 정량 수치(정밀도)는 없다. 계획서의 "100장 확인"은 하지 못했다.

**table 라벨의 의미 문제**: 같은 12장에서 사람이 단 `table` 라벨의 상당수가 소파 앞 커피테이블, 사이드 테이블, 낮은 선반이었다. 이것을 `dining table`로 합치면 클래스 의미가 넓어진다(`docs/tier2-data-plan-2026-09-20.md`가 임의 변경을 경계한 부분).

## 3. 모델 비교: A0(배포 중) vs A1(HomeObjects 추가 학습)

- **A0**: `tier2_v3_fresh`(v3 데이터, 120에폭 학습 중 best 91에폭). 배포 중인 `models/yolo11n_tier2_fp32.onnx`와 **바이트 단위로 동일**하다(SHA256 `b5b31a69…32c2` 일치). 재학습하지 않고 그대로 썼다.
- **A1**: A0와 같은 레시피(`yolo11n.pt`에서 시작, 최대 120에폭, 배치 128, AdamW lr0 0.001, lrf 0.01, warmup 5, patience 35, 시드 0)로 v4 데이터에서 학습. **109에폭에서 조기 종료**(best 70에폭, 학습 107분).
- 평가: (a) v3 val 3,315장(학습 중 모델 선택에 쓰인 낙관적 세트, 회귀 확인용), (b) HomeObjects val 404장(chair/table만 정답). 평가 스크립트가 기존 감사(`docs/tier2-accuracy-audit-2026-09-20.md`)의 A0 수치를 정확히 재현했다(mAP50 0.5081, mAP50-95 0.3434).

| 지표 | A0 | A1 | 차이 |
|---|---|---|---|
| (a) v3 val mAP50 | 0.5081 | 0.5046 | −0.0035 |
| (a) v3 val mAP50-95 | 0.3434 | 0.3434 | 0.0000 |
| (a) chair AP50 | 0.336 | 0.337 | +0.001 |
| (a) dining table AP50 / AP50-95 | 0.531 / 0.371 | 0.522 / 0.374 | −0.009 / +0.003 |
| (a) bottle / cup / food AP50 | 0.329 / 0.397 / 0.455 | 0.327 / 0.391 / 0.452 | −0.002 / −0.006 / −0.003 |
| (a) cat / dog AP50 | 0.809 / 0.701 | 0.810 / 0.695 | +0.001 / −0.006 |
| (b) HomeObjects chair AP50 | 0.529 | 0.663 | +0.134 (A1에게는 같은 분포) |
| (b) HomeObjects table AP50 | 0.339 | 0.710 | +0.371 (A1에게는 같은 분포, 라벨 정의 변경 효과 포함) |

(a)의 차이는 모두 ±0.01 이내다. 각 모델을 한 번씩 학습한 결과이고 반복 학습으로 분산을 재지 않았으므로, 이 정도의 차이는 실행 간 변동과 구별되지 않는다(A0 자체도 같은 레시피로 재현해 보지 않았다). **식탁 합병이 카페형 식탁(v3 val)을 해쳤는지**는 AP50이 −0.009로 작아서 해쳤다는 증거는 없다. 그래서 계획했던 "chair만 추가" 변형(A1c)은 학습하지 않았다.

## 4. 해상도 효과 (재학습 없음)

같은 가중치를 입력 크기만 바꿔 다시 내보내 평가했다(`A0_n_416`, `A0_n_480`, `A1_n_416`). 모델이 320으로 학습됐으므로 "더 큰 입력에서 얼마나 오르는가"의 하한에 가깝고, 해당 해상도로 *재학습*한 결과가 아니다.

| 모델 | 입력 | (a) mAP50 | (a) mAP50-95 | bottle AP50 | cup AP50 | chair AP50 | table AP50-95 | 지연 평균 |
|---|---|---|---|---|---|---|---|---|
| A0 | 320 | 0.5081 | 0.3434 | 0.329 | 0.397 | 0.336 | 0.371 | 10.47ms |
| A0 | 416 | 0.5400 | 0.3528 | 0.401 | 0.454 | 0.372 | 0.269 | 17.22ms |
| A0 | 480 | 0.5477 | 0.3395 | 0.433 | 0.480 | 0.377 | 0.187 | 23.05ms |
| A1 | 416 | 0.5379 | 0.3514 | 0.393 | 0.452 | 0.373 | 0.274 | 17.85ms |

- 해상도를 올리면 병·컵·의자 재현율이 오른다(예: 병 재현율@0.35 0.216 → 0.275(416) → 0.315(480), 정밀도는 거의 유지). 외부 음료 룰의 입력이 개선되는 방향이다.
- 식탁 AP50-95는 크게 떨어진다. 식탁은 `slot_monitor`와 표면 감지가 박스 위치를 쓰는 클래스라 이 하락은 무시할 수 없다. 416 **재학습**으로 해결되는지 확인이 필요하다.
- 지연은 개발 PC(i7-8700, 2스레드, ORT CPU, FP32)의 평균이다. **i5-4200U 실측은 하지 않았다.** 기존 문서(`i5-4200u-pose-tier2-load-estimate.md`)는 프레임 90에서 Pose와 Tier 2가 직렬로 돌아 이미 145~225ms 스톨을 추정하므로, 416 모델은 그 위에 지연을 더 얹는다. 추가량의 4200U 환산은 하지 않았다.

## 6. 한계와 미측정

- (a) v3 val은 학습 중 모델 선택에 쓰인 세트라 낙관적이다(기존 감사와 같은 한계). 독립 현장 평가가 아니다.
- (b) HomeObjects val은 A0에게는 도메인 밖이지만 A1에게는 같은 분포다. A1의 상승을 일반화로 해석하면 안 된다. 어느 쪽이든 거실 사진이라 카페와 다르다.
- 각 모델은 한 번씩만 학습했고 시드 변동을 재지 않았다. ±0.01 이내의 차이는 구별할 수 없다.
- 교사 라벨 품질은 12장 육안 확인뿐이다(정량 미측정).
- NMS 전후는 파이썬 재현이다. 전처리가 Ultralytics식 letterbox라 C 코드와 픽셀이 완전히 같지 않고, C의 후보 상한·최대 검출 수 제한도 재현하지 않았다. 두 NMS 변형이 같은 전처리를 쓰므로 *차이*는 공정하지만 절대 수치는 앱과 다를 수 있다.
- **실제 영상(`records/`)으로 `unmanned_detector.exe`를 돌려 `external_drink`·`animal_on_chair` 이벤트 수를 전후 비교하는 것은 하지 않았다.** 어느 영상이 해당 장면인지 특정하지 못했고, 룰 확정 필터(K-of-N)·모션 게이트가 섞여 NMS 효과를 분리하기 어렵다.
- i5-4200U 지연: 미측정. 현장 효과: 새 로그가 쌓여야 확인 가능(`scripts/analyze_field_logs.py`).
- 학습 데이터·모델은 AGPL-3.0(HomeObjects)과 Ultralytics 가중치(AGPL-3.0)에 기반한다. 현장 기기에 모델을 배포하는 것이 AGPL 의무에 해당하는지는 이 문서가 판단하지 않는다(README 제한 사항 참고). 이번에 배포 모델은 바뀌지 않았다.

## 7. 다음에 할 만한 것

1. **416으로 재학습**(`run_train_tier2.py --imgsz 416`): 식탁 박스 하락이 사라지는지, 병·컵 이득이 유지되는지 확인. 4200U 지연을 실측한 뒤에만 배포를 검토한다.
2. 카페 현장 프레임 일부를 직접 라벨링해 평가 세트로 쓰기. 거실 데이터의 효과도 카페 기준으로 다시 잰다.
3. 재현 방법은 아래 순서다.

```
# 1) 데이터: datasets/homeobjects-3K 에 zip 을 풀어 둔 상태에서
.venv-train\Scripts\python.exe -I scripts\build_tier2_homeobjects.py --table merge --out datasets\tier2_v4
# 2) 학습(같은 레시피, 배포 모델을 덮어쓰지 않도록 --no-deploy-copy)
.venv-train\Scripts\python.exe -I scripts\run_train_tier2.py --data <v4 yaml> --weights yolo11n.pt --epochs 120 --batch 128 --device 0 --workers 8 --amp --patience 35 --optimizer AdamW --lr0 0.001 --lrf 0.01 --warmup-epochs 5 --warmup-bias-lr 0.001 --weight-decay 0.0005 --project runs\tier2_v4_n320 --no-deploy-copy --no-int8
# 3) 평가·지연·표
.venv-train\Scripts\python.exe -I scripts\eval_tier2_homeobjects.py --label A1 --model <onnx> --imgsz 320
.venv-train\Scripts\python.exe -I scripts\bench_tier2_latency.py --model <onnx>
.venv-train\Scripts\python.exe -I scripts\report_tier2_tables.py --labels A0,A0-n416,A0-n480,A1,A1-n416
```
