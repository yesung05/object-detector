# 학습 데이터 수집 및 규칙 기반 시스템 설계

## 1. 목적

셀프 무인 카페에 설치되는 영상 분석 SW가 매장마다 다른 구조와 카메라 환경에서도 일관되게 동작하도록 다음 체계를 정의한다.

- 어떤 영상을 어떤 조건에서 수집할지
- 사람·테이블·컵·트레이·문 상태를 어떻게 라벨링할지
- 학습/검증/운영 데이터를 어떻게 분리할지
- 모델 출력과 주문 데이터를 어떤 규칙으로 결합할지
- 규칙을 어떻게 검증하고 매장별로 조정할지
- 오탐과 미탐을 운영 데이터로 다시 개선하는 방법

이 문서는 [시나리오.md](시나리오.md)와 [order-group-verification-design.md](order-group-verification-design.md)의 시나리오를 실제 데이터와 규칙으로 구현하기 위한 기준 문서다.

## 2. 전체 구조

시스템은 모델과 규칙의 역할을 분리한다.

```text
카메라 영상
  ↓
객체/자세 모델
  ├─ 사람, 컵, 트레이, 포장, 문 상태 후보
  └─ bbox, confidence, keypoint
  ↓
관측 계층
  ├─ 짧은 track
  ├─ 테이블별 인원
  ├─ 새 상품 등장
  └─ 카메라 가시성/건강 상태
  ↓
규칙 계층 ← 주문 DB/로그의 결제·취소 이벤트
  ├─ 그룹 형성
  ├─ 주문 크레딧 생성·배정
  ├─ 증거 점수 계산
  └─ 상태 전이
  ↓
CONFIRMED_ORDERED / LIKELY_ORDERED / UNVERIFIED / REVIEW_REQUIRED
```

모델은 “사람이 주문했다”를 직접 판정하지 않는다. 모델은 관측 가능한 객체와 자세만 제공하고, 주문 상태는 시간·수량·ROI·상품 증거를 결합한 규칙이 결정한다.

## 3. 데이터 종류

### 3.1 원본 영상 데이터

가능하면 운영 해상도와 FPS 그대로 보관한다. 다만 개인정보와 저장 비용 때문에 상시 원본 저장을 기본값으로 두지 않는다.

수집 단위는 다음 중 하나를 사용한다.

- 설치 검증용으로 동의된 시간대의 연속 영상
- 이벤트 전후 짧은 클립(예: 전 30초, 후 90초)
- 오탐/미탐 신고 시 저장된 제한 클립
- 사람이 없는 매장의 배경·조명 변화 영상

모든 영상에는 다음 메타데이터를 함께 기록한다.

```json
{
  "clip_id": "store01-cam02-20260830-143200",
  "store_id": "store01",
  "camera_id": "cam02",
  "floor": 1,
  "started_at": "2026-08-30T14:32:00+09:00",
  "duration_seconds": 120,
  "width": 1920,
  "height": 1080,
  "fps": 15,
  "camera_role": "seating",
  "visibility_grade": "B",
  "lighting": "day",
  "crowd_level": "medium",
  "layout_version": "store01-layout-v3"
}
```

`layout_version`은 테이블·카메라·가구 배치가 바뀔 때마다 변경한다. 같은 카메라라도 배치가 바뀌면 다른 환경으로 취급한다.

### 3.2 주문 이벤트 데이터

기존 키오스크 SW는 수정하지 않고, DB·로그·파일·기존 API를 읽기 전용으로 수집한다.

필수 필드:

```json
{
  "event_id": "unique-id",
  "order_id": "A1042",
  "kiosk_id": "kiosk-01",
  "event_type": "paid",
  "event_at": "2026-08-30T14:32:11+09:00",
  "menu_count": 4,
  "cover_count": 4
}
```

- `event_id`: 중복 이벤트 제거에 사용한다.
- `event_type`: `paid`, `cancelled`, `refunded`를 구분한다.
- `menu_count`: 실제 메뉴 수량이다.
- `cover_count`: 1인 1메뉴 정책에 따라 주문이 커버할 인원 수다. 세트·사이드·무료 증정 때문에 `menu_count`와 다를 수 있다.
- 주문 시스템에 `cover_count`가 없으면 별도 매핑 규칙으로 계산한다.

카메라 시간과 주문 시간은 동일한 시계 기준으로 동기화해야 한다. 시간 오차는 매칭 실패의 주요 원인이므로 장치별 오차를 운영 지표로 기록한다.

### 3.3 파생 관측 데이터

원본 영상에서 다음 관측 이벤트를 생성한다.

| 이벤트 | 주요 필드 |
| --- | --- |
| `person_seen` | camera, track, bbox, confidence, ROI, timestamp |
| `table_occupancy` | table, people_count, confidence, timestamp |
| `group_started/updated/ended` | group, table, people_count, timestamps |
| `product_appeared` | class, table, bbox, confidence, first_seen |
| `product_removed` | object, table, last_seen |
| `door_state_changed` | door, state, confidence, timestamp |
| `camera_health_changed` | camera, state, evidence, timestamp |

파생 데이터에는 모델 버전과 규칙 버전을 반드시 남긴다. 같은 영상도 버전에 따라 결과가 달라질 수 있기 때문이다.

### 3.4 정답 데이터

정답은 자동 판정과 분리해 사람이 검수한다.

- 프레임 정답: 객체 위치와 클래스
- 구간 정답: 객체가 새로 등장·사라진 시점
- 테이블 정답: 시간대별 실제 인원 수
- 주문 연결 정답: 어느 테이블/그룹이 어느 주문으로 커버됐는지
- 이벤트 정답: 쓰러짐, 장기 체류, 문 열림 등 실제 발생 구간
- 판정 가능성: `observable`, `partially_observable`, `not_observable`

카메라에 보이지 않는 사실을 추측해 정답으로 만들지 않는다. 영상과 주문 데이터만으로 알 수 없는 경우 `not_observable`로 라벨링하고 학습 및 규칙 정확도 계산에서 별도 집계한다.

## 4. 수집 범위 설계

### 4.1 매장 다양성 축

데이터는 단순히 영상 시간을 많이 모으는 것이 아니라 아래 조합을 의도적으로 포함해야 한다.

| 구분 | 포함해야 할 조건 |
| --- | --- |
| 매장 크기 | 소형, 중형, 넓은 매장 |
| 층 | 단층, 1층+2층, 상층 카메라 있음/없음 |
| 카메라 | 단일, 다중, 화각 중첩, 중첩 없음 |
| 구조 | 기둥, 파티션, 계단, 유리 반사, 낮은 조명 |
| 시간 | 주간, 야간, 개점 직후, 폐점 직전 |
| 혼잡도 | 무인, 1~2명, 보통, 혼잡 |
| 고객 구성 | 1인, 2인, 3인, 4인 이상, 합류·분리 |
| 주문 | 1인 1메뉴, 한 명이 여러 명 몫 결제, 연속 결제, 취소·환불 |
| 상품 | 컵, 트레이, 포장, 기존 잔, 가림, 미수령 |
| 행동 | 착석, 이동, 자리 변경, 화장실, 2층 이동, 테이크아웃 |

### 4.2 정상 데이터가 우선이다

운영 환경 대부분은 정상 상황이다. 정상 데이터가 부족하면 규칙이 흔한 행동을 이상으로 판단한다.

초기 수집 권장 비율:

| 분류 | 비율 |
| --- | ---: |
| 일반 정상 운영 | 60% |
| 경계/혼동 상황 | 30% |
| 실제 또는 연출 이상 상황 | 10% |

경계 상황에는 사람이 컵을 가리는 경우, 기존 컵이 남은 경우, 테이블 합석, 여러 팀의 동시 이동, 아이가 작게 보이는 경우, 직원 청소 등이 포함된다.

### 4.3 희귀 위험 이벤트

쓰러짐·카메라 가림·장시간 문 열림 등 희귀 이벤트는 실제 발생만 기다리지 않는다.

- 안전하게 연출한 쓰러짐 자세
- 카메라를 천·손·종이로 일부/전체 가린 영상
- 조명을 끄거나 강한 빛을 비춘 영상
- 문을 다양한 각도와 시간으로 열어 둔 영상
- 영상 스트림 정지·반복·프레임 드롭을 인위적으로 만든 입력

실제 위험 행동을 연출할 때는 안전 담당자와 공간을 확보하고, 일반 고객이 없는 통제된 시간에 진행한다.

### 4.4 하드 네거티브

모델이나 규칙이 자주 틀리는 “비슷하지만 정답이 아닌 것”을 별도 수집한다.

- 컵처럼 보이는 조명, 화분, 휴지통, 테이블 장식
- 사람처럼 보이는 포스터, 마네킹, 유리 반사
- 쓰러진 것처럼 보이는 소파에 기대거나 엎드린 자세
- 문 상태를 가리는 사람, 그림자, 역광
- 하나의 컵을 여러 각도에서 중복 검출하는 장면
- 청소 중 모인 컵과 실제 고객 상품

하드 네거티브는 오탐 원인을 줄이는 데 일반 데이터보다 가치가 높으므로, 오탐 검토 때마다 별도 목록에 추가한다.

## 5. 현장 수집 절차

### 5.1 설치 직후 기준 데이터

각 카메라에서 다음 순서로 10~30분씩 수집한다.

1. 사람이 없는 매장과 모든 테이블이 빈 상태
2. 조명 켜짐/꺼짐 및 주간/야간 변화
3. 테이블마다 1~4명이 앉은 상태
4. 컵·트레이를 0개부터 최대 예상 수량까지 배치
5. 사람이 컵을 가리거나 들고 이동하는 상태
6. 문 닫힘·부분 열림·완전 열림 상태
7. 계단 및 사각지대 진입·이탈

이 데이터로 ROI, 기준 루마, 객체 크기, 검출 가능한 테이블을 확인한다.

### 5.2 운영 중 이벤트 샘플링

상시 원본 저장 대신 다음 조건에서 제한 클립을 생성한다.

- 규칙이 `UNVERIFIED` 또는 `REVIEW_REQUIRED`를 생성한 경우
- 운영자가 오탐·미탐으로 표시한 경우
- 모델 신뢰도가 임계값 주변인 경우
- 신규 매장/새 레이아웃의 초기 관찰 기간
- 기존 데이터에 드문 인원·조명·상품 조건인 경우

가능하면 이벤트 전후 링 버퍼를 사용해 원인을 확인할 문맥을 함께 저장한다.

### 5.3 개인정보와 보존

- 원본 영상 접근 권한을 최소화한다.
- 학습용 반출 데이터는 얼굴·화면 개인정보를 블러 처리하거나 필요한 객체 영역만 잘라 사용한다.
- 매장·카메라 ID는 외부 학습 데이터에서 익명화한다.
- 영상, 라벨, 주문 데이터의 보존 기간을 별도로 정한다.
- 주문번호는 해시 또는 내부 샘플 ID로 치환하고 결제 개인정보는 수집하지 않는다.
- 데이터 삭제 요청과 모델 학습 반영 이력을 추적할 수 있어야 한다.

## 6. 라벨 체계

### 6.1 객체 라벨

초기 클래스:

```text
person
cup
tray
food_container
takeout_bag
door_open_region (선택)
```

각 객체에는 다음 속성을 붙일 수 있다.

```text
occluded: none / partial / heavy
truncated: true / false
table_id: T-01 / T-02 / none
usable_evidence: true / false
source: customer / staff / leftover / unknown
```

`source`는 영상에서 명확한 경우에만 지정한다. 모르면 `unknown`으로 둔다.

### 6.2 테이블 인원 라벨

일정 간격의 프레임 또는 변화 시점마다 기록한다.

```json
{
  "table_id": "T-03",
  "timestamp": 145.2,
  "visible_people": 3,
  "estimated_occupants": 4,
  "observability": "partially_observable"
}
```

- `visible_people`: 실제 프레임에서 보이는 사람 수
- `estimated_occupants`: 앞뒤 영상 문맥상 테이블에 머무는 것으로 확인된 인원
- `observability`: 정답 신뢰도

### 6.3 상품 등장 이벤트 라벨

단순 컵 수 외에 “언제 새 상품이 테이블에 귀속됐는지”를 표시한다.

```json
{
  "event": "product_placed",
  "class": "cup",
  "table_id": "T-03",
  "started_at": 244.0,
  "stable_at": 248.5,
  "quantity_delta": 1,
  "observability": "observable"
}
```

기존 잔, 청소 중 이동한 잔, 잠깐 지나간 컵은 `new_product_evidence`에서 제외하는 정답을 함께 남긴다.

### 6.4 주문·그룹 연결 라벨

```json
{
  "order_id_hash": "sha256:...",
  "cover_count": 3,
  "assigned_table_id": "T-03",
  "assigned_group_id": "G-0012",
  "ground_truth_status": "confirmed",
  "evidence": ["count_match", "three_new_cups"],
  "observability": "observable"
}
```

정답 검수자가 영상만으로 확정할 수 없으면 `ground_truth_status=unknown`으로 둔다. 이 샘플은 오탐/미탐 분모에서 제외하고, 불확실 상태 처리 능력을 평가하는 별도 세트에 포함한다.

## 7. 라벨링 품질 관리

- 라벨링 가이드에 긍정·부정·모호 사례 이미지를 포함한다.
- 초기 데이터와 어려운 데이터의 일부는 2명이 독립 라벨링한다.
- 불일치는 제3 검수자가 확정하고 가이드에 사례를 추가한다.
- 클래스별 최소 객체 크기와 가림 기준을 수치화한다.
- 매장/카메라별 라벨 통계를 확인해 특정 환경에 편중되지 않게 한다.
- 라벨 수정 이력을 버전으로 남긴다.

권장 이중 라벨 비율은 초기 20%, 안정화 후 5~10%다. 주문·그룹 연결 정답은 객체 bbox보다 판단이 복잡하므로 더 높은 비율로 이중 검수한다.

## 8. 데이터셋 분리

### 8.1 누수 방지

같은 영상의 인접 프레임을 학습과 검증에 나누면 성능이 과대평가된다. 다음 단위로 묶어서 분리한다.

- 동일 연속 촬영 구간
- 동일 주문 세션
- 동일 방문 그룹
- 가능하면 동일 날짜

### 8.2 권장 분리

```text
train      70%: 모델 학습 및 규칙 후보 탐색
validation 15%: 임계값 선택과 모델 비교
test       15%: 최종 고정 평가
```

별도로 `unseen-store test`를 둔다. 학습에 포함되지 않은 매장 또는 레이아웃을 사용해 신규 설치 일반화 성능을 평가한다.

다음 테스트 세트를 고정한다.

- 주간/야간
- 단층/2층
- 소형/대형 매장
- 단일/다중 카메라
- 정상/혼잡/사각지대
- 컵·트레이 가시성 높음/낮음

## 9. 모델 학습 체계

### 9.1 초기 전략

1. 기존 사람/자세 모델은 유지하고 현장 평가부터 수행한다.
2. 컵·트레이는 기존 사전학습 모델의 실제 매장 성능을 측정한다.
3. 오탐·미탐이 많은 객체만 현장 데이터로 미세 조정한다.
4. 문 상태는 고정 카메라 ROI와 참조 영상 기반 규칙을 우선 사용한다.
5. 주문 여부 자체를 end-to-end 영상 모델로 학습하지 않는다.

### 9.2 증강

현장 조건에 맞는 증강만 적용한다.

- 밝기·대비·색온도 변화
- 약한 블러와 압축 노이즈
- 부분 가림
- 원근과 크기 변화
- 제한적인 수평 반전(문 방향 등 의미가 바뀌면 금지)

실제와 다른 극단적 합성 증강은 성능을 해칠 수 있으므로 검증 세트 개선 여부로 채택한다.

### 9.3 모델 평가 지표

객체 모델은 일반 mAP 외에 운영 지표를 본다.

| 대상 | 핵심 지표 |
| --- | --- |
| 사람 | 테이블별 인원 오차, 누락 지속 시간 |
| 컵/트레이 | 테이블별 신규 등장 precision/recall |
| 자세 | 쓰러짐 이벤트 precision/recall, 검출 지연 |
| 문 | 열림/닫힘 정확도, 상태 전환 지연 |
| 카메라 건강 | blackout/whiteout/frozen 오탐률 |

최종 목표는 bbox 자체보다 주문·체류 규칙에 필요한 관측이 안정적인지 확인하는 것이다.

## 10. 규칙 시스템 설계

### 10.1 규칙 계층

규칙을 네 단계로 분리한다.

1. **센서 규칙**: 카메라 blackout, whiteout, frozen, 문 상태
2. **관측 규칙**: track 유지, 테이블 점유, 신규 상품 등장
3. **도메인 규칙**: 주문 크레딧, 그룹 배정, 1인 1메뉴
4. **운영 규칙**: 유예 시간, 알림, 재알림, 수동 검토

낮은 단계가 불안정하면 높은 단계는 자동 확정을 중지한다. 예를 들어 카메라 상태가 불량하거나 테이블 가시성이 낮으면 미주문 알림을 내지 않는다.

### 10.2 규칙 입력과 출력

모든 규칙은 다음 공통 형태를 가진다.

```text
rule_id
version
enabled
scope(store/camera/floor/table)
input events
conditions
hold/grace/cooldown
output state or event
evidence
```

제안하는 버전형 규칙 설정 예시:

```json
{
  "rules_version": "2026-08-30.1",
  "store_profile": "self_service_cafe",
  "rules": {
    "table_group": {
      "enabled": true,
      "stable_seconds": 15,
      "empty_end_seconds": 60
    },
    "product_evidence": {
      "enabled": true,
      "classes": ["cup", "tray", "food_container"],
      "stable_seconds": 5,
      "order_window_seconds": 600
    },
    "order_assignment": {
      "credit_ttl_seconds": 1200,
      "confirm_score": 0.8,
      "likely_score": 0.55,
      "ambiguity_margin": 0.15,
      "allow_split_order": false
    },
    "unordered_review": {
      "enabled": true,
      "grace_seconds": 600,
      "minimum_visibility_grade": "B",
      "cooldown_seconds": 1800
    }
  }
}
```

현재 `config.json`은 단일 임계값을 저장하는 평면 구조다. 위 구조는 주문·그룹 규칙을 구현할 때 도입할 제안이며, 기존 설정과의 마이그레이션 및 기본값 처리가 필요하다.

### 10.3 상태 전이

테이블/그룹 상태는 다음처럼 관리한다.

```text
EMPTY
  ↓ 사람 안정 관찰
OCCUPIED_UNVERIFIED
  ├─ 주문/상품 증거 충분 → CONFIRMED_ORDERED
  ├─ 일부 증거           → LIKELY_ORDERED
  ├─ 상충/복수 후보      → REVIEW_REQUIRED
  └─ 비워짐              → CLOSED
```

상태가 한 번 확인됐다고 영구 유지하지 않는다. 새 인원이 합류하면 `observed_people > covered_people`인지 다시 평가한다.

### 10.4 주문 크레딧 규칙

```text
paid(order, cover_count=N)    → 미배정 크레딧 N 생성
assigned(order, group, K)     → 주문과 그룹 양쪽에 K 기록
cancelled/refunded(order)     → 미배정분 회수, 배정분은 REVIEW_REQUIRED
ttl_expired(order)            → unassigned_takeout_possible로 종료
```

한 그룹에 확정 배정되는 크레딧은 관찰 인원 수를 넘지 않는다. 메뉴 정책에 따라 `cover_count`를 계산할 수 없는 주문은 자동 배정하지 않는다.

### 10.5 주문 배정 점수

초기 점수는 설명 가능한 항목의 가중 합으로 만든다.

```text
score =
  w_count   × 인원/주문 수량 일치도
+ w_time    × 결제 후 그룹/상품 등장 시간 근접도
+ w_product × 신규 컵·트레이 증거 일치도
+ w_route   × 이동/카메라 간 연결 근거
+ w_unique  × 경쟁 후보가 없는 정도
- penalties × 가시성 저하·상충 증거
```

초기 가중치는 전문가 가설로 시작하되, 검증 데이터에서 정답률과 오탐 비용을 비교해 조정한다. 테스트 세트를 보고 반복 조정하지 않도록 validation에서만 결정한다.

### 10.6 보수적 판정 조건

다음 상황에서는 점수가 높아도 자동 확정을 제한한다.

- 카메라 상태가 blackout/whiteout/frozen
- 해당 테이블 가시성 등급이 기준 미만
- 동시에 점수가 비슷한 경쟁 그룹이 존재
- 주문 시간 동기화 오차가 허용 범위를 초과
- 주문 데이터가 중복·누락·역순으로 수신됨
- 사람 수 또는 상품 수 관측 신뢰도가 낮음
- 2층 등 카메라가 없는 구역

## 11. 현재 규칙과 개선 방향

현재 구현은 다음 규칙을 제공한다.

| 현재 기능 | 현재 기준 | 개선 방향 |
| --- | --- | --- |
| `overstay` | track 체류시간 초과 | 테이블/그룹 체류로 전환 |
| `unordered_seated` | `UNORDERED` track의 시간 초과 | 주문·상품 근거가 없는 그룹의 검토 이벤트로 변경 |
| `person_fallen` | bbox 비율·pose와 지속 시간 | 자세 변화·바닥 ROI·회복 여부 추가 |
| 문 상태 | ROI와 참조 이미지 차이 | 조명별 참조, 상태 신뢰도, 가림 감지 추가 |
| 카메라 건강 | 전체 프레임 루마·변화량 | 시간대 기준선, ROI 제외, 진단 근거 출력 |

현재 `unordered_seated`는 실제 착석·결제·상품 수령을 확인하지 않으므로 운영상 “미주문 확정”으로 사용해서는 안 된다. 주문·그룹 시스템이 구현되기 전까지는 비활성화하거나 “장기 체류 관찰”로 이름과 메시지를 변경하는 것이 안전하다.

## 12. 규칙 개발 절차

모든 신규 규칙은 다음 순서로 도입한다.

1. 실제 운영 시나리오와 실패 시나리오를 문서화한다.
2. 필요한 입력 데이터와 관측 가능 조건을 정의한다.
3. 정답 데이터에 규칙을 오프라인 재생한다.
4. validation에서 임계값을 선택한다.
5. 규칙 버전과 변경 사유를 기록한다.
6. 운영에서는 알림을 보내지 않는 `shadow mode`로 먼저 실행한다.
7. 점주 검토 결과로 오탐·미탐을 수집한다.
8. 기준을 만족한 매장/카메라 범위에서만 알림을 활성화한다.

### 규칙 변경 기록 예시

```json
{
  "rule_id": "unordered_review",
  "from_version": "1.2",
  "to_version": "1.3",
  "changed_at": "2026-09-10T10:00:00+09:00",
  "changes": {
    "grace_seconds": {"from": 300, "to": 600},
    "minimum_visibility_grade": {"from": "C", "to": "B"}
  },
  "reason": "야간 및 2층 이동 고객 오탐 감소",
  "validation_dataset": "rules-val-2026-09-v2"
}
```

## 13. Shadow Mode와 리플레이

### 13.1 Shadow Mode

규칙은 계산하지만 점주 알림이나 외부 동작은 실행하지 않는다. 다음을 기록한다.

- 어떤 규칙이 언제 발화했는지
- 사용한 사람 수·주문 수량·상품 증거
- 후보 그룹별 점수
- 자동 판정을 막은 가시성/카메라 상태
- 이후 운영자의 정답 표시

### 13.2 리플레이

저장된 파생 이벤트 또는 짧은 영상 클립을 같은 시간 순서로 재생해 새 규칙을 시험한다. 규칙 변경 전후 결과를 동일 데이터에서 비교한다.

리플레이 결과에는 최소한 다음을 포함한다.

```text
규칙 버전
전체 평가 이벤트 수
확정 주문 precision/recall
UNVERIFIED 오탐률
평균 판정 지연
관측 불가로 보류한 비율
매장/시간대/가시성 등급별 결과
```

## 14. 운영 피드백 루프

```text
운영 판정
  ↓
점주 확인: 맞음 / 오탐 / 미탐 / 판단불가
  ↓
원인 분류
  ├─ 객체 검출 실패
  ├─ ROI/카메라 문제
  ├─ 주문 데이터 문제
  ├─ 규칙 임계값 문제
  └─ 본질적으로 관측 불가
  ↓
학습 데이터 또는 규칙 개선 후보 등록
  ↓
오프라인 평가 → Shadow Mode → 제한 배포
```

오탐을 모두 모델 학습 문제로 보내지 않는다. ROI 설정, 시간 동기화, 주문 중복, 가시성 부족은 규칙/설치/데이터 파이프라인 문제다.

## 15. 평가 기준

### 15.1 모델 계층

- 사람 검출 누락률과 테이블 인원 MAE
- 컵/트레이 신규 등장 precision/recall
- 쓰러짐 이벤트 precision/recall과 검출 지연
- 문 상태 정확도와 전환 지연
- 카메라 건강 상태 오탐률

### 15.2 규칙 계층

- `CONFIRMED_ORDERED` precision: 확정이라고 한 그룹 중 실제 주문 그룹 비율
- 주문 크레딧 배정 recall: 관측 가능한 정답 주문 중 올바르게 배정한 비율
- `UNVERIFIED` 오탐률: 실제 주문 그룹을 점검 대상으로 잘못 표시한 비율
- `REVIEW_REQUIRED` 비율: 사람이 검토해야 하는 비율
- 평균 판정 지연: 결제/착석 후 상태가 결정되기까지 시간
- 자동 보류 적정성: 관측 불가 상황에서 잘못 확정하지 않은 비율

무인 카페에서는 미주문자를 놓치는 것보다 정상 고객을 미주문자로 잘못 판단하는 비용이 더 클 수 있다. 따라서 초기에는 recall보다 `CONFIRMED_ORDERED`와 `UNVERIFIED`의 오탐 억제를 우선한다.

## 16. 배포와 매장별 설정

### 16.1 공통 규칙과 매장 프로필

- 공통 기본값: 모델 임계값, 상태 전이 구조, 안전 제한
- 매장 프로필: 층, 카메라 역할, 테이블 ROI, 가시성 등급
- 카메라 보정값: 루마, 문 참조 이미지, 객체 최소 크기
- 운영 정책: 1인 1메뉴 계산, 테이크아웃, 유예 시간

규칙 코드와 매장 설정을 분리해 한 매장 튜닝이 다른 매장에 영향을 주지 않게 한다.

### 16.2 Hot Reload 안전 조건

- 새 설정은 스키마와 범위를 검증한 뒤 적용한다.
- 적용 실패 시 기존 정상 설정을 유지한다.
- 규칙 버전과 적용 시각을 로그·대시보드에 표시한다.
- 포트, 모델 파일 등 재시작이 필요한 항목과 즉시 적용 가능한 규칙을 구분한다.
- 상태 임계값 변경 시 기존 latch와 진행 중 그룹을 유지할지 초기화할지 규칙별로 명시한다.

## 17. 초기 구현 우선순위

### 1단계: 데이터 기반 만들기

- 이벤트 클립 및 메타데이터 포맷
- 테이블/층/카메라 ROI 설정
- 주문 데이터 읽기 어댑터와 시간 동기화
- 운영자 오탐·미탐 표시 기능

### 2단계: 관측 안정화

- 테이블별 인원 카운트
- 컵·트레이 신규 등장 검출
- 카메라 가시성·건강 상태를 규칙 입력으로 연결
- 고정 리플레이 평가 세트 구축

### 3단계: 주문 규칙

- 주문 크레딧 생성·취소·만료
- 그룹 후보와 설명 가능한 점수
- 상태 전이 및 Shadow Mode
- 대시보드의 판정 근거 표시

### 4단계: 제한 운영

- 가시성 A/B 매장에서만 자동 확인
- 장기 `UNVERIFIED`는 점검 알림으로만 제공
- 매장별 성능을 평가해 활성 범위를 확대

## 18. 완료 기준

규칙 기반 주문 확인 기능은 다음 조건이 충족되어야 운영 활성화할 수 있다.

- 주문 데이터 중복·누락·시간 오차가 측정되고 허용 범위 안이다.
- 테이블별 사람 수와 신규 상품 등장 성능이 매장별로 검증됐다.
- `not_observable` 상황에서 자동 확정하지 않는 테스트가 통과한다.
- 규칙 버전, 입력 근거, 상태 전이가 로그로 재현 가능하다.
- Shadow Mode에서 정상 고객을 `UNVERIFIED`로 표시하는 비율이 합의된 기준 이하이다.
- 점주가 자동 판정 근거를 확인하고 수동으로 수정할 수 있다.
